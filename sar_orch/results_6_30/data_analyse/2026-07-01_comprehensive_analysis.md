## 三、智能体数量影响分析

### 3.1 综合性能对比

| 智能体数量 | 有效实验 | 完成率 | 平均覆盖率 | 平均转运率 | 平均步数 | 平均Token | 平均耗时 |
|-----------|---------|--------|-----------|-----------|---------|----------|---------|
| 2 | 22 | 86.4% | 0.994 | 0.948 | 29.1 | 486,071 | 284s |
| **3** | **23** | **91.3%** | **1.000** | **0.987** | **24.9** | **450,670** | 399s |
| 4 | 22 | 81.8% | 1.000 | 0.946 | 33.5 | 690,562 | 592s |
| 5 | 25 | 80.0% | 0.994 | 0.948 | 29.3 | 610,268 | 518s |

**核心洞察：3 智能体是最佳配置**
- 最高完成率 (91.3%)
- 最低平均 Token 消耗 (450,670)
- 最少平均步数 (24.9)
- 最高平均转运率 (0.987)

**4 智能体出现"协作退化"：**
- 完成率下降至 81.8%（比 3 智能体低 9.5%）
- 步数激增至 33.5（比 3 智能体多 34%）
- Token 消耗暴涨 53%（690k vs 450k）
- 耗时翻倍 (592s vs 399s)

### 3.2 智能体闲置率分析

| 智能体数量 | 闲置率 (NoOp) | 说明 |
|-----------|-------------|------|
| 2 | 19.6% – 27.4% | 基本合理 |
| 3 | 24.7% – 47.1% | 开始出现竞争 |
| 4 | 51.1% – 59.4% | **过半时间闲置** |
| 5 | 51.1% – 66.0% | **严重冗余** |

**重要发现：智能体闲置率从 2→5 翻倍。** 当智能体 ≥4 时，超过一半的动作是 NoOp（空操作），表明：
1. 协调器无法有效并行分配任务
2. 任务执行完毕后智能体无事可做
3. 智能体越多，边际收益递减越严重

### 4.2 Token 效率（Token/步）

| 智能体数量 | Token/步 | 相对增长 |
|-----------|---------|---------|
| 2 | 15,973 | 基准 |

### 4.3 个体智能体 Token 分布

**原因：** Alice 作为首个命名的智能体，协调器优先向其派发任务。

Completion/Prompt 比稳定在 **2-5%**，表明 Prompt 非常冗长而 LLM 输出极其简洁。

## 五、失败分析

### 5.1 失败类型分布

| 失败原因 | 数量 | 涉及场景 |
|----------|------|---------|
| 步数耗尽（60步上限） | 10 | S2, S3, S4 |
| 连接/端口冲突 | 4 | S5 |

**14 个失败实验全部表现为：**
- 覆盖率 = 1.0（探索完成）
- 转运率 < 1.0（消防/救援未完成）
- 步数达到 60 步硬限制
- `finished = False`

**即：探索阶段全成功，但消防/转运阶段在步数预算内无法完成。**

### 5.2 最高风险组合

1. **Scene 2 × 4 agents** — 3/4 失败，转运率仅 0.733
2. **Scene 3 × 5 agents** — 3/5 失败，转运率最低 0.611
3. **Scene 5 × 5 agents** — 2 连接/端口冲突 + 1 步数耗尽

### 5.3 端口冲突问题

Scene 5 的 4 个连接/端口冲突失败均来自 benchmark 并发运行时的端口竞争（benchmark 使用固定偏移量 `offset=0→8080/8191`）。

## 六、协调器调度模式

### 6.1 任务类型分布

| 任务类型 | 分发次数 | 占比 |
|---------|---------|------|
| 导航 (Navigate/Explore) | 1,594 | 27.8% |
| 补给 (GetSupply) | 1,534 | 26.7% |
| 人员救援 (Carry/DropOff) | 1,402 | 24.4% |
| 灭火 (UseSupply/Extinguish) | 1,320 | 23.0% |
| 空闲 (NoOp) | 0 | 0% |

协调器从不主动分发 `NoOp` 任务，所有闲置来自智能体层面的 `NoOp()` 选择。

### 6.2 调度策略特征

- 任务分配随场景推进呈阶段式变化：探索 → 补给 → 灭火 → 救援 → 交付
- 智能体数量增多后，智能体层面的 `NoOp()` 大幅增加，说明协调器无法有效并行化
- Coordinator Token 占比随智能体数量增加而下降（32%→19%），因为协调器开销相对固定

## 九、核心结论与建议

### 9.1 关键发现

1. **3 智能体是最优配置** — 在所有指标上表现最佳：完成率 91.3%、最少步数 24.9、最低 Token 消耗 450k
2. **4+ 智能体存在"协作退化"** — 闲置率超过 50%，完成率反而下降，Token 和步数双双增加
3. **60 步上限是主要瓶颈** — 所有 14 个失败实验的覆盖率均为 1.0，探索成功但来不及完成消防/转运
4. **Scene 3 是最难场景** — 完成率 75%，平均步数最高，Token 消耗最大
5. **Token 增长呈亚线性** — 智能体数量翻倍但 Token 仅增 23%，说明 LLM 调用效率高于线性
6. **不存在"部分成功"** — 每步每完成实验都达到了满覆盖率和满转运率；未完成实验都卡在转运率上
7. **端口冲突影响 Scene 5** — benchmark 并发时的端口分配问题导致 4 个实验失败

### 9.2 改进建议

| 问题 | 建议 |
|------|------|
| 60步上限不足 | 对困难场景增加步数预算至 80-100 步 |
| 4+ 智能体闲置率高 | 优化协调器任务并行分配策略，或设计动态智能体退出机制 |
| Token 消耗高 | 精简系统提示词，或使用 Token 预算约束 |
| 端口冲突 | 为 benchmark 并发引入动态端口分配或重试机制 |
| Scene 2 × 4 agents 100% 失败 | 需要单独调查：可能是该组合的地图布局+智能体起始位置导致严重路径竞争 |
| Alice 的 Token 偏差 | 为协调器添加智能体 round-robin 均衡调度 |

## 十、附录：数据说明

### 数据目录结构
```
results_6_30/benchmark/
├── scene_{1..5}/
│   └── agents_{2..5}/
│       └── seed_{0,10,20,30,40}/
│           ├── result.json          # {coverage, transport_rate, steps, finished, elapsed_seconds}
│           ├── summary.csv          # {per-agent token totals, total interactions}
│           ├── meta.json            # {scene, agents, seed}
│           ├── experiment_logs/
│           │   ├── trajectory.csv   # 每步的 actions, successes, observations, coverage, transport
│           │   ├── agent_interactions.csv  # 每个智能体的工具调用记录
│           │   ├── router_interactions.csv # 协调器子任务分发记录
│           │   ├── token_usage.csv  # 每次 LLM 调用的 Step, Agent, PromptTokens, CompletionTokens, TotalTokens
│           │   ├── summary.csv      # 聚合摘要（含 per-agent token 累计）
│           │   └── run_metrics.json # 运行指标
│           ├── error.log            # 错误日志
│           └── stderr.log           # 标准错误输出
```

### 指标定义
- **Coverage**: 地图探索覆盖率 (0-1)，1.0 表示完全探索
- **Transport Rate**: 人员救援完成率 (0-1)，1.0 表示所有人已送达
- **Finished**: 实验是否正常完成（覆盖率=1 且转运率=1，或达到步数上限）
- **Steps**: 实验实际消耗步数
- **Token**: LLM API 调用的 Prompt + Completion Token 总和
- **NoOp/Idle Rate**: 智能体执行空操作的动作占比
