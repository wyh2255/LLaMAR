## 1. Scene 5 深度分析

### 1.1 场景特征

Scene 5 是唯一一个**双人救援（2 persons）**场景，仅有 1 个 type B fire（1 个着火点）。该场景首次引入多人救援协作需求 —— 之前所有场景都只有 1 个 person。

- **1 fire**（type B, 1 灯） — 最简单的火情配置
- **2 persons** — 需要往返两次或双人同时搬运
- **task_timeout=35**

### 1.2 完整结果表

| Seed | agents=2 | agents=3 | agents=4 | agents=5 |
|------|----------|----------|----------|----------|
| **0** | OK 18s 244K | OK 22s 298K | OK 56s 1,535K | **OK 11s 1,502K** |
| **10** | OK 22s 314K | OK 16s 853K | OK 22s 426K | FAIL 60s tr=0.64 1,050K |
| **20** | FAIL 60s **tr=0.36** 1,126K | OK 31s 501K | OK 13s 244K | OK 13s 817K |
| **30** | OK 42s 870K | OK 23s 1,553K | OK 15s 1,419K | FAIL 61s tr=0.93 1,620K |
| **40** | OK 25s 264K | FAIL 60s **tr=0.43** 1,438K | OK 55s 2,132K | OK 8s 207K |
| **Succ** | **4/5 = 80%** | **4/5 = 80%** | **5/5 = 100%** | **3/5 = 60%** |

> 注意：a5 seed_0 最初失败，后经 retry 成功（多次重试消耗约 2.5M 额外 token）。

### 1.3 Agent 配置对比

| Agents | 成功率 | 成功均步数 | 失败均 tr | 平均 Token |
|--------|--------|-----------|----------|-----------|
| 2 | 80% | 27 | **0.36** | 564K |
| 3 | 80% | 23 | 0.43 | 929K |
| 4 | **100%** | 32 | — | 1,151K |
| 5 | 60% | 11 | 0.81 | 1,039K |

**核心发现：**
- **agents=4 是 Scene 5 的唯一完美配置**（100%）
- **agents=5 反而最差**（60%）— 5 个 agent 处理 1 个火 + 2 个人导致协调过载
- Scene 5 的失败跑运输率（tr=0.36, 0.43）是整个 benchmark 最低的值

### 1.4 Scene 5 独有失败模式：双人救援瓶颈

Scene 5 的 4 个失败跑都有一个显著特征：**coverage=1.0**（全部找到），但**运输率极低**：

| 失败 Run | Steps | Coverage | Transport Rate | 解读 |
|----------|-------|----------|---------------|------|
| a2 s20 | 60 | 1.0 | **0.36** | 仅完成约 1/3 搬运 |
| a2 s30 | 60 | 1.0 | **0.36** | 同上 |
| a3 s40 | 60 | 1.0 | **0.43** | 约 40% 完成 |
| a5 s10 | 60 | 1.0 | **0.64** | 中度不足 |
| a5 s30 | 61 | 1.0 | 0.93 | **最接近成功 — 差 0.07** |

**双人救援的计算：**
- 系统有 2 个人需要搬运
- 4 个失败跑中，a5 s30（tr=0.93）最接近成功（差 ~0.07 = 0.5 个人没完成）
- a2（2 agent）场景下 tr=0.36 意味着 2 个人中只完成了不到 1 个
- 这暗示 **双人搬运需要至少 3-4 个 agent 来协调**：1-2 个灭火 + 2 个搬运

### 1.5 对比 Scene 4（同为 1 fire 场景）

| 维度 | Scene 4 | Scene 5 |
|------|---------|---------|
| Fire | 1 big (A, 3 灯, 10x10) | 1 (B, 1 灯) |
| Person | **1** | **2** |
| 成功率 | 90% | 80% |
| 最佳 agent | a3/a5=100% | a4=100% |
| 最差 agent | a2/a4=80% | a5=60% |
| 失败模式 | tr=0.60-0.70（单人中度） | **tr=0.36-0.64（双人重度）** |

**结论：** 火情大小不重要，**人数决定难度**。Scene 5 虽然火更小（1 灯 vs 3 灯），但 2 个 person 使失败严重程度翻倍。

## 5. 关键结论

### 5.1 场景难度实证排名

```
Scene 4 (90%) ≈ Scene 1 (90%) < Scene 5 (80%) < Scene 3 (75%) < Scene 2 (55%)
   最易                                       (新场景)                  最难
```

### 5.2 Scene 5 独特发现

1. **双人救援是全新的难度维度**：火情变小（1 灯 vs 其他场景 2-3 灯），但 2 persons 将失败严重程度推到最高（全场最低 tr=0.36）
2. **agents=4 是 Scene 5 的最佳配置**（100%），其次是 a2/a3（80%），a5 最差（60%）
3. **更多 agent 不一定更好**：a5 比 a2 表现更差，验证了"过度协调"假说
4. **所有失败 coverage=1.0** — 系统能找到所有目标，但 2 persons 的双重运输要求导致调度瓶颈

### 5.3 Agent 配置建议

| 场景类型 | 推荐 agent 数 | 原因 |
|---------|-------------|------|
| 1-2 fires + 1 person | 3-5 | a5 在 S2 达到 100%，a3 在 S4 达到 100% |
| 3 fires + 1 person | **4** | a4=100%, a5=40% (过度协调) |
| 1 fire + 2 persons | **4** | a4=100%, a5=60% |
| 任何场景通用 | **3** | 5 场景中 4 场景 >= 80% |

### 5.4 系统局限

1. **max_steps=60 是硬瓶颈**：所有 24 个失败跑全部达到 max_steps。提高 max_steps 可能解决"4 缺 1"类失败
2. **双人救援场景暴露了运输协调短板**：即使找到全部目标，系统也无法在时限内完成双人搬运
3. **Scene 1 的 token 异常仍未解决**：建议排查 S1 的 LLM 配置

### 5.5 后续建议

1. **增加 max_steps 实验**：将 max_steps 从 60 提升至 80-100，看"4 缺 1"和双人瓶颈是否自然缓解
2. **S1 token 异常排查**：锁定 S1 a2 s30/40, a3 s10/40 复现分析 LLM 调用链
3. **Scene 5 专项优化**：双人搬运调度策略需要改进，尤其是 2-3 agent 场景
4. **探索中间 agent 配置**：比如 agents=3 在 S5 不够用，但 agents=5 又过度，agents=4 最优——agent 数的选择存在窄窗口
