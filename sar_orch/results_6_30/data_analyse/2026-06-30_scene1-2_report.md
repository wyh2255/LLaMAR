## 2. Scene 1 详细分析

### 2.1 Performance by Agent Count

| Agents | 成功/总计 | 成功步数(均值) | 失败步数 | 平均耗时(成功) |
|--------|----------|--------------|---------|-------------|
| 2 | 5/5 | 24.8 | — | 243.5s |
| 3 | 5/5 | 21.4 | — | 350.6s |
| 4 | 3/5 | 17.0 | 50 (×2) | 346.1s |
| 5 | 4/4 | 21.0 | — | 376.4s |

**关键观察：**
- **agents=3 反而是最佳配置**：5/5 全部完成，均值步数 21.4，且存在 outliers（seed 20 用了 55 步）
- **agents=4 最难协调**：2 个 50 步失败（seeds 0, 10），tr=0.73/0.87。比 2/3/5 都差
- **agents=5 出乎意料好**：4/4 全部成功，均值步数 21.0
- 所有失败的 runs 都达到了 **100% 覆盖率**，说明问题不在于"找不到目标"，而是"找到了但搬不回去"

### 2.2 Failed Runs 分析

| Run | 步数 | Transport | 问题 |
|-----|------|-----------|------|
| scene_1/agents_4/seed_0 | 50 | **0.73** | 卡在最后 4 个运输目标 |
| scene_1/agents_4/seed_10 | 50 | **0.87** | 卡在最后 2 个运输目标 |

失败模式与 agent 数正相关（agents=4 最差），说明 **coordinator 在中等规模 agent 下的负载均衡成问题**。更多 agent 不代表更好——4 个 agent 时协调开销最大。

### 2.3 Token 消耗分析

| Agents | Tokens/Step（均值） | 典型分布 |
|--------|-------------------|---------|
| 2 | 13.7K | Alice/Bob 大致均衡 |
| 3 | 16.3K | 一个 agent 可占 60%+ |
| 4 | 13.5K | 严重不均衡（某 agent 占 >50%） |
| 5 | 19.0K | 任务分片更自然 |

**token 效率模式：**
- 成功 runs 的 tokens/step 随 agents 增加而增加（每个 step 需要更多 LLM 调用）
- agents=2 seed_40（37步）用了 643K tokens——是同等步数平均的 2 倍
- agents=3 seed_20（55步）用了 1.13M tokens——一个 agent（Charlie）占了 53%
- 失败的 runs 每个 step 更"贵"，原因是 agent 空转产生无用 token

## 4. max_steps=60 的效果

对比 max_steps=50 和 max_steps=60 的 retry 结果：

| Run | max_steps=50 | max_steps=60 |
|-----|-------------|-------------|
| s1 a2 seed=40 | ❌ 50步 tr=0.80 | ✅ 37步 tr=1.00 |
| s1 a3 seed=30 | ❌ 50步 tr=0.93 | ✅ 15步 tr=1.00 |
| s1 a3 seed=40 | ❌ 50步 tr=0.73 | ✅ 12步 tr=1.00 |
| s1 a5 seed=10 | ❌ 50步 tr=0.73 | ✅ 19步 tr=1.00 |

**结论：多给的 10 步带来了显著改善**，几乎所有之前 50 步卡住的运行都在 60 步内完成。继续观察 agents=4 seeds 0/10 在 60 步下是否也能通过。

## 6. 结论与建议

1. **max_steps=60 是正确的选择**——显著降低了无谓的步数截断失败
2. **agents=4 是瓶颈**——成功率最低（60%），需要关注 coordinator 在 4 agent 时的负载均衡
3. **覆盖率 100% 但 transport 不完整**是普遍失败模式——agent 能找到所有目标但协同搬运失败
4. **种子 0 和 10 在 agents=4 时系统性地困难**——可能与场景布局和初始位置有关
5. **Scene 2 开局良好**——尚未出现异常
