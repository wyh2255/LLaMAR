## 6. 脱敏路径与决策文本误伤评估

**RedactionPolicy**（redaction.py:20-49）包装 `SensitiveTextRedactor`（src/Agent/redaction.py:94-178）。

**应用点（事件文本写入前）**：
1. **回调 fan-out 前（最关键）**：server.py:1613 `body = self._memory_redactor.sanitize_callback(body)`（secure 路径；redactor 取自 `ingestor.redaction`，server.py:685）。`sanitize_callback` = `redact_data` 深拷贝（redaction.py:37-45）。
2. **ingestor 证据值**：ingestor.py:751（`_reduce_evidence_in_tx` 每个 claim 的 value `redact_data` 后再进 reducer）；ingestor.py:767（`_append_projection_event` value 脱敏后进 Temporal payload）。
3. **legacy 单文本防御**：`sanitize_event`（redaction.py:47-49），例：sar_orch/map/store.py:295（agent.last_message）。
4. **失败 ToolResult**：`redact_tool_result`（src/Agent/redaction.py:154-178）。
5. **反思 trace**：`_redact_truth`（reflection.py:738-742，来自 long_term.py）。

**脱敏规则内容**（src/Agent/redaction.py）：
- 敏感**键**整值替换：authorization/cookie/credentials/password/secret/api_key/token/hmac/proof/signature/mail_body 等（:30-60）。
- 正则**模式**：`X-A2A-Callback-Proof:` 头（:66-69）、`Authorization: Bearer/Basic`（:70-77）、`Cookie:`（:78）、`api_key=`（:79-82）、`password/secret/...=`（:83-89）、**`\b[a-f0-9]{64}\b`（64 位 hex 串按 hmac 脱敏，:90）**。
- **精确 secret 替换**：构造 `RedactionPolicy(secret=coordinator_secret)` 时绑定（redaction.py:29-31），命中即替换（src/Agent/redaction.py:132-134）。

**决策文本（任务描述）误伤评估**：
- 坐标如 `(3,2)`、坐标串 `x=3,y=2`、人名 `Alice`、普通救援指令文本：**不含上述键/模式，不会被现有规则替换**（`=value` 模式仅匹配 password/secret/api_key 等关键字赋值；64-hex 模式需要 64 个连续 hex 字符）。→ 决策原文（含坐标/名字）可安全保留。
- 会触发替换的场景：文本中出现精确 `coordinator_secret` 本身、64 位 hex 串、`Authorization:`/`Cookie:`/`X-A2A-Callback-Proof:` 头格式片段。
- ⚠️ **关键坑**：现有 `_log_send_message` 把原始 `content` 直接写 logs（coordinator.py:152-159, 167-173），**无脱敏**。新决策 Temporal 写入若从该点取文本，必须显式套用 `RedactionPolicy`（如 `ingestor.redaction.redactor.redact(content)` 或构造 `RedactionPolicy(secret=...)`），否则决策原文（万一 LLM 输出含 secret）会以明文落入 `temporal_event.payload`，与既有 callback 路径的脱敏口径（server.py:1613）不一致。

## 7. env_step 语义与决策事件该带什么

- **temporal_event 不强制 env_step**：表 schema **没有 env_step 列**（store.py:134-155）。env_step 只存在于：`projection_field.env_step`（store.py:210，`INTEGER` 可空）与 evidence 事件 payload JSON 里的 `"env_step": inp.env_step`（ingestor.py:784）。
- **coordinator 侧 step 来源**：`_on_router_event` 取 `step = getattr(self._barrier, "_step_counter", 0)`（coordinator.py:240）→ 传给 `_log_send_message(step, args)`（coordinator.py:257）。即**决策事件应带的 env_step = tool_start 时刻的 `barrier._step_counter`**——这正是「dispatch 时的 step 参数」的唯一来源，二者是同一个值。
- **barrier._step_counter 语义**：初始化 0（barrier.py:114），每次 env step 完成后 `+= 1`（barrier.py:557）。即「已完成的环境步数」。
- **worker 侧对照**：telemetry 的 `step` 来自 `step_provider=lambda: getattr(self._barrier, "_step_counter", 0)`（sar_orch/worker.py:459），server 侧要求 int 否则整包零 claim（server.py:249-251）；observation 的 `step` 取自 obs 字段并进 evidence_id（server.py:944-946）。
- **写法建议**：决策事件把 env_step 放进 payload JSON（仿 ingestor.py:784 `{"env_step": ...}`），因为表无此列；reducer 的 env_step fence（projections.py:104-113）只作用于投影字段，决策事件不经过 reducer，env_step 仅为审计语义。
