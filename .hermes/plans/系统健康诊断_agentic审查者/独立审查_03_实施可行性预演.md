### 1.1 任务书指定核验点

**（a）update_plan 的 args 结构在 `_on_router_event` 的 tool_start 里能不能拿到？**

- tool_start 回调在**工具执行前**触发（`src/Agent/router_agent/agent.py:706-712`），`arguments` 已是解析后的 dict（`sar_orch/coordinator.py:255`）。
- `UpdatePlanTool.parameters` 只有**一个**属性 `plan`（完整计划节点列表，非增量），`required: ["plan"]`（`src/a2a/builtin_tools/update_plan.py:164-216`）。
- added/modified 前后对比是 `MissionGraph.replace` 的**执行结果**：`_format_plan_feedback` 吃 `view.get("diff")`（`update_plan.py:67-132`），tool_start 时刻不存在。
- tool_result 回调（`coordinator.py:286-290`）只带 `tool_name/success/error_code/content`（content 仅为 query_sar_state 用），**同样拿不到结构化 diff**。
- **结论**：方案 §3.1「added/modified 摘要：logical_id + changes 前后对比，复用 update_plan.py:31-53 的格式化语义」**在当前回调结构下不可实现**。格式化函数（31-53 段）吃的是 replace 的 diff view，不是 tool_start 的 arguments。三个出路，方案必须选边：
  1. tool_start 只记「计划声明」：新 plan 的 `logical_id` 列表 + 节点数 + revision 摘要（diff 由审查者对比两代 `coordinator_decision.update_plan` 事件自行推导——两代事件都在 temporal 流水里，可行）；
  2. 写入点改到 `UpdatePlanTool.execute` 内（a2a 内核层，需要新 hook 或直接在该工具里调 ingestor，超出 sar_orch 回调面，且 B10「不触碰既有 producer」的边界要重新解释——update_plan 不是 temporal producer，可动，但方案没写）；
  3. 扩展 tool_result 回调携带工具返回值（动 `agent.py` step_callback 契约，牵动面最大）。
  另注意：`plan` 全量文本可能很大（多节点 × objective/assignments/description），若事件带 plan 需 8000 字符截断（仿 `ingestor.py:794`），方案未提。

**（b）事件写入需要新的 ingestor helper 还是直接 append_temporal_event？**

- `append_temporal_event` 是生产唯一 INSERT 入口（`store.py:695-744`），但它是**事务原语**：必须在 `canonical_transaction()`（`store.py:611-627`，BEGIN IMMEDIATE）内调用；现有 4 个生产调用方全是 ingestor 内部 helper（`ingestor.py:512-541 / 543-574 / 756-801 / 929-947`）。
- **结论**：建议新增 ingestor helper（仿 `_append_projection_event`，`ingestor.py:756-801`），因为还需要 ① 幂等 claim（`store.claim_callback_idempotency`，`store.py:643-662`，按 scope_id+key 查 ledger，语义通用可直接复用，但命名是 callback 专用）、② 脱敏（`self._redaction.redactor.redact_data`，ingestor 实例属性）、③ scope fail-closed 检查（仿 `ingestor.py:366-369`）。直接裸调 append_temporal_event 也可行但 caller 要自己补这三样。
- **硬前提（方案未写）**：`coordinator.py` **没有 `self._memory_ingestor` 实例属性**——`memory_ingestor` 是 `start()` 内的局部变量（`coordinator.py:449-452`），只经 `state_provider.set_memory_ingestor()`（:458）传出，`self._memory_store` 在 :453 保存。P1 必须新增 `self._memory_ingestor` 保存点（或等价访问路径），否则 `_log_send_message` 拿不到写入通道。
- **scope 解析**：可复用 `_resolve_long_term_scope_id()`（`coordinator.py:704-741`，server 侧 `_resolve_export_scope_id` → `store.list_scopes()` 兜底，活动 scope 优先）；或 `ingestor.scope_id_for(context_id, runtime_epoch)`（`ingestor.py:305-306`），后者需要 context_id/epoch，tool_start 回调里没有，前者更合适。

**（c）test_memory_online_truth_boundary.py 固定集合断言会破在哪几行？**

**（b）多轮循环的同步执行与 ReflectionModelPort 的 asyncio.run 封装怎么接？**

- 滚动 daemon 线程无 event loop → 每轮 `asyncio.run`（`reflection.py:310-312`）路径自然可用；terminal 路径（event loop 内）→ `_invoke_off_thread`（`reflection.py:369-406`，join 上限 timeout_sec+5=305s）。同步 while 循环套每轮一次 `complete_with_function_call` 可行（方案 §5 正确）。
- **两个方案没写的约束**：
  1. `complete_with_function_call` **只匹配 tools[0]**（`reflection.py:336-346`：`if name != expected_name: continue`）——多工具轮（4 个查询工具同传）时，模型调用非 tools[0] 的工具会被静默跳过 → fail-closed 无 function_call。方案 §5「按 tools[0] 动态匹配，换 schema 无需改解析」**只对每轮单工具成立**。出路：每轮单工具（编排固定查询顺序）/ 扩展 port 支持多工具（动 reflection.py 契约，牵动 test_long_term_reflection.py 的 port 测试面，但测试用 stub port（:648）不改签名则基本不破）/ 合并为单工具（如 `query_evidence(source=...)`）。方案必须选边。
  2. `complete_with_function_call` 每次重建 `messages=[system, user]`（`reflection.py:302-305`）——**轮间工具结果没有回喂机制**，调用方必须自行把上一轮 tool result 序列化进下一轮 user_prompt（或 system_prompt）。方案说「每轮一次 LLM function-call」，但轮间上下文传递机制没写，这是 agentic 循环的核心实现缺口。
