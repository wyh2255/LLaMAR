## 1. 主方案内部一致性（§2 边界 / §3 契约 / §6 Phase / §7 风险 / §9 D1–D10）

### B-1（Blocker）§3.2 诊断字段集（D3 拍板）不含 `severity`，§3.3 渲染格式要求 `[severity]`，两处冻结契约直接矛盾

- **证据**：
  - 主方案 §3.2（L58）字段清单：`diagnosis_key`、`kind`、`target`、`finding`、`suggestion`、`confidence`、`source_refs`、`policy_version` —— 无 `severity`。
  - 主方案 §9 D3（L143）拍板：「诊断字段集：diagnosis_key/kind/target/finding/suggestion/confidence/source_refs/policy_version」—— 与 §3.2 一致，同样无 `severity`。
  - 主方案 §3.3（L66）渲染契约：「渲染：一行一诊断，`[severity] target: finding → suggestion (confidence=N)`」—— 渲染格式从字段集之外引入 `[severity]`。
- **分析**：P3 按 §3.2/D3 定义 DiagnosisCandidateV1 DTO 时没有 severity 来源；P4 按 §3.3 渲染时无处取值。实施者只能二选一偏离冻结契约（擅自加字段，或渲染时丢弃 severity），两者都违反「契约修订须回主方案重算 hash」的流程（补充 L76：「契约修订（回主方案，重算 hash）」）。
- **建议处置**：回主方案修订：要么字段集补 `severity`（含枚举与 validator 校验规则，走契约修订），要么渲染格式去掉 `[severity]`。G0 已过、hash 已冻结，此修订需重新冻结。

### M-1（Major）诊断循环与既有滚动反思的关系未定义：「升级为」vs「保持现状」vs「诊断与反思同模型配置」三处表述互相冲突，直接决定 P3 实施范围

- **证据**：
  - 主方案 §0（L14）：「长期记忆反思者**升级为** agentic 系统健康审查者」；目标 2（L19）：「反思者从「单轮 function-call 记忆提炼」**升级为**「多轮只读查询 + 方向性纠错」」—— 替换语义。
  - 主方案 §4 流程图（L71-83）：`coalesce 单飞（long_term_reflection.py:267-277）→ [新增] 决策事件…→ 快照…→ agentic 诊断循环`—— 单飞槽位只画了诊断循环，未画既有滚动反思。
  - 主方案 B7/D10（L33/L150）：「触发时机**保持现状**（每 N 步滚动 + terminal）」—— 现状语义（既有滚动反思仍存在）。
  - 主方案 R7（L115）：「**诊断与反思同模型配置**；触发频率保持现状」—— 并存语义。
- **分析**：若诊断取代滚动反思，则 G4 已批准正式可用的 `long_term_mode=read`（G4 记录 L29/L36）将失去滚动 producer（长期记忆只剩 terminal 反思），这是对已批准功能的隐性行为变更，主方案未声明；若并存，则同一触发点（experiment.py:810-832 的 task complete / every-N-step / supervision 三触发 + terminal）出现双循环，coalesce 单飞（long_term_reflection.py:267-277）一次只放行一个线程，调度语义、成本（R7 的「+6-10 次调用」口径）、terminal join 时序均未设计。新进度 L34 的 G4 边界讨论九条（「O-A 反思失忆 → 方向升级为 agentic 系统健康诊断通道」）也未能澄清是替换还是并存。
- **建议处置**：P3 实施前必须在主方案明示二者关系（推荐：明确并存、诊断循环与滚动反思共享触发点与 coalesce 槽位、各自独立计时），并纳入 G2 人工判断。

### M-3（Major）D9 诊断 audit 事件写入路径/校验机制未定义；provenance=reflection 与「allowlist 7→8」「B6 三重锁」自相矛盾

- **证据**：
  - 主方案 §3.1（L50）：「provenance：allowlist 加 `coordinator_decision`（contracts.py:69-79，**7→8**）；校验点 contracts.py:278 / ingestor.py:351,620,625 自动覆盖」。
  - 主方案 D9（L149）：「诊断产出同时写 canonical temporal `evidence.diagnosis_audit`（**provenance=reflection**，仅供 audit/评测，不进事实域）」。
  - 主方案 B6（L32）/目标 4（L21）：「`reflection` 来源 = FIELD_SOURCE_POLICY 最低优先级，冲突永远让位」——把 reflection 描述为可参与字段仲裁的来源。
  - 代码事实：`ONLINE_PROVENANCE_ALLOWLIST` 实测 7 项（contracts.py:69-79，无 `reflection`）；allowlist 校验点（contracts.py:278、ingestor.py:619-625）只作用于 `NormalizedProjectionInputV1`/`ingest_projection` 的投影输入，**对纯 temporal append 根本不触发**（探索 01 §3 亦确认）。
- **分析**：三处互斥：(a) 若 audit 事件走投影输入式校验，provenance=reflection 不在 allowlist 会被 `online_truth_forbidden` 拒绝——须把 allowlist 扩到 9 项，与 §3.1「7→8」矛盾，且破坏「测试面会破的断言」（探索 01 §7 的固定集合断言）；(b) 若走新 append helper 纯追加，则 §3.1「校验点…自动覆盖」对 audit 事件不成立，R6（L114）「FORBIDDEN_TRUTH_TERMS 照常校验」无落点，B6 的「最低优先级让位」成为永远无法触发的死语义（「三重锁」名不副实）；(c) 主方案 §4（L85）「不进投影 reducer 的事实域」只是断言，未给出机制（reducer 是 ingest 输入驱动、不扫描 temporal_event，故纯 append 路径天然安全——但这一点文档没有写明，实施者可能误走 ingest_projection 路径被拒，或误把 audit 事件当投影输入）。
- **建议处置**：主方案补一条 audit 写入契约：明确走「新 append helper + 写入前 validator（含 truth scan/redaction）+ 不构造投影输入」路径，并声明 allowlist 保持 7→8 不变、B6 降级为防御性声明或删除「三重锁」表述。

### M-4（Major）`evidence.diagnosis_audit` 自回声通道：长期记忆收集器与诊断时间线工具都会看到既往诊断

- **证据**：
  - 主方案 D9（L149）audit 事件进 canonical temporal；§4（L74）诊断窗口「收集器前缀 +1」；B5（L31）「诊断 source_ref 只允许指向四类在线证据，禁指向既有诊断」。
  - 代码事实：`_REFLECTION_EVENT_PREFIXES = ("control.", "callback.", "evidence.", "supervision.")`（reflection.py:431）—— **前缀是 `evidence.` 而非 G4 文本的 `evidence.projection`**，`evidence.diagnosis_audit` 会被长期记忆反思收集器 `accepts_event_type` 命中并进入长期记忆输入窗口；`store.temporal_events`（store.py:834-841）/ `MemoryReadPort.temporal_events`（environment_state_provider.py:139-144）返回 scope 全量事件，诊断自己的时间线工具与快照窗口同样可见 audit 事件。
  - G4 记录 L43：「反思输入范围扩展（仍只读 `callback.*`/`evidence.projection`/`supervision.*`/`control.*` 四类）」—— 与实现前缀 `evidence.` 本身已有偏差，新事件类型使该偏差产生实际后果。
- **分析**：回声室防护（B5）只守 source_refs 白名单，不守「提示/工具结果可见性」：诊断 LLM 的时间线查询会返回自己既往的 audit 事件（甚至长期记忆内容可源自诊断，形成 诊断→长期记忆→诊断 的二级回声环）；「禁指向既有诊断」的判别机制（按 event_type 前缀？按 diagnosis store 反查？）也未定义。
- **建议处置**：①长期记忆收集器/诊断窗口对 `evidence.diagnosis_audit` 显式排除（或把 G4 文本与实现前缀统一后对 diagnosis 单独例外）；②诊断时间线工具返回集过滤 audit 事件；③validator 明确「诊断引用」判定规则；以上三点均需测试守护（补充 R2 材料补「audit 事件不进任何反思窗口」的负例）。

### M-5（Major）诊断工具为实时查询（非快照窗口），source_ref 可验证性与原子快照一致性契约未定义

- **证据**：
  - 主方案 §4（L75-79）：先「快照 scope_event_snapshot」，随后「LLM 多轮 → 轮内工具调用 → 只读四类查询」；§5（L89-90）：「数据读取层已全部存在——MemoryReadPort 投影…、temporal 流水（store.py:835-840）…」—— 全部是实时读 API。
  - 主方案 §3.2（L58）：source_refs「只允许指向四类在线证据的 event_id」；§4（L79）validator「ref 可验证性」。
  - 上游：原子快照补充 L22-39（revision/events/digest 同一临界区、幂等键绑定 snapshot digest）、L61-62（G2 验收「snapshot_digest 与 support evidence 必须可复算一致」）。
- **分析**：诊断循环的 LLM 在快照之后实时查询 store，引用的 event_id 可能落在快照窗口外（多轮之间新写入的 callback/decision 事件）——「可验证性」对哪个集合成立未定义；若按快照窗口校验，实时工具查询必然产出大量「伪造 ref」误拒；若按实时 store 校验，则快照 digest 无法复算，长期记忆原子快照补充的一致性契约被架空（D6 模板 = LongTermMemoryStore，理应继承该契约）。
- **建议处置**：主方案明确二选一：工具读冻结快照（推荐，与原子快照契约对齐），或 ref 校验以实时 store + 写入时点记录为准（需另立一致性契约）。

## 3. 与 H1/H3 真值边界对照（H1 卡 L18/L34-43、H1 审批 L49-52、H3 记录 L82-88）

**正面结论**：

3. **coordinator_decision 的 H1 论证路径正确**：B9（L35）+ G1 门 + R1 判断项 1（补充 L40）与 H1 审批 L51「扩展须重新取得审查」的要求对齐。

**论证缺口（漏洞）**：
- M-7：LLM 产物（audit 事件）入 canonical 无 B9 式论证。
- M-4：audit 事件自回声（工具/收集器可见性）与 G4「四类」文本偏差（`evidence.` vs `evidence.projection`）。
