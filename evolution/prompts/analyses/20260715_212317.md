## Root Cause Analysis
### Cause 1: Coordinator prompt allows query-polling as a substitute for planning (Prompt weakness)
**What failed**: The `system.semantic.md` at `sar_orch/prompts/coordinator/system.semantic.md` lines 72-73 says:
> *"Every round, dispatch a task to EVERY online agent. Do NOT call `query_task_events` again immediately — that wastes steps. Instead, read Context Memory or dispatch/re-plan tasks for other agents, then query again."*
The LLM systematically ignores the "don't poll" instruction. After its 6 dispatches complete, the coordinator has no model of "what to do when all tasks are done" and falls into the path of least resistance: repeatedly calling `query_task_events` on stale task IDs. The prompt gives no explicit exit strategy or "if all tasks are COMPLETED and the mission isn't done, re-plan" instruction — it only tells the LLM what not to do, not what to substitute.
At step 34, with 8 identical queries on the same task IDs (all showing COMPLETED), the coordinator has clearly exhausted its planning ability. With `router_max_steps=200`, it could spin for hundreds of LLM calls before timing out — not hitting `max_steps`, but dying to the `orchestration_timeout=1200s`.
### Cause 2: No dispatch-to-every-agent enforcement (LLM behavior + code gap)
**What failed**: The prompt instructs "every round, dispatch to all online agents" but the system provides no guardrails. The coordinator dispatches:
- Round 1 (step 0): Alice + Bob → Explore
- Round 2 (step 6): Alice → firefighting, Bob → firefighting
- Round 3 (step 15): Alice → extend firefighting, Bob → confused rescue task
After dispatch-5 completes (Alice), the coordinator never dispatches again. Bob runs aimlessly on his stale dispatch-6 task (which never terminates because person rescue is impossible solo). The coordinator reads "RUNNING" for Bob and just keeps polling, never canceling the stale task or dispatching something new.
The code in `query_task_events.py` has a 5-second default wait (`timeout=5.0`). When it finds no terminal task, it loops inside the tool call waiting. This means each of those 27 queries consumed 0-5s of wall-clock time. The 8 queries at step 34 likely consumed ~40 seconds of real time.
### Cause 3: Person rescue task is unsolvable for a single agent (Prompt gap + coordination failure)
**What failed**: The worker prompt says "*2+ robots must carry simultaneously. All carriers must be at the deposit and ALL perform DropOff.*" But dispatch-6 gives Bob only a solo task (no coordination protocol for getting Alice to also participate in carrying). The worker prompt instructs agents to "*Check if another robot is also carrying before you try to move*" but the prompt has no concrete mechanism for agents to coordinate on shared rescue.
Bob's actions from step 15-34 show confused behavior: he teleports between LostPersonTimmy, ReservoirUtah, DepositFacility, ReservoirYork without any coherent plan. He never calls `carry_person` or `drop_off_person` — the system doesn't even show these as tool calls. The worker doesn't know how to execute a multi-agent rescue and falls back to aimless explore/navigate.
**Verification**: The tool distribution shows 8 `get_supply` but 0 `carry_person` or `drop_off_person` calls. The agents never attempted person rescue at all.
### Cause 4: Massive token waste from context memory injection every round (Architectural)
**What failed**: The `SARCoordinatorStateProvider.snapshot()` (in `sar_orch/coordinator_state_provider.py`) injects the full semantic map snapshot, task status view, recent changes, and supervision alerts on every single LLM call. With the semantic map tracking fires, persons, reservoirs, deposits, agents, observation records, and step budget, this context block is large.
Coordinator: 1,316,778 tokens across ~205 LLM calls = ~6,423 tokens/call. If most of that is injected context (not generated text), then each call carries ~5-6K of injected state overhead. With 27 query_task_events calls each triggering a full context injection, that's ~173K tokens just on query polling.

## Modification Recommendations
### Priority P0: Add query rate limiting and stale-task re-dispatch to coordinator prompt
**What to change**: `sar_orch/prompts/coordinator/system.semantic.md` — replace the "do not call query_task_events immediately" soft instruction with a hard action template.
**Specific change** — add this as a new section at line 90:
```
## Query Rate Limit (HARD RULE)
You may call query_task_events on the SAME set of task IDs at most ONCE per dispatch round.
After the first query:
- If ALL tasks are COMPLETED → immediately dispatch new tasks to ALL agents (next phase).
- If ANY task is RUNNING → call update_plan or dispatch tasks to IDLE agents. Do NOT query again until you have dispatched at least one new task.
- If ANY task is FAILED/CANCELED → cancel all stale tasks, then re-dispatch to that agent.
- If ANY task is INPUT_REQUIRED → reply immediately, then query ONCE more.
Violating this rule wastes step budget. If you have no new tasks to dispatch, evaluate:
  "Am I done fighting all fires? → rescue phase."
  "Am I done rescuing persons? → call finish_task(success=True, summary=...)"
  "Is there work I haven't assigned? → dispatch it NOW."
```
**Expected effect**: Hard-cuts the query loop. Forces the LLM to take action after every query instead of polling, and gives explicit phase transition triggers.
### Priority P1: Implement coordinator-side query deduplication with auto-termination
**What to change**: `src/a2a/builtin_tools/query_task_events.py` — add a per-task-store query counter that blocks repeat queries on the same task IDs without intermediate action.
**Specific change** — at the top of `execute()`:
```python
# In QueryTaskEventsTool.execute() — add dedup guard
store = self._store
query_key = tuple(sorted(task_ids))
if hasattr(store, "_last_query_key") and store._last_query_key == query_key:
    # Same task IDs queried again without any new dispatch — auto-return empty
    logger.warning("Repeated query_task_events for same tasks %s — forcing re-plan", task_ids)
    return ToolResult(
        success=True,
        content=json.dumps([{"task_id": tid, "state": "STALE", "action_required": "re-dispatch"} for tid in task_ids]),
    )
store._last_query_key = query_key
```
Also reduce the default `timeout` from 5.0 to 1.0 to prevent the 5s wait per query call (saves 27 × 4s = ~108s wall-clock time).
**Expected effect**: Eliminates the 8-query spin at step 34. The tool forces the coordinator to take action (dispatch/re-plan) instead of looping. Cuts wall-clock time by ~2 minutes.
### Priority P2: Add agent-level rescue coordination protocol and explicit tooling
**What to change**: `sar_orch/prompts/worker/system.md` — add a structured rescue protocol section, and verify the tools `carry_person` / `drop_off_person` are properly exposed.
**Specific change** — at the end of the worker's Critical Rules (after line 24), add:
```
## Person Rescue Protocol
1. NavigateTo(PersonName) — arrive at the person's location.
2. Call get_agent_state() to check if another agent is also at this person.
3. If solo: call no_op() and wait. The coordinator must dispatch a second carrier.
4. If 2+ agents present: all call carry_person(PersonName).
5. NavigateTo(DepositName) — all carriers go to the same deposit.
6. All call drop_off_person() simultaneously.
7. Finish the task.
IMPORTANT: If you are the only agent at the person, do NOT attempt carry_person solo.
Wait with no_op() until a second carrier arrives.
```
**Also**: Verify in `sar_orch/tools/worker/` that `carry_person.py` and `drop_off_person.py` tools exist and are loaded into the worker agent's tool list. From the tool distribution (explore, navigate_to, get_supply, use_supply, report_observation, finish_task, move, query_shared_memory, get_agent_state — no carry/drop), person rescue tools may be missing from the agent's toolset entirely.
**Expected effect**: Bob stops teleporting aimlessly. Person rescue becomes an explicit multi-step protocol the worker understands, with proper "wait for partner" behavior instead of random navigation.
### Priority P3: Reduce context memory injection overhead
**What to change**: `sar_orch/coordinator_state_provider.py` — `snapshot()` method. Trim the injected context for query-only rounds.
**Specific change**: Add a context mode flag in `RuntimeState`:
- When the coordinator calls `query_task_events`, inject only `task_status_view` and `step_budget` — skip the full semantic map snapshot (`semantic_summary` with fires, persons, agents, reservoirs, deposits, observations).
- On dispatch/re-plan rounds, inject the full snapshot.
**Expected effect**: Cuts ~3-4K tokens per query call. With 27 query calls, saves ~80-108K tokens per experiment run. This is compositive with P0 (fewer query calls overall).

## Good vs Bad Pattern
### Observed bad pattern
The coordinator dispatches a batch of tasks once, then switches into pure polling mode — querying completed task IDs repeatedly without ever re-planning or dispatching new work. Meanwhile, one agent (Bob) executes a broken task that never terminates (solo person rescue), wasting 19 environment steps. The coordinator never cancels the stale task, never re-dispatches, and never transitions to the rescue phase. The system enters a deadlock: the barrier waits for Bob's action, Bob's agent loop runs aimlessly (navigate → explore → navigate → ...), the coordinator polls completed tasks, and no new dispatches ever break the cycle.
### Desired good pattern
After each batch of tasks completes, the coordinator immediately reassesses: "Firefighting complete? → Transition to rescue. Rescue complete? → Call finish_task." Within 1-2 query calls of detecting COMPLETED status, the coordinator dispatches the next phase's tasks to ALL agents. Every agent always has a productive task. A stale-running agent is canceled and re-dispatched within 3 steps. The coordinator never calls query_task_events more than once per active task set without an intervening dispatch.
