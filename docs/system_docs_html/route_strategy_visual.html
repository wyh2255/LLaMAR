# Agentic 显式 DAG 路由与 Team Partition 策略

> **设计状态：目标设计 / 未实现契约。**
>
> 本文规定后续实现者必须达到的架构与行为契约，不是当前代码已经提供的功能清单。文中带有“**拟新增**”标记的类、接口、状态和端点均为目标结构；没有该标记的文件行号只用于说明当前实现、改造边界或现有兼容面。除非另有说明，当前阶段只改造 SAR 的 `orchestration_mode="agentic"` 路径；现有通用 `RouterAgent.DAGPlan` 与 `_execute_dag_loop()` 保持不变。

## 1. 设计目标与术语

本策略把 RouterAgent 的自主重规划保留下来，但将“计划声明、依赖顺序、物理派发安全、团队通信授权和终止清理”从 LLM 提示词中收回到框架。Router 负责提出逻辑任务及参与者；框架负责验证、占用、建队、派发、聚合和回收。

本文使用以下术语：

- **Mission**：一次外部请求在 Coordinator 内形成的完整 agentic 编排实例，由 `context_id` 标识。
- **逻辑节点 / logical node**：MissionGraph 中的 DAG 节点，由 Router 声明，例如 `rescue-thomas`。它表示一个逻辑目标，不等于一次 Worker A2A 任务。
- **参与者 / participant**：执行一个逻辑节点的 Worker ID 集合。单参与者节点也必须经过同一模型，只是无需多成员 TEAM_UPDATE。
- **物理派发 / physical dispatch**：发往某一个 Worker 的一次 A2A 任务及其状态、Worker 侧任务 ID、结果缓冲和取消记录。
- **TeamPartition**：Coordinator 权威维护的在线 Worker 通信划分。任何在线 Worker 同一时刻只能属于一个 active team。
- **peer mail**：Worker 到 Worker 的直接、签名 MAIL 旁路。它用于协作，不改变 DAG 节点完成状态，也不替代 Coordinator 对任务的派发权。

规范性用词：**必须**表示不变量；**应**表示默认实现；**可以**表示兼容或可选能力；“未来”或“拟新增”表示当前尚未实现。

## 2. 当前实现基线与改造边界

当前 agentic 路径能够派发任务和记录一些计划信息，但计划仍是 advisory task list，团队仍是单全局 roster。以下证据是当前代码，不应被误读为目标实现已经存在。

| 当前事实 / 问题 | 现有代码证据 | 影响 |
|---|---|---|
| `PlanNode` 是每个任务一条记录，`update_plan()` 只做替换、diff 和运行字段保留 | `src/a2a/coordinator/task_store.py:13-35`、`151-216` | 没有对依赖引用、环、参与者集合或激活顺序做框架级验证 |
| 未声明任务会被静默补成 ad-hoc 节点 | `src/a2a/coordinator/task_store.py:218-245`；调用方 `src/a2a/builtin_tools/dispatch_task.py:90-101` | LLM 可以绕过计划直接创造物理工作，逻辑 DAG 不是真正的路由门 |
| `dispatch_task` 是立即返回的 fire-and-forget 路径 | `src/a2a/builtin_tools/dispatch_task.py:102-143` | 返回成功不代表 Worker 已接受；多参与者 fan-out 无 awaited acceptance 事务 |
| `send_message(assign_task)` 只检查 Worker 存在和当前忙碌状态 | `src/a2a/builtin_tools/send_message.py:126-189` | 不检查声明节点、依赖已完成、计划的 Worker/participant 或团队安装 ACK |
| 逻辑 task ID 与 Worker task ID 通过双向字典兼容映射混用 | `src/a2a/coordinator/task_store.py:38-60`、`83-107` | 回调、取消、结果查询可能把两个命名空间交叉路由 |
| agentic 每次执行建立一个 `TaskStore`，超时/异常只取消未完成 Future | `src/a2a/coordinator/agent_executor.py:295-394` | 没有统一的物理任务取消、team lease 回收、callback/future 清理 finalizer |
| 周期同步直接把查询到的状态写回 PlanNode | `src/a2a/coordinator/agent_executor.py:914-964`、`src/a2a/coordinator/task_store.py:270-289` | push、sync、cancel、watchdog 没有唯一 canonical 状态入口 |
| push callback 有模块级 artifact cache，并自行解析 callback 状态 | `src/a2a/coordinator/server.py:52-54`、`664-860` | artifact 和终态可能脱离 mission 上下文，重复/乱序回调可能重复完成 |
| CoordinatorTeamRegistry 只有一个全局 team，configure 是整表替换 | `src/a2a/coordinator/team_registry.py:67-83`、`112-159` | 两个并行逻辑节点不能拥有两个不相交的通信队伍 |
| WorkerTeamState 只有一个 active membership | `src/a2a/worker/team_state.py:1-16`、`105-121` | 这本身适合“每 Worker 一个排他成员关系”，但不能支持当前全局 registry 的重叠语义；目标设计保留它 |
| `/team-status` 按 semantic map 枚举所有其它 agent，且只接受明文 `agent_id` | `src/a2a/coordinator/server.py:871-902` | 会把所有机器人误呈现为队友，并允许伪造身份查询；目标必须改为分区权威 + 认证请求 |
| Worker team-status 缓存只按 `env_step` | `sar_orch/worker_state_provider.py:65-89` | 同一 SAR step 内的 team 迁移不能触发刷新；目标缓存键必须包含 team generation |
| Worker context 已渲染 team summary / teammates，但未由 TeamPartition 过滤 | `sar_orch/worker_state_provider.py:155-169` | Context Memory 需要明确 safe fields 与 team 边界 |
| peer mail 的 `configure_team` 等工具是在启动后由 SARCoordinator 注入的 | `sar_orch/coordinator.py:412-456` | 当前必须依赖 Router 记得先手动配置 team；目标由框架在节点激活时自动完成 |
| Server 生命周期会停止 sync/watchdog/A2A，但没有 mission finalizer 钩子 | `src/a2a/coordinator/server.py:317-386`、`1334-1337` | Coordinator shutdown 必须进入 `MissionRuntime.abort()`，不能只让 Uvicorn 退出 |

当前代码中已有的 peer mail 签名、epoch、MailboxStore 和 `WorkerTeamState.delivery_snapshot()` 是可复用的基础，不等于已经满足本文的 exclusive partition 契约。现有协议与安全限制见 [`peer_mail.md`](./peer_mail.md)。

## 3. 最终三层模型

### 3.1 MissionGraph：逻辑 DAG

**拟新增** `MissionGraph` 只保存一次 Mission 的逻辑真相。每个 `MissionNodeSpec` 至少包含：

- `logical_id`：Router 声明的逻辑节点 ID，在该 Mission 内唯一；
- `participant_ids`：非空、无重复的 Worker ID 列表；兼容旧调用时由 `worker_id` 归一化为单元素列表；
- `objective` 与按 Worker 划分的 `assignments`；
- `depends_on`：只允许引用本图节点，不能自依赖，不能形成环；
- 声明状态（例如 pending/skipped），不允许覆盖框架维护的执行状态。

运行态节点由框架维护，目标状态为：

```text
planned -> blocked -> ready -> activating -> active -> completed
                                      │          ├-> failed
                                      │          └-> canceled
```

- `blocked`：存在尚未成功终态的依赖；
- `ready`：全部依赖为 completed/verified，参与者和资源满足激活前置条件；
- `activating`：已经 claim，但还在 team saga 或物理 dispatch acceptance 中；
- `active`：team 已安装，且至少一个物理派发被接受或正在执行；
- `completed`：全部参与者物理派发成功终态；
- `failed`：任一参与者失败/取消，除非未来显式 retry policy 改变该规则；
- `canceled`：被 MissionRuntime finalizer 或显式取消终止。

逻辑节点的完成不是 peer mail 的结果，而是其全部 PhysicalDispatch 聚合结果的结果。一个节点可以有多个参与者，不能再把旧 `PlanNode` 当作逻辑节点。

### 3.2 PhysicalDispatch：物理 A2A dispatch

**拟新增** `PhysicalDispatch` 是每个 Worker 的独立物理记录。它至少包含：

- `dispatch_id`：Coordinator 生成的 opaque ID，例如 `dsp_<uuid>`；
- `logical_node_id`：只作为内部关联，不作为 ID 生成规则；
- `worker_id`；
- `worker_task_id`：A2A/Worker 接受后返回的第三个 ID；
- canonical physical state；
- bounded artifact/result snapshot；
- cancellation outcome、source timestamps、terminal/finalization guard。

物理记录必须先在本地一次性预分配，再进行网络 I/O。每一个参与者都有一个 dispatch；多个 dispatch 共同构成一个逻辑节点的 fan-out。物理查询、取消、watchdog、push callback 和周期 sync 只能接收 `dispatch_id`，不应“先试 logical ID 再试 physical ID”。

### 3.3 TeamPartition：排他通信分区

**拟新增** `TeamPartitionRegistry` / `TeamPartitionService` 是 Coordinator 生命周期级的通信拓扑权威，不是 LLM 的第二份计划。

- 每个在线 Worker 恰好属于一个 active team；
- 默认队伍为 `solo:<worker_id>`，例如 `solo:Charlie`；singleton 不需要多成员 TEAM_UPDATE，但仍是有效的 peer-mail authorization domain；
- 多人临时协作队伍只在一个逻辑节点 `activating/active` 期间存在，例如 `team:rescue-thomas:<revision>`；
- 该逻辑节点终态后，成员恢复到各自 singleton，或在同一 Mission 已通过前置检查并持有 lease 的下一个节点中直接转入目标队伍；
- 任一 Worker 不能同时属于两个 collaborative team，也不能在 `INSTALLING`、`COMPENSATING`、`DEGRADED` 的 transition lease 中被另一个节点 claim。

Team ID、密钥、epoch、endpoint roster、transition ID 均由框架生成。Router 只能声明 participants 和 objective，不能声明 team secret、roster endpoint、epoch 或 dispatch ID。

### 3.4 三层关系

```text
MissionGraph (逻辑真相)
  logical node rescue-thomas
       │ participants=[Alice, Bob]
       │ depends_on=[scout-north]
       ▼
PhysicalDispatch (执行真相)
  dsp_7f... -> Alice -> worker_task_id=...
  dsp_91... -> Bob   -> worker_task_id=...
       │ terminal aggregation only
       ▼
TeamPartition (通信真相)
  team:rescue-thomas:r42 = [Alice, Bob]
  solo:Charlie             = [Charlie]
  solo:David               = [David]
```

TeamPartition 是 MissionGraph 的运行时派生拓扑；它不产生新的逻辑依赖，也不改变节点结果。PhysicalDispatch 是逻辑节点的物理展开；它不拥有新的逻辑目标。

## 4. Mission admission 与状态所有权

### 4.1 当前阶段：单一 active agentic Mission

本阶段的 admission 是硬约束：Coordinator 同时只允许一个 active agentic Mission。**拟新增** `ActiveMissionAdmission` 在 `_execute_agentic()` 创建 `TaskStore` 前取得 `context_id` lease；第二个请求必须返回 `mission_already_active` 或进入明确的等待队列，不能覆盖第一个 Mission 的 TaskStore、EventStore、Watchdog、state provider 或 callback。

该边界是对当前实现的诚实约束：

- `src/a2a/coordinator/agent_executor.py:295-394` 为每次 agentic 执行创建单个 TaskStore；
- `src/a2a/coordinator/agent_executor.py:914-964` 的周期状态同步从一个 watchdog 取一个 TaskStore；
- `src/a2a/coordinator/server.py:664-860` 的 callback 使用共享入口和模块级 artifact cache；
- `src/a2a/coordinator/task_store.py:38-60` 有模块级 Future 与 Worker ID 反向映射。

因此不能在本阶段宣称支持并行多 Mission。Admission lease 的所有权范围包括：MissionGraph、PhysicalDispatch map、结果缓冲、TaskWatchdog/state-provider attachment、TeamPartition transition ownership、callback/future 清理。

### 4.2 未来关系：ActiveMissionRegistry

**拟新增** `ActiveMissionRegistry` 是后续多 Mission 并发的替换点，而不是本阶段默认启用的组件。只有在 EventStore、TaskWatchdog、state projection、push callback、artifact buffer、Future registry 和 TeamPartition lease 都按 `context_id` 隔离后，才可以将单一 admission 扩展为多个 Mission。否则应继续使用 `ActiveMissionAdmission`，用 admission 失败而不是数据串线换取安全。

### 4.3 运行态所有权

```text
Coordinator lifetime
  TeamPartitionService
  persisted control secret + global membership epoch
  PartitionTransition journal
  ActiveMissionAdmission

Mission lifetime (one context_id)
  MissionRuntime
  MissionGraph
  PhysicalDispatch records
  result/artifact buffers
  watchdog/provider attachment
  callback/future ownership

Worker lifetime
  WorkerTeamState (one active membership)
  MailboxStore
  peer sender/inbound authorization context
```

任何跨层引用都必须通过明确的 owner API；禁止通过 module/global cache 找当前 Mission 或当前 team。

## 5. ID 命名空间与 canonical 物理状态机

### 5.1 logical / physical ID 完全分离

1. Logical ID 由 Router 在 MissionGraph 中声明，只在 MissionGraph API 中解释。
2. Physical dispatch ID 由 Coordinator 使用系统随机源生成，目标格式为 `dsp_<uuid>`，必须 opaque、不可预测、不可由用户字符串拼接得到。
3. Worker A2A task ID 是 Worker/SDK 产生的另一个 ID；它不能冒充 logical ID 或 dispatch ID。
4. 只有 TaskStore 内部映射允许 `logical_node_id -> dispatch_id -> worker_task_id`；对外查询、取消和 callback 路由必须显式给出对应命名空间。
5. 结果、artifact、watchdog、cancel、help reply 都必须先解析到唯一 `PhysicalDispatch`，不能用“两个字典都试一遍”的兼容策略。

### 5.2 唯一 canonical `apply_physical_status()`

**拟新增** `TaskStore.apply_physical_status(dispatch_id, raw_state, source, observed_at, result=None)` 是唯一允许改变 PhysicalDispatch lifecycle 的入口。以下来源必须全部调用它：

- awaited dispatch acceptance；
- `/a2a/push-callback`；
- `_periodic_state_sync()`；
- native cancellation 的结果；
- timeout、parent cancel、shutdown cleanup；
- startup recovery/reconcile。

该方法负责：

- 将 A2A/protobuf 原始状态映射为有限 canonical enum；
- 检查 transition 是否允许，拒绝终态回退；
- 第一次终态时保存有界结果并设置 finalization guard；
- 只触发一次 `MissionGraph.mark_dispatch_terminal()` 和逻辑聚合；
- 产出派发级事件，并让逻辑节点获得 release/reconcile eligibility；
- 将重复、过晚或无法归属的 callback 记录为 bounded diagnostic，不得改变新 Mission。

目标物理状态机：

```text
                         ┌──────────────┐
                         │ INPUT_REQUIRED│
                         └──────┬───────┘
                                │ help/reply
                                ▼
PREPARED -> DISPATCHING -> ACCEPTED -> RUNNING ───────┐
    │          │            │          │              │
    │          │            └──────────┴──────────────┤
    │          │                                       ▼
    │          └──────────────> CANCEL_PENDING -> CANCELED
    │                                             or FAILED
    │
    └──────────────────────────────────────> FAILED (acceptance error)

ACCEPTED/RUNNING/INPUT_REQUIRED -> COMPLETED | FAILED | CANCELED
COMPLETED/FAILED/CANCELED are terminal; terminal state never regresses.
```

`INPUT_REQUIRED` 是 active 物理状态，不是逻辑完成；`MAIL` 也不是完成信号。若父级终止时无法确认远端取消，必须保留 `CANCEL_PENDING`，不能伪装成 CANCELED。

### 5.3 逻辑聚合规则

- 所有参与者 dispatch 为 `COMPLETED`（或明确允许的 `VERIFIED`）时，逻辑节点变为 `completed`；
- 任一参与者为 `FAILED` 或 `CANCELED` 时，逻辑节点变为 `failed`，除非未来引入且已声明的 retry policy；
- 任一参与者为 `INPUT_REQUIRED` 时，逻辑节点保持 `active`，帮助请求只路由到对应 dispatch；
- 聚合由第一个物理终态触发的 canonical 方法完成 exact-once 保护，不能由 Router 读取 EventStore 后自行推断。

## 6. `activate_plan_node` 的规范时序

**拟新增** `send_message(message_type="activate_plan_node", related_task_id=<logical_id>)` 是 Router 激活节点的唯一正常入口。它不接受 `who` 或 `content`；participants、objective、assignment 全部来自已验证的 MissionGraph。

### 6.1 六阶段时序

```text
Router
  │ update_plan(full declarative graph)
  ▼
[1 DAG gate]
  │ ready? dependencies succeeded? admission lease?
  ▼
[2 participant claim]
  │ claim node + every Worker; reject busy/transition lease
  ▼
[3 Team ACK saga]
  │ prepare before/after partition snapshots
  │ TEAM_UPDATE to all affected members; await terminal ACKs
  ▼
[4 awaited fan-out acceptance]
  │ preallocate opaque dispatch IDs
  │ dispatch every participant concurrently
  │ await each first A2A acceptance and save worker_task_id
  ▼
[5 physical terminal aggregation]
  │ push/sync/cancel/timeout -> apply_physical_status()
  │ all terminal -> logical node terminal
  ▼
[6 release / reconcile]
  │ newer-epoch singleton restore or next-node direct transition
  │ release claims, clear buffers, emit final events
```

### 6.2 阶段 1：DAG gate

按以下顺序检查并返回稳定错误，不抛出未处理异常：

1. `related_task_id` 对应逻辑节点存在，否则 `node_not_found`；
2. 节点为 `ready`，否则 `node_not_ready`；
3. 所有 `depends_on` 节点为 completed/verified，否则 `dependency_incomplete`；
4. 当前 `context_id` 持有 active admission lease，否则 `mission_already_active`；
5. 所有 participant 在线、存在于 Agent/Worker registry，且没有 active physical dispatch；
6. 所有 participant 不在其它 node 的 activating/active claim 或非终态 transition lease 中，否则 `participant_busy`；
7. 多人节点要求 TeamPartitionService 预检通过。

`assign_task` 在 graph-managed Mission 中不能绕过 gate：已声明 logical ID 必须使用 `activate_plan_node`，未知 ID 返回 `undeclared_task`，不能再隐式 `add_adhoc_node()`。单 Worker 兼容调用可继续保留，但不能破坏已声明图。

### 6.3 阶段 2：participant claim

在网络调用前由 MissionRuntime 原子地：

- 将 logical node 从 `ready` 置为 `activating`；
- 给 node 和每个 participant 写入 mission-scoped claim/fence；
- 预留 transition ownership；
- 预分配全部 PhysicalDispatch 为 `PREPARED`；
- 固化当次 objective、assignments、team epoch 预期和 before-membership snapshot。

任何一步失败都不能留下“已激活但无 owner”的节点。claim 未释放前，另一个逻辑节点不得接管该 Worker。

### 6.4 阶段 3：Team ACK saga

多人节点从当前 singleton 或其它已持有的成员关系迁移到目标 collaborative team。TeamPartitionService 在 registry lock 内创建不可变 delivery plan，网络发送在锁外执行；每个目标 Worker 都必须返回 terminal ACK。

- 全部 TEAM_UPDATE ACK：`PartitionTransition=INSTALLED`，节点继续；
- 任一发送/ACK 超时或拒绝：不派发任何 participant task，transition 进入 `COMPENSATING`；
- compensation ACK 全部成功：`COMPENSATED`，节点释放 claim 并返回 `team_setup_failed`；
- compensation 失败/超时：`DEGRADED`，保留 member fence 和 transition journal，返回 `team_setup_failed`，不得继续派发，等待 service/recovery reconcile。

Team ACK 是“网络 saga 已完成”的证据，不是分布式原子事务。日志只记录 worker ID、transition ID、epoch、ACK outcome，不记录 secret。

### 6.5 阶段 4：awaited fan-out acceptance

Team 安装完成后，MissionRuntime 使用预分配的 PhysicalDispatch 构造每个 Worker prompt。prompt 可以包含 team ID、成员 ID、objective、assignment，但不能包含 peer secret、Coordinator secret、签名、原始 endpoint credential 或认证 token。

每个 dispatch 依次经历 `PREPARED -> DISPATCHING -> ACCEPTED`，且必须等待第一份 A2A acceptance 才返回 activation success。多个 participant 的 acceptance 可以并行等待，但不能使用旧的仅创建后台 task 即返回的 `DispatchTaskTool.execute()` 作为 graph activation primitive。

若第 N 个 participant acceptance 失败：

- 已接受集合通过 canonical 状态机进入取消流程；
- 逐项记录 cancel outcome，无法确认的为 `CANCEL_PENDING`；
- logical node 为 failed；
- team release/reconcile 仍由 MissionRuntime finalizer 和 transition fence 完成；
- 不能只返回一个异常就遗留其它 Worker 任务或 collaborative team。

### 6.6 阶段 5/6：物理终态、release 与 reconcile

Worker 的 push 或周期 sync 只更新对应 dispatch。`apply_physical_status()` 首次聚合出 logical terminal 后安排 `release_node_team()`：通常以更大的 global membership epoch 将成员恢复到 singleton。若下一个 ready node 已由同一 Mission 预检并取得完整 claim，可以在同一 transition ownership 下直接迁移，避免不必要的可见双跳。

释放不是“删除状态”：必须先完成或记录 team delivery outcome，再解除 member fence；任何未解决的远端取消或 membership ACK 都必须以 `CANCEL_PENDING` / `DEGRADED` 真实呈现。

## 7. TeamPartition transition、epoch 与 Coordinator recovery

### 7.1 `PartitionTransition` 状态机

**拟新增** `PartitionTransition` 持久记录至少包含：`transition_id`、`context_id`、来源 logical node、before/after membership snapshot、affected worker IDs、member fence/lease、Coordinator-global membership epoch、每成员 delivery ACK、compensation plan、reason、created/updated time 和 terminal outcome。

```text
                         all UPDATE ACK
                 ┌──────────────────────────┐
                 │                          ▼
PREPARING -> INSTALLING ----------------> INSTALLED
                  │  │                       │
       ACK/网络失败│  │ timeout               │ node terminal
                  ▼  │                       ▼
             COMPENSATING ----------------> RELEASE PREPARING
                  │  all compensation ACK       │
                  ▼                             ▼
             COMPENSATED                 INSTALLING(singletons/next team)

INSTALLING or COMPENSATING
          │ compensation/ACK timeout or unrecoverable mismatch
          ▼
       DEGRADED

DEGRADED：保留 fence、before/after snapshot 和 journal；禁止新 claim，
由 service/recovery 以更大 epoch reconcile，直到出现明确 terminal outcome。
```

`DEGRADED` 不是成功，也不是静默回滚。它表示网络世界与 Coordinator 记录尚未一致；必须可观测、可恢复、不可把 Worker 交给另一个 activation。

### 7.2 全局持久 membership epoch

`MessageEnvelope.team_epoch` 的语义改为 Coordinator-global membership generation，而不是每个 team 各自从 1 开始的计数器。原因是 Alice 从 `solo:Alice` 移到 rescue team 再回 singleton 时，Worker 只能用一个单调代数判断旧 TEAM_UPDATE/REVOKE 是否可接受。

**拟新增** run-persisted Coordinator control state 必须原子写入且权限为 `0600`，至少包括：

- Coordinator control secret（或其安全存储引用）；
- 下一 membership epoch；
- 当前 partition 的非 secret topology snapshot；
- active `PartitionTransition` journal、before/after snapshots 和 fence；
- 足以进行启动恢复的 mission/dispatch 标识和 terminal/reconcile 状态。

现有 `WorkerTeamState` 已持久化 `last_generation` 并在 `0600` 文件中保存单 active team：`src/a2a/worker/team_state.py:1-16`、`372-390`、`392-444`。目标实现必须继续保留这种防 replay 语义，但把收到的 epoch 解释为全局 generation；相同 team/epoch/内容可幂等重装，旧 revoke 不能删除更新后的新 membership。

### 7.3 Coordinator restart/recovery

启动恢复顺序必须是：

1. 读取 Coordinator persisted control state 和 transition journal；
2. 分配严格大于已知本地/Worker generation 的新 epoch，绝不能重置为 1；
3. 将此前未完成的 activating/active logical nodes 标记为 abort/reconcile，当前阶段不做隐式 resume；
4. 取消或查询已知 PhysicalDispatch，无法确认的记录为 `CANCEL_PENDING`；
5. 以新的 epoch 为所有 online Worker 重新建立 singleton，或完成明确的 compensation；
6. 解决 `DEGRADED` transition 的 fence/reconcile 后，才释放 admission 并接受新 Mission。

恢复过程必须幂等：重复启动、重复 TEAM_UPDATE、迟到旧 callback、旧 TEAM_REVOKE 都不能把 Worker 恢复到旧队伍，也不能修改新 Mission。

## 8. Parent timeout/cancel/shutdown：`MissionRuntime.abort()` finalizer

**拟新增** `MissionRuntime.abort(reason)` 是唯一 parent-level cleanup primitive。它必须从以下所有入口调用：

- 正常 mission finish（先完成 release/reconcile）；
- `_execute_agentic()` orchestration timeout；
- Router/controller error；
- A2A executor `cancel()`；
- SAR experiment cancel；
- Coordinator shutdown；
- Coordinator startup recovery。

finalizer 的规范顺序：

```text
freeze new activations
  -> mark Mission aborting + stop Router admission
  -> enumerate context-owned PhysicalDispatch only
  -> native-cancel ACCEPTED/RUNNING/INPUT_REQUIRED dispatches
  -> route every outcome through apply_physical_status()
  -> bounded wait for terminal ACKs
  -> unresolved remote work = CANCEL_PENDING
  -> compensate/reconcile TeamPartition at newer epoch
  -> release node/participant claims and transition fences
  -> clear futures, callback mappings, artifact buffers, watchdog/provider attachment
  -> persist final mission/transition outcome
  -> release ActiveMissionAdmission lease
```

finalizer 必须可重入、幂等、有 bounded timeout；二次调用只能补偿尚未完成的步骤。`CANCEL_PENDING` 或 `DEGRADED` 必须保留为事实，不允许为了让父任务显示成功而强制写成 completed。Server 当前 lifespan 只停止 sync/watchdog/A2A（`src/a2a/coordinator/server.py:367-386`），目标要在这些关闭动作之前调用 finalizer；`SARCoordinator.stop()` 的现有 server shutdown 等待（`sar_orch/coordinator.py:528-535`）也必须接入同一 primitive。

## 9. Worker peer mail、`/team-status` 与 Context Memory

### 9.1 Worker peer mail 的 team authorization 边界

peer mail 仍为 Worker 直接连接 Worker，Coordinator 只负责安装/撤销 roster 和授权材料，不作为正常 MAIL relay。当前基础协议、MAIL/TASK/TEAM_UPDATE 的种类与 HMAC 规则见 [`peer_mail.md`](./peer_mail.md)。目标授权判定必须同时满足：

1. envelope 的 recipient 是接收 Worker 本身；
2. `team_id` 与 Worker 当前 active membership 相同；
3. `team_epoch` 与当前 global generation 相同；
4. sender ID 在当前 team roster 内，且不能是 self；
5. HMAC 使用当前 team secret 校验成功；
6. Worker signer 只能发 `MAIL`，不能借 MAIL ingress 发 TASK 或伪造 Coordinator directive；
7. 旧 epoch、非本队成员、错误 secret、self-send 和跨 team mail 必须拒绝。

Worker 的单 active team 状态应继续由 `WorkerTeamState` 提供原子 `delivery_snapshot()`：当前实现 `src/a2a/worker/team_state.py:257-283` 已将 team、epoch、members、endpoint 和 secret 作为同一锁下的 immutable snapshot 返回。目标只扩展 partition 语义，不把 WorkerTeamState 改成多 team map。

多人团队结束后，Alice 给 Bob 的旧 team mail 即使网络上迟到，也必须因 epoch/team mismatch 被拒绝；Alice 给 Charlie 的跨队 mail始终拒绝。MAIL 的送达、读取和失败事件不能驱动 DAG completion。

### 9.2 `/team-status` 认证原则

当前 `src/a2a/coordinator/server.py:871-902` 的端点使用明文 `agent_id` 并从 semantic map 返回所有其它 agent。目标端点必须：

- **拟新增** `CoordinatorServer.set_team_partition_service(service)`，从权威 TeamPartition 查询请求者当前 team；不得从 semantic-map agent 列表重建 membership；
- **拟新增** Worker-authenticated request proof：使用 Coordinator control secret 派生的 timestamped HMAC/token 或已认证 Worker session，proof 绑定请求中的 Worker ID，限制 clock skew 和 replay；
- 拒绝缺失、过期、重复或代表其它 Worker 的 proof；
- singleton team 返回空 peer list，而不是所有其它 Worker；
- 只返回 safe team view，不返回 team secret、Coordinator secret、HMAC、签名、原始 token 或未脱敏 endpoint credential。

认证 proof 只存在于传输层请求，不得注入 Context Memory 或普通日志。

### 9.3 `/team-status` 缓存原则

当前 `SARWorkerStateProvider.fetch_team_status_async()` 在 `sar_orch/worker_state_provider.py:65-89` 只按 `env_step` 缓存。目标 cache key 至少为 `(env_step, team_generation)`，建议同时包含 `team_partition_revision`；同一 SAR step 内发生 team install/revoke 时必须重新请求。失败可以短暂保留 last-known safe view，但必须标记 stale/refresh failure，不能把旧队伍当作当前授权事实。

Worker context 的 version tuple 当前已经包含 `(env_step, mailbox_version, team_generation)`（`sar_orch/worker_state_provider.py:91-114`）；目标要让 provider 的 team-generation 和 endpoint cache 一致，且只用当前 membership 生成 peer list。

### 9.4 Context Memory 渲染边界

Coordinator 与 Worker 必须分开渲染，不把物理 dispatch、全局拓扑和秘密混为一段 prompt。

**Coordinator Context Memory：**

- `### Mission DAG`：按稳定顺序展示 blocked/ready/activating/active/completed/failed 节点、依赖、participants、logical node ID、team ID/epoch、每个 opaque dispatch ID 的 bounded status 和 block/failure reason；
- `### Physical Dispatches`：展示 Worker、dispatch ID、Worker task ID 的脱敏/有界状态和 acceptance/terminal outcome，用于 help/cancel 诊断；
- `### Team Topology`：展示 team ID、member IDs、source logical node、epoch、setup health、transition summary；
- 不把 `### Task Plan & Progress` 继续当逻辑 DAG，它只能保留为兼容的物理任务视图；
- stable sort logical IDs、worker IDs、dispatch IDs，保证同一拓扑的 prompt 与 NDJSON 顺序稳定；
- 内容必须有上限，result/原因只显示 bounded preview。

**Worker Context Memory：**只渲染当前 Worker 可用于行动的 safe fields：`team_id`、`team_epoch`、当前 member IDs、当前 collaborative objective、当前 team peer 的 position/inventory/task status、mailbox unread summary。不能渲染 team secret、Coordinator secret、原始 endpoint credential、HMAC/signature、request proof、未授权 team membership 或 raw signed envelope。

Context Memory 是观察投影，不是状态 authority。Router 不能通过修改 prompt 中的 team 文本获得授权；Worker ingress 和 Coordinator service 必须再次依据当前 partition/epoch 做判定。

### 9.5 观察日志字段

目标 service-layer 事件应记录：

```text
context_id, logical_node_id, transition_id,
team_id, team_epoch, worker_ids, opaque dispatch_ids,
event_name, source, outcome, reason, observed_at
```

推荐事件：`mission_graph_updated`、`mission_node_ready`、`mission_node_activation_started`、`team_partition_transition`、`team_member_ack`、`mission_node_dispatch_started`、`mission_node_terminal`、`team_partition_release`。

**禁止进入观察日志、EventStore event data、Context Memory、异常文本和实验 payload 的字段：** Coordinator secret、team secret、HMAC、签名、request token、原始 signed envelope、peer endpoint credential、认证 proof、mail body/subject（除非另有明确脱敏审计字段）。现有 peer mail 文档也要求事件不含 body、subject、secret、signature；目标设计延续并扩大该约束。

## 10. 核心数据流与状态机图

### 10.1 核心数据流

```text
External A2A request
        │ task_id/context_id/query
        ▼
CoordinatorAgentExecutor
        │ acquire ActiveMissionAdmission
        ▼
MissionRuntime + MissionGraph
        │ Router: update_plan (logical specs only)
        │ framework: DAG gate / claims
        ▼
TeamPartitionService ── signed TEAM_UPDATE ──> WorkerTeamState × N
        │                                      │ ACK / install
        │ all ACK                                     ▼
        ├───────────────────────────────> exclusive TeamPartition
        │
        │ preallocate dsp_<uuid> records
        ▼
awaited fan-out A2A dispatch ────────────> Worker Agent × N
        │ acceptance -> worker_task_id
        │
        ├── push callback ─┐
        ├── periodic sync ─┼──> TaskStore.apply_physical_status()
        ├── cancel result ──┘             │ exact-once terminal guard
        │                                  ▼
        │                         MissionGraph aggregation
        │                                  │ logical terminal
        ▼                                  ▼
release/reconcile TeamPartition <── MissionRuntime.abort/finalizer
        │
        └──> Coordinator/Worker Context Memory + secret-free events
```

### 10.2 逻辑节点激活与回收状态机

```text
                 deps incomplete
          ┌─────────────────────────┐
          ▼                         │
       BLOCKED ── deps success ──> READY
                                     │ activate gate
                                     ▼
                                ACTIVATING
                               │          │
                  team saga fail│          │ team ACK + acceptance
                               ▼          ▼
                             FAILED      ACTIVE
                                           │
                   any dispatch fail/cancel│ all dispatch terminal success
                                           ▼                 ▼
                                        FAILED          COMPLETED
                                           └──────┬──────────┘
                                                  │ release/reconcile
                                                  ▼
                                           claims released
```

### 10.3 物理状态、逻辑聚合和团队状态的分工

| 事件 | 物理层动作 | 逻辑层动作 | TeamPartition 动作 |
|---|---|---|---|
| acceptance | `DISPATCHING -> ACCEPTED` | 节点保持 activating/active | 保持已安装 team |
| Worker running | `ACCEPTED -> RUNNING` | 节点 active | 保持 team |
| input required | `RUNNING -> INPUT_REQUIRED` | active，绑定 help dispatch | 保持 team |
| one terminal failure | 该 dispatch terminal | 节点 failed | finalizer 取消其它已接受 dispatch，随后 release |
| all terminal success | 所有 dispatch terminal | 节点 completed | release 或同 mission 下一节点直接迁移 |
| parent timeout/cancel | nonterminal -> CANCEL_PENDING/CANCELED/FAILED | mission aborting/canceled | compensation/reconcile，不能遗留 lease |
| late/duplicate callback | 忽略或 bounded diagnostic | 不变 | 不变 |

|---|---|---|---|

| TaskStore（拟新增） | `apply_physical_status(dispatch_id, raw_state, source, observed_at, result=None)` | canonical normalize、终态保护、exact-once aggregate | push/sync/cancel/timeout 的唯一入口 |
| MissionRuntime（拟新增） | `activate_plan_node(logical_id)` | DAG gate、claim、team saga、awaited fan-out | 不接受 Router 自带 who/content |
| MissionRuntime（拟新增） | `dispatch_prepared_many(dispatch_ids)` | 并发等待各 participant acceptance | 第一个 acceptance 返回前不得宣称成功 |
| MissionRuntime（拟新增） | `abort(reason)` | 取消、bounded wait、CANCEL_PENDING、team reconcile、清理 owner | 所有 parent termination path 共用且幂等 |
| SendMessageTool（拟新增动作） | `message_type="activate_plan_node"` | `related_task_id=logical_id` | 未知节点、未 ready、participant busy 都返回稳定错误 |
| TeamPartitionRegistry（拟新增） | `ensure_singletons(online_workers)` | 建立 `solo:<worker_id>` | 每个 online Worker 恰好一个 team |
| TeamPartitionRegistry（拟新增） | `prepare_activation(node_id, members, objective)` | 返回 before/after snapshot、epoch、transition/fence、delivery plan | 事务前置；同 Worker transition lease 互斥 |
| TeamPartitionService（拟新增） | `activate_node_team(...)` / `release_node_team(...)` | 送 TEAM_UPDATE/REVOKE，等待 ACK，补偿/降级 | 网络在锁外；状态在 durable transition 中 |
| CoordinatorServer（拟新增） | `set_team_partition_service(service)` | 注入唯一 topology authority | `/team-status`、callback、reconcile 均不得读 module/global team |
| `/team-status`（拟改造） | authenticated status request | 返回当前请求 Worker 的 safe peer view | proof 绑定 worker ID，防 replay/impersonation，singleton 返回空 peers |
| WorkerTeamState（保留并改语义） | `install/revoke/current/delivery_snapshot` | 一个 active team、global epoch、原子发送快照 | 旧 epoch 不得覆盖新 membership；stale revoke 应幂等安全 |
| Context provider（拟改造） | Coordinator/Worker topology projection | DAG、dispatch、team view 分离，stable sort、bounded | 只作观察投影，不作授权 authority |

## 12. 稳定错误码与不变式

### 12.1 错误码

| 错误码 | 触发条件 | 调用方处理 |
|---|---|---|
| `mission_already_active` | 当前阶段已有其它 active agentic Mission | reject 或进入受控队列，不创建/覆盖 TaskStore |
| `undeclared_task` | graph-managed run 中派发未知 logical ID | 先 update_plan，不允许隐式 ad-hoc |
| `node_not_found` | activate 的 logical ID 不存在 | 修正 graph/reference |
| `node_not_ready` | 节点仍 blocked/activating/active/terminal | 读取 DAG 后等待或重规划 |
| `dependency_incomplete` | 依赖未 completed/verified 或依赖失败 | 不派发本节点 |
| `planned_worker_mismatch` | legacy worker_id 与 participant_ids/assignment 不一致 | 修正声明，不能以 `who` 覆盖计划 |
| `participant_busy` | Worker 有 active dispatch、其它 claim 或非终态 transition lease | 等待、取消或选择其它 participant |
| `team_setup_failed` | 任一 TEAM_UPDATE ACK 失败 | 不派发；执行 compensation/reconcile |
| `TEAM_ACK_TIMEOUT` | bounded 时间内未收到 terminal ACK | transition -> COMPENSATING 或 DEGRADED |
| `TEAM_COMPENSATION_FAILED` | compensation 也未完成 | transition -> DEGRADED，保留 fence |
| `dispatch_acceptance_failed` | participant A2A acceptance 未成功 | 取消已接受集合，逻辑节点 failed |
| `unknown_physical_dispatch` | callback/sync 引用不存在或不属于当前 context 的 dispatch | 丢弃或 diagnostic，不得创建记录 |
| `invalid_physical_transition` | raw state 导致终态回退或非法跳转 | 保留 canonical state，记录来源 |
| `CANCEL_PENDING` | 取消请求已发出但远端终态未确认 | finalizer 不得释放相关事实直到 reconcile/fence 策略允许 |
| `stale_membership` | TEAM_UPDATE/REVOKE epoch 不新或不匹配 | Worker 安全拒绝/幂等处理 |
| `unauthorized_team_mail` | 非当前 roster/epoch/secret/recipient 或 Worker 发 TASK | ingress 拒绝并记录安全事件 |
| `team_status_unauthorized` | status proof 缺失、过期、伪造或跨 Worker | HTTP 认证失败，不返回 topology |

### 12.2 不变式

| 编号 | 必须始终成立的事实 | 验证重点 |
|---|---|---|
| I1 | 一个 active agentic Mission admission lease 只归一个 `context_id` | 第二 Mission 不覆盖第一 Mission 状态 |
| I2 | MissionGraph 只包含 logical ID；PhysicalDispatch 只通过 opaque dispatch ID 查询 | ID 碰撞、拼接和跨 namespace 测试 |
| I3 | 每个 online Worker 恰好一个 active team | singleton 建立、多人队伍并存、release 恢复 |
| I4 | 一个 Worker 不能同时被两个 active/transition node claim | 并发 activation 返回 `participant_busy` |
| I5 | Team ACK 全部成功以前，不会发送 participant task | partial ACK 不得出现 Worker task |
| I6 | `apply_physical_status()` 是唯一物理状态权威，终态单调且 exact-once 聚合 | duplicate/out-of-order push、sync、artifact |
| I7 | peer mail 只在当前 team、epoch、roster、secret 下被接受 | 同队成功、跨队和旧 epoch 拒绝 |
| I8 | peer mail 本身永不改变逻辑 node terminal state | MAIL/读取事件不能完成 DAG |
| I9 | parent timeout/cancel/shutdown/recovery 都调用同一个 abort finalizer | 无遗留 Future、claim、transition 或未记录 cancel |
| I10 | epoch 全局持久且 Worker generation 单调 | Coordinator restart 后严格更大，旧 revoke 不生效 |
| I11 | Context Memory 与日志不含 secret、token、签名、原始 credential | 真实 server + log artifact 扫描 |
| I12 | topology、DAG、dispatch 输出稳定排序且 bounded | 相同状态不同插入顺序得到同一渲染 |

## 13. 分期实施路线

| 阶段 | 目标 | 主要产物与门槛 |
|---|---|---|
| Phase 0：生命周期契约 | 先固定 admission、ID、canonical status、restart、abort、transition fencing | **拟新增** lifecycle RED tests；第二 Mission、乱序状态、parent abort、restart epoch 必须先能明确失败 |
| Phase 1：MissionGraph 与双存储 | 将 advisory PlanNode 上移为逻辑图，建立 PhysicalDispatch 分离 API | graph validation、cycle、dependency frontier、participant claim、opaque ID 测试；旧单 Worker facade 保持兼容 |
| Phase 2：显式计划与 Context 投影 | 扩展 update_plan participant/objective/assignments，移除正常路径 advisory 语义 | invalid graph 不创建 dispatch；Coordinator 分开渲染 Mission DAG 与物理任务 |
| Phase 3：exclusive TeamPartition | 建立 singleton 默认队伍、多 team 共存、global epoch、durable transition | [Alice,Bob] 与 [Charlie,David] 可并存；同 Worker 不重叠；ACK/compensation/DEGRADED/restart 测试 |
| Phase 4：activation/runtime | 加入 `activate_plan_node`、Team ACK 前置、awaited fan-out、canonical status aggregation | 依赖 gate、Nth acceptance failure、duplicate callback、late artifact、cancel pending 全通过 |
| Phase 5：Worker auth/context/observability | 分区过滤 `/team-status`、认证 proof、generation cache、safe Context Memory、secret-free events | forged agent ID、same-step transition refresh、cross-team mail、日志泄密检查 |
| Phase 6：生产收口 | 所有 termination path 接入 `MissionRuntime.abort()`，server/SAR wiring、recovery、真实 E2E | focused/full suite、peer-mail smoke、5 scenes × 2 agent counts cross-validation |

实现时不应把 `configure_team`、`disband_team`、`sync_team` 继续作为 graph mode 的正常 Router workflow；它们可以保留为兼容/诊断接口，但不能形成第二个独立 team state authority。`sar_orch/coordinator.py:412-456` 的当前注入点应改为注入 Coordinator-owned partition service，而不是让 Router 自主管理 roster。

## 14. 验证门槛与验收标准

### 14.1 单元与生产 wiring 门槛

必须同时覆盖：

- graph unique IDs、未知依赖、自依赖、环、failed dependency 不解锁；
- active node 不能被 full-plan replacement 静默移除或改 participants；
- logical/physical ID 不能碰撞或跨路由；
- duplicate/out-of-order push、sync、`WORKING` after terminal、late artifact 不回退/重复聚合；
- Nth participant acceptance 失败时只取消已知 accepted set，其余明确为 acceptance failure；
- parent timeout/cancel 在 `DISPATCHING`、`RUNNING`、`INPUT_REQUIRED` 各阶段都走 finalizer；
- partial TEAM_UPDATE ACK、compensation success/failure、DEGRADED 和 member fence；
- Coordinator restart 读取持久 state，使用严格更大 epoch 重建 singleton；
- stale callback from finalized context 不修改新 Mission；
- `/team-status` 真实 CoordinatorServer 中的 singleton、双 collaborative teams、伪造身份和 cache refresh；
- Worker MAIL 同队成功、跨队拒绝、旧 epoch 拒绝、Worker 发 TASK 拒绝；
- secret/token/signature/raw envelope 不出现在 response、Context Memory、EventStore、NDJSON 和实验日志。

测试应通过真实 CoordinatorServer wiring 验证端点和生命周期，不能只复制一个 handler 做孤立测试。

### 14.2 peer-mail smoke acceptance

使用隔离端口和独立 log directory，验收证据必须包括：

- 每个 online Worker 都有 singleton 或当前 collaborative team；
- graph activation 前所有必须的 Team delivery ACK 已完成；
- 没有 `No active team`；
- 没有 `worker_busy`、`task_not_routable_yet`、`unknown_task_id`；
- peer mail 不跨 partition；
- logical node、team transition、opaque dispatch 状态在 Context Memory/event logs 可追踪；
- parent timeout/cancel 后不存在无 owner 的 active team transition；无法确认的远端取消明确记录为 `CANCEL_PENDING`；
- 重启后 Worker `team_state.json` 的 generation 没有回退。

### 14.3 必做 SAR 交叉验证：5 scenes × 2 agent counts

框架改动后必须运行 **5 个场景 × 2 种 agent 数量 = 10 个确定性配置**，统一使用 `seed=42`、`max_steps=20`、peer mail enabled：

```text
scenes:       1, 2, 3, 4, 5
agent counts: 2, 4
seed:         42
max_steps:    20
peer mail:    enabled
```

每次运行保留日志和结果 artifact，并收集：

- `coverage`、`transport_rate`、`end_reason`；
- `worker_busy`、`task_not_routable_yet`、`unknown_task_id`；
- `team_setup_failed`；
- cross-team mail rejection count；
- transition ACK/compensation/DEGRADED、`CANCEL_PENDING` 和 restart recovery 证据（适用时）。

通过标准：

```text
worker_busy = 0
task_not_routable_yet = 0
unknown_task_id = 0
team_setup_failed = 0
cross-team mail rejection 只能出现在预期的安全测试行为中
```

不能仅凭 unit tests 或进程 exit code 宣称成功；必须保存 10 次运行 artifact，并与 baseline 的 coverage/transport rate 对照。

## 15. 完成定义

当且仅当以下事实均成立，才可宣布该策略实现完成：

1. SAR agentic mode 暴露的是经过验证的 MissionGraph，而非 advisory list；
2. 框架而非 prompt 强制 dependency order、participant identity 和 activation gate；
3. 两个不相交 collaborative teams 可以并存，未参与协作的 online Workers 保持 singleton；
4. 每个 Worker 同一时刻只有一个 authoritative active team membership；
5. Team installation ACK 在所有 collaborative participant dispatch 之前；
6. peer mail 只在当前 team 内授权，且不会独立完成 DAG；
7. canonical PhysicalDispatch terminal 状态确定性聚合到 logical node，并正确解锁后继；
8. logical ID、opaque physical dispatch ID、callback/Future、watchdog 和 artifact buffer 都是 context-owned；
9. transition 是有 ACK、fence、before/after snapshot、compensation、DEGRADED 语义的持久 saga；
10. timeout、cancel、shutdown、restart、late callback、partial fan-out 都有生产 wiring 的确定性测试；
11. focused tests、full suite、peer-mail smoke 与 **5 scenes × 2 agent counts** 验证门槛全部通过。
