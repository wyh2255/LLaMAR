# 1 系统架构

## 1.1 问题、目标与设计立场

原始 LLaMAR 面向部分可观测的长时程多机器人任务，采用 *plan–act–correct–verify* 闭环：语言模型据观测提出子任务和动作，再依据环境反馈调整计划【原始 LLaMAR：§1、§4｜`paper/02_多机器人任务规划与分解/LLaMAR_Long-Horizon_Planning_Multi-Agent_Robots_2407.10031.md:L27–108`】。这一路线擅长利用 LLM 的开放式任务理解与分解能力；但在多智能体场景中，若把“谁可以执行、何时可以执行、哪个回调可改变状态、谁能向谁通信”都留给 prompt 解释，则关键协调约束只是模型的软行为，而不是系统可检查的状态条件。

本章所述重构保持 LLM 的决策角色，但将以下**协调责任**下沉至框架：

1. **任务结构约束**：已声明逻辑节点的依赖、参与者与激活资格；
2. **物理执行约束**：一次 A2A 派发的唯一标识、合法状态迁移、重复回调处理和终态聚合；
3. **通信授权约束**：在线 Worker 的 team 归属、成员变更 epoch，以及 peer mail 的授权边界；
4. **环境同步约束**：多 Worker 高层动作按 SAR 回合提交，超时以可观测的 `NoOp` 补齐。

因此，本文不是以一个固定工作流取代 LLM，而是采用“**LLM 声明意图，框架裁决状态转换**”的分工。Router 可以提出节点、依赖、参与者和目标；但不能直接写入节点终态、伪造物理 dispatch，也不能绕过当前的参与者占用或通信授权。

这一定位与近期多智能体研究中的两类问题相呼应：具身 MAS 同时面对部分可观测、异步协作、异构能力与开放环境的协调困难【Feng et al., 2026：§4.1–4.3｜`paper/01_综述_Survey/Multi_Agent_Embodied_AI_Survey.md:L391–481`】；而 LLM-MAS 的系统级差异不仅来自单个 agent 的 prompt，也来自拓扑、调度、共享记忆和低层通信配置【Li et al., 2026：§2.2｜`paper/01_综述_Survey/MAS_Automated_Optimization_Survey_2605.2011.md:L118–162`】。本文的贡献边界是把这些配置中的一部分固定为可审计运行时协议，**不是**自动搜索最优 team topology，也不是自演化 MAS。

## 1.2 架构概览与研究对象

一次 SAR 实验由 `sar_orch/experiment.py:130–528` 创建并清理四类运行时组件：

| 组件 | 当前实现 | 角色 | 不承担的职责 |
|---|---|---|---|
| `SARBarrier` | `sar_orch/barrier.py:74–475` | 收集每个 Worker 的动作并原子执行一个环境回合 | 不做任务分解或 Worker 调度 |
| `SARCoordinator` | `sar_orch/coordinator.py` + `src/a2a/coordinator/` | 承载 Router、任务准入、A2A 服务与协调状态 | 不直接调用 SAR 环境动作 |
| `SARWorker × N` | `sar_orch/worker.py` + `src/a2a/worker/` | 承载 Worker ReAct loop 与 SAR 领域工具 | 不拥有全局 Mission 状态 |
| `ExperimentLogger` | `sar_orch/logger.py` | 落盘轨迹、工具调用、token 与事件证据 | 不裁决系统状态 |

每个 Coordinator 持有一个 Router LLM，每个 Worker 持有一个执行 LLM。Coordinator 通过 A2A 向 Worker 发送任务，Worker 经领域工具向 `SARBarrier` 提交高层动作；环境回合完成后，局部观测和结构化事件再反馈至 Worker 和 Coordinator。实验启动遵循“Coordinator 先绑定、Worker 再注册、确认注册后提交初始任务”的顺序【`sar_orch/experiment.py:265–335`】。这是一条实验运行路径，而不是对跨主机进程部署、容错复制或大规模 swarm 的宣称。

为避免把模块目录误写成抽象层级，系统可按**依赖方向**理解为：

```text
SAR world (SAR/)  ←  环境状态、动作结果与观测
       ▲
SAR orchestration (sar_orch/)  ←  barrier、领域工具、状态投影、实验日志
       ▲
A2A runtime + ReAct agents (src/a2a/, src/Agent/)  ←  通信、生命周期、LLM 工具循环
```

`SAR/` 不包含 LLM 或 A2A 概念；`src/a2a/` 和 `src/Agent/` 不以 SAR 任务为前提；`sar_orch/` 通过组合和工具注入把三者接合。这种依赖反转使“任务协调机制”和“环境动力学”可分别演进，但并不自动证明替换任意环境后仍有相同的任务语义或性能。

## 1.3 三个平面：控制、数据与环境步进

### 1.3.1 控制平面与数据平面

Coordinator–Worker 通信采用两条职责不同的通道：

- **WebSocket 控制平面**：Worker 注册、心跳、取消通知及相关控制交互；
- **A2A HTTP 数据平面**：任务载荷、流式状态、结果与 artifact 的传输。

在当前 Coordinator 服务中，Worker WebSocket 端点为 `/ws/worker/{worker_id}`，A2A 服务经独立端口处理 JSON-RPC；Worker 注册信息还用于 AgentCard/能力发现【`docs/system_docs/系统架构概览.md:L56–58`；`docs/system_docs/框架.md:L72–85`】。二者分离的工程含义是：心跳失联与任务投递失败可以保留不同的恢复与审计语义，避免将“Worker 不在线”和“某次任务未接受”压缩为同一网络错误。

### 1.3.2 环境步进平面

`SARBarrier` 将本来独立到达的 Worker 高层动作合成为一个联合动作。对第 $t$ 个环境回合，令 $a_t^i$ 表示 Worker $i$ 提交的动作；当全部 $N$ 个动作到齐时，barrier 执行：

$$
(o_{t+1}^{1:N}, r_t^{1:N}) = \operatorname{SAREnv.step}(a_t^1,\ldots,a_t^N).
$$

若某 Worker 自首个提交动作起在 `STEP_TIMEOUT=60s` 内未提交，barrier 写入 `NoOp` 并记录其索引，再推进该回合【`sar_orch/barrier.py:141–236`】。该策略提供的是“**一次回合不会因缺失动作永久等待**”的有界等待性质；它不意味着延迟 Worker 的真实意图被正确恢复，也不意味着任务一定完成。

实现采用 `threading.Event` 和 `threading.Lock`，而非跨 Worker 事件循环共享 `asyncio` 原语：Worker 运行在不同线程的独立事件循环，`SARBarrier` 需用线程安全同步机制唤醒等待者【`sar_orch/barrier.py:1–9,112–116`】。每次实际环境步都会快照动作、成功标志、观测、超时 Worker 及指标，以避免固定频率轮询漏记多个已完成回合【`sar_orch/barrier.py:382–475`】。

### 1.3.3 环境抽象的边界

SAR 中 `get_agent_state` 是零步数状态查询，而 `NavigateTo` 在当前 GridEngine 中是直接位置置换，不执行路径搜索。因此该实验路径主要考察高层任务分解、资源协调与通信，而不能把结果扩展解释为连续运动规划或真实机器人避障性能【`docs/system_docs/框架.md:L460–465`】。

## 1.4 三层协调状态：从意图到执行与通信

核心状态不使用一个混合的“任务字典”，而被拆为三类具有不同所有者、标识符和更新规则的对象：

```text
MissionGraph          : 逻辑意图与依赖（what / when）
      │ fan-out
      ▼
PhysicalDispatch      : 面向单 Worker 的执行记录（who / execution state）
      │ authorization context
      ▼
TeamPartition         : 通信成员关系与 epoch（who may communicate）
```

### 1.4.1 MissionGraph：逻辑真相

`MissionGraph` 是一次 agentic Mission 内的纯逻辑 DAG。节点声明 `logical_id`、非空且去重的 `participant_ids`、按 Worker 的 `assignments`、`objective` 与 `depends_on`；图替换前检查重复 ID、未知依赖、自依赖与环【`src/a2a/coordinator/mission_graph.py:41–64,206–247`】。`replace()` 在锁内完成验证和替换，并拒绝修改或移除正在 `activating/active` 的节点语义字段【`mission_graph.py:322–453`】。

逻辑节点的系统维护状态为：

```text
planned ── frontier recomputation ──> blocked / ready
ready ── activation accepted ───────> activating ──> active
active ── all dispatch completed ───> completed
active ── any dispatch fails/cancels -> failed
nonterminal ── abort ───────────────> canceled
```

其中 `completed`、`failed` 和 `canceled` 是不可回退终态【`mission_graph.py:20–34,487–606`】。需注意，`skipped` 是 Router 可声明的豁免状态，而非运行期终态；它在依赖判断中视同满足，但不等价于一次成功的物理执行【`mission_graph.py:643–665`】。

### 1.4.2 PhysicalDispatch：执行真相

逻辑节点可向多个参与者展开为多个 `PhysicalDispatch`。每条 dispatch 具有 opaque 的 `dsp_<uuid>`、逻辑节点 ID、Worker ID、Worker A2A task ID、canonical state、结果/产物缓冲与终态序号【`src/a2a/coordinator/mission_runtime.py:37–121,274–287`】。逻辑 ID、dispatch ID 与 Worker A2A task ID 是三个不同命名空间；查询和回调必须先解析至 dispatch，而不以“尝试多个字典”的方式猜测 ID 类型。

对于参与者集合 $P(v)$，激活节点 $v$ 的物理展开为：

$$
D(v)=\{d_{v,w}\mid w\in P(v)\},\qquad |D(v)|=|P(v)|.
$$

框架先为全部 $d_{v,w}$ 预分配 `PREPARED` 记录，再进行网络 I/O；若本地分配阶段异常，已分配记录回滚【`mission_runtime.py:229–249`】。这避免了“部分记录已创建但系统尚无一致视图”的本地半完成状态；它不把远端 A2A 接受过程伪装为数据库事务。

物理状态机为：

```text
PREPARED → DISPATCHING → ACCEPTED → RUNNING ⇄ INPUT_REQUIRED
     └────────────────────────────→ CANCEL_PENDING → CANCELED / FAILED
ACCEPTED / RUNNING / INPUT_REQUIRED → COMPLETED | FAILED | CANCELED
```

`MissionRuntime` 的 canonical transition 检查拒绝重复、过晚或非法回退，并仅在第一次终态时写入结果和完成 future【`mission_runtime.py:451–532`】。逻辑聚合遵循：全部参与者 `COMPLETED` 才令节点 `completed`；任一 `FAILED/CANCELED` 令节点 `failed`；`INPUT_REQUIRED` 保持逻辑节点 active【`mission_graph.py:543–590`】。因此，peer mail、日志文本或单个 Worker 的口头“完成”均不能单独结束逻辑节点。

### 1.4.3 TeamPartition：通信真相

`TeamPartitionRegistry` 维护在线 Worker 到 team assignment 的映射。默认为 `solo:<worker_id>`，每个在线 Worker 恰有一个 assignment；不同协作 team 可以并存，但成员不可重叠【`src/a2a/coordinator/team_partition_service.py:182–220,279–362`】。成员变更使用 Coordinator 全局单调 `epoch`，而不是每个 team 自己从 1 计数，以便 Worker 拒绝过期的 TEAM_UPDATE/REVOKE【`team_partition_service.py:192–220,272–275`】。

对于多人节点，在已配置实际 delivery adapter 时，框架执行 Team ACK saga：先占用参与者，再安装成员关系，只有全部 ACK 成功后才进入 dispatch acceptance；失败则进入补偿或 `DEGRADED`，而不是静默继续派发【`mission_runtime.py:603–696`；`team_partition_service.py:825–970`】。当 `enable_peer_mail=False`、没有 delivery adapter 时，当前实现**跳过**该 saga，以避免必然超时后形成永久 fence；此时参与者互斥仍由 MissionGraph claim 维持，但不能声称 Worker 已完成可验证的 team 安装【`mission_runtime.py:829`；`team_partition_service.py:779–790`】。

`TeamPartition` 与 `CoordinatorTeamRegistry` 是两套不同机制：前者可表达多个并行分区并服务于 Mission 运行时；后者是 peer-mail 工具集的单一全局 roster。论文中若不作此区分，会把“能否发送 MAIL”的工具配置与“节点激活时的排他成员关系”混为同一状态机【`docs/system_docs/route_strategy.md:L74–108`】。

## 1.5 从声明到回收的端到端协议

下列过程给出 agentic 路径的抽象执行语义；每一步对应明确的状态所有者。

1. **Mission admission**：`MissionRuntimeManager.admit(context_id)` 先取得单一 active mission lease，再创建 TaskStore 和附属状态投影；并发第二 Mission 返回 `mission_already_active`【`src/a2a/coordinator/agent_executor.py:305–354`】。
2. **计划声明**：Router 经 `update_plan` 提交完整逻辑规格；MissionGraph 原子验证并重算 ready frontier。
3. **激活门控**：`activate_plan_node` 先检查节点 ready、依赖已满足、mission 未 abort、参与者未被逻辑 claim 或 team fence 占用。
4. **原子 claim 与预分配**：在 mission 锁内重检竞争条件，将节点置为 `activating`、占用参与者并预分配 dispatch。
5. **team 安装或显式跳过**：有 delivery adapter 时执行 ACK saga；没有 adapter 时记录为跳过，而非虚构 ACK 成功。
6. **等待 fan-out acceptance**：对全部参与者派发 A2A 任务，接受失败时取消已接受集合，并以真实 `CANCEL_PENDING` 或终态记录远端结果。
7. **状态收敛与聚合**：push callback、周期同步、取消及恢复都路由到 canonical physical transition，之后仅由聚合规则更新逻辑节点。
8. **统一终止**：正常完成、超时、取消、关闭和恢复最终经 `MissionRuntime.abort()` 处理；其冻结新激活、有界等待远端取消、reconcile team、清理映射并释放 admission lease【`mission_runtime.py:538–599`】。

上述“统一 abort”是减少遗漏清理分支的实现策略，而非无失败保证：远端取消未被确认时保持 `CANCEL_PENDING`，team 补偿失败时可保持 `DEGRADED`，系统不会为了得到表面上的成功状态而覆写这些事实。

## 1.6 两条编排路径与可比较性

`CoordinatorAgentExecutor` 按 `orchestration_mode` 在 `dag` 与 `agentic` 两条路径间分流【`src/a2a/coordinator/agent_executor.py:266–271`】。两者不应被写成“同一机制的简版与增强版”：它们将不同协调维度下沉到框架。

| 配置 | 计划结构（依赖序、分层 fan-out） | 派发安全与通信授权 | 真实入口 |
|---|---|---|---|
| C0：原始 SAR LLaMAR | prompt / 原有循环 | prompt / 原有循环 | `SAR/baselines/llamar.py` |
| C1：`dag` | 框架：`route_dag()` 及逐层执行 | 不经过 MissionRuntime / TeamPartition | `_execute_dag_loop()` |
| C2：`agentic` | LLM 声明、框架验证 frontier | 框架：admission、dispatch、claim、partition | `_execute_agentic()` |

`_execute_agentic()` 在创建 TaskStore 前取得 runtime lease，并在 finally 中执行 `abort()`【`agent_executor.py:305–450`】；`_execute_dag_loop()` 则独立使用 Router 的 DAG plan 和完成结果字典【`agent_executor.py:452–500`】。因此：

- C1 的核心问题是“框架能否保证给定依赖的执行序”；
- C2 的核心问题是“在 LLM 自主编排时，框架能否阻止重复派发、非法状态回退、越权通信或错误回调污染”；
- “同时下沉两类约束”的 C3 尚不存在，不能把它写为已经评估的配置。

这一区分也限定实验解释：即使 C1 改善了顺序纪律，现有 SAR checker 对多数子任务并不按前置条件评分；即使 C2 的运行时审计无违规，也只是覆盖到的安全机制未报告违规，并不是任务效能或活性的证明。

## 1.7 相关研究的定位：固定协议，而非自动演化

用户指定的自动优化综述将 MAS 表示为由拓扑、角色、分解/调度、共享记忆和通信基础设施共同决定的系统配置；其中 P3 是人工指定的 orchestration，P4/P5 则涉及自动优化或大规模涌现协调【Li et al., 2026：§2.1–2.4｜`MAS_Automated_Optimization_Survey_2605.2011.md:L91–235`】。本系统处于一个更受限的位置：Router 可在 Mission 内声明任务图，但底层状态协议、标识符边界和授权条件由工程师固定，目的在于可追踪性与安全性，而不是每个实例搜索最优组织结构。

这一界限也避免与 TacoMAS、Meta-Team 的贡献混淆。TacoMAS 研究测试时联合更新能力与通信图，且其理论结论依赖有界噪声和有偏编辑等条件【`paper/10_自进化与多智能体协同交叉/2605.09539__tacomas/note.md:L101–185`】；Meta-Team 研究任务后基于分布式经验更新 agent、交互与团队 scaffold【`paper/10_自进化与多智能体协同交叉/2605.29790__meta-team/note.md:L134–176`】。LLaMAR-SAR 当前不做这些 topology/capability 更新；它提供的是未来进行自适应或自进化时仍可依赖的、secret-free 且状态可审计的执行底座。

## 1.8 实现现状、限制与汇报口径

为避免把设计目标写成完成事实，汇报时应保留以下边界：

1. **单 Mission 准入**：当前 Coordinator 同时仅允许一个 active agentic Mission；`ActiveMissionRegistry` 的多 Mission 并发设计未实现【`docs/system_docs/route_strategy.md:L110–123`】。
2. **节点级 team 复用未实现**：协作 team 在节点成功后不会自动释放；`release_node_team()` 当前由 Mission abort 调用。因此同一 Mission 中复用同一批多人协作成员可能被 `participant_busy` 阻塞【`route_strategy.md:L302–308`】。
3. **Team ACK 是条件机制**：只有真实 delivery adapter 接线才有“全员 ACK 后再派发”的协议证据；默认未启用 peer mail 的实验路径跳过该 saga，不能把 I5 的强语义外推至该配置。
4. **环境与物理机器人有鸿沟**：SAR 的动作与导航抽象不包含真实网络延迟、连续动力学、路径规划、碰撞恢复或硬件故障。
5. **当前文稿是架构证据，不是性能结论**：架构代码、单元测试和运行日志可支持“机制存在、约束被检查、特定路径可审计”；性能增益、统计显著性及跨场景泛化必须由第 4 章定义的对齐实验另行支持。
