# 系统架构

> **初稿状态说明**：本章为文档驱动初稿，源自 `docs/system_docs/{框架.md, 系统架构概览.md, route_strategy.md}`。所有 `文件:行号` 引用均指向 `src/` 与 `sar_orch/`；`integration/` 为冻结的旧实现，全文不引用。行号随 commit 漂移，定稿前须按 spec §五-1 逐一复核。

## 1.1 概述

本文的系统是在 LLaMAR 之上的一次重构。原始 LLaMAR 将多智能体协调完全交由 prompt 承担：Planner 在 prompt 内分解任务，Actor 在 prompt 内决定谁做什么，任务间的依赖顺序、派发的互斥性、通信的授权范围均无框架层表达。本重构把其中一部分职责下沉为框架状态机，使之成为系统可保证的性质，而非依赖模型每一步都恰好推理正确。

系统由四个进程内组件构成，全部由 `sar_orch/experiment.py` 的 `run_experiment()` 统一创建并管理生命周期：

| 组件 | 实现文件 | 职责 |
|---|---|---|
| **SARBarrier** | `sar_orch/barrier.py` | 包裹 `SAREnv`，对多智能体做回合同步 |
| **SARCoordinator** | `sar_orch/coordinator.py` | 包裹 `CoordinatorServer`（`src/a2a/coordinator/server.py`）+ SAR 专属工具与 prompt，内核为 `src/Agent/router_agent/` 的 ReAct Agent |
| **SARWorker × N** | `sar_orch/worker.py` | 包裹 A2A Worker Server（`src/a2a/worker/`）+ SAR 领域工具，内核为 `src/Agent/worker_agent/` 的 ReAct Agent |
| **ExperimentLogger** | `sar_orch/logger.py` | 线程安全 CSV / NDJSON 日志 |

一个 Coordinator 持有 1 个 LLM，N 个 Worker 各持有 1 个 LLM。Coordinator 不直接操作环境，只通过 A2A 协议向 Worker 派发任务并收集结果；Worker 通过领域工具作用于 `SAREnv`。

启动顺序为：先起 Coordinator 并绑定端口，等待后依次启动 N 个 Worker（各自经 WebSocket 回连 Coordinator 注册），确认注册完成后提交初始任务描述（默认 "Extinguish all fires and rescue all persons"），随后轮询 barrier 直至完成或超出预算。

## 1.2 分层结构

系统分四层，上层包裹下层，且下层不知晓上层存在：

```
sar_orch/     SAR 领域编排层（场景、工具、日志、实验脚本）
   │
src/a2a/      A2A 协议传输层（Coordinator–Worker 通信基础设施，域无关）
src/Agent/    自建 ReAct Agent 内核（router_agent/ + worker_agent/，域无关）
   │
SAR/          底层网格世界仿真引擎（纯 Python，无 LLM 概念）
```

这一分层的意义在于：`SAR/` 完全不含 LLM 概念，因此环境可被替换而不触动协调逻辑；`src/a2a/` 与 `src/Agent/` 域无关，因此协调机制不绑定搜救domain。

值得说明的一处设计决策是 `router_agent/` 与 `worker_agent/` 存在代码重复。这并非疏漏，而是允许两者独立演化——Worker 需要支持 `NeedInputError`（任务执行中请求补充输入），Router 不需要。

## 1.3 双通道通信

Coordinator 与 Worker 之间使用两条独立通道：

- **WebSocket** — 控制平面。Worker 注册、心跳、状态查询。
- **A2A HTTP** — 数据平面。任务载荷、执行结果、artifact。

拆分的理由是二者的失效语义不同：心跳丢失应触发 Worker 摘除，而任务载荷投递失败应触发重试或补偿，混用一条通道会使两类故障难以区分。

## 1.4 步同步：SARBarrier

`SARBarrier`（`sar_orch/barrier.py:74`）包裹 `SAREnv`，使所有 Worker 的高层动作按回合对齐。实现上使用 `threading.Event` / `Lock` 而非 asyncio 原语——每个 Worker 运行在独立线程的独立事件循环中，asyncio 原语无法跨线程同步。

超时处理：单步等待超过 `STEP_TIMEOUT`（60 秒）时自动以 `NoOp` 补齐该 Worker 的动作，使回合得以推进而非整体挂死。这一策略使超时成为可观测事件（记入 `TimeoutAgents`）而非静默死锁。

另有两处与步数记账相关的决策：`get_agent_state` 不消耗步数，因为它只是零成本的 GPS 查询，若计步会诱使 LLM 为了确认自身位置而浪费预算；`NavigateTo` 是瞬移，`SAR/` 的 GridEngine 直接 `set_position()`，不做路径规划。后者意味着本环境考察的是任务分解与协调，而非运动规划。

## 1.5 三层协调模型

本重构的核心是把协调拆成三个各自单一职责的层，每层有独立的真相来源。

### 1.5.1 MissionGraph — 逻辑真相

`MissionGraph`（`src/a2a/coordinator/mission_graph.py`）保存一次 Mission 的逻辑结构。每个节点由 `MissionNodeSpec` 声明，含 `logical_id`（Mission 内唯一）、`participant_ids`（非空、无重复的 Worker 列表）、`objective` 与按 Worker 划分的 `assignments`、以及 `depends_on`（只能引用本图节点，不得自依赖或成环）。

Router（即 Coordinator 的 LLM）只能声明节点与依赖，**不能覆盖框架维护的执行状态**。`MissionGraph.replace(specs)`（`mission_graph.py:322`）在写锁内完整验证后原子替换，并拒绝对 `activating` / `active` 节点的移除或参与者/依赖/objective 变更（`:330-352`）。

运行态节点状态机：

```
planned → blocked → ready → activating → active → completed
                                            │
                                            ├→ failed
                                            └→ canceled
```

三个终态（completed / failed / canceled）不允许回退。逻辑节点的完成是其全部 `PhysicalDispatch` 聚合的结果——**不是 peer mail 的结果**，这一点在 §2 中形式化为不变式 I8。

### 1.5.2 PhysicalDispatch — 执行真相

`PhysicalDispatch`（`mission_runtime.py:110`）是每个 Worker 的独立物理记录，含 `dispatch_id`（形如 `dsp_<uuid>`）、`logical_node_id`、`worker_id`、`worker_task_id`、canonical physical state、有界的 artifact / result 快照、取消结果与 finalization guard。

关键设计是**先分配后 I/O**：`MissionRuntime.create_dispatches()`（`:229`）一次性把全部物理记录预分配为 `PREPARED`，然后才进行网络 I/O；分配失败则回滚已分配记录（`:246-249`）。这避免了部分分配成功、部分失败导致的状态不一致。

一个逻辑节点的多个参与者各对应一个 dispatch，共同构成该节点的 fan-out。物理查询、取消、watchdog、push callback 与周期性 sync 一律以 `dispatch_id` 为键，不做"两个字典都试一遍"的兼容尝试——逻辑 ID 空间与物理 ID 空间严格不相交（形式化为 I2）。

### 1.5.3 TeamPartition — 通信真相

`TeamPartitionRegistry` / `TeamPartitionService`（`team_partition_service.py:182,756`）是 Coordinator 生命周期级的通信拓扑权威：

- 每个在线 Worker 恰好属于一个 active team（形式化为 I3）
- 默认队伍为 `solo:<worker_id>`（`ensure_singletons()`，`:204`）；singleton 无需多成员 TEAM_UPDATE，但仍是有效的 peer-mail 授权域
- membership epoch 来自 Coordinator 全局单调计数器，确保旧 epoch 的 TEAM_UPDATE / REVOKE 被拒绝（形式化为 I10，防重放）
- 多人临时协作队伍只在某逻辑节点 `activating` / `active` 期间存在，形如 `team:rescue-thomas:<revision>`
- 任一 Worker 不能同时属于两个协作 team，也不能在 `INSTALLING` / `COMPENSATING` / `DEGRADED` 的 transition lease 期间被另一节点 claim（形式化为 I4）

Team ID、密钥、epoch、endpoint roster、transition ID 全部由框架生成；Router 只能声明 participants 与 objective。

**一处必须写明的实现现状**：逻辑节点进入终态后，其成员的 team fence **不会**自动释放，只在整个 Mission `abort()` 时释放。`release_node_team()`（`team_partition_service.py:896`）仅有 `MissionRuntime.abort()` 一个调用者，且 `TransitionStatus.RELEASE_PREPARING`（`:44`）从未被赋值。因此本文的正确表述是"team 隔离在 Mission 生命周期内保持"，节点级释放归入未来工作。

### 1.5.4 三层关系

```
MissionGraph（逻辑真相）
  logical node rescue-thomas
       │ participants=[Alice, Bob], depends_on=[scout-north]
       ▼
PhysicalDispatch（执行真相）
  dsp_7f… → Alice → worker_task_id=…
  dsp_91… → Bob   → worker_task_id=…
       │ 仅做终态聚合
       ▼
TeamPartition（通信真相）
  team:rescue-thomas:r42 = [Alice, Bob]
  solo:Charlie = [Charlie]
```

TeamPartition 是 MissionGraph 的运行时派生拓扑，不产生新的逻辑依赖，也不改变节点结果。PhysicalDispatch 是逻辑节点的物理展开，不拥有新的逻辑目标。

### 1.5.5 两套 team 机制的区分

这里有一处易混淆之处需明确：`TeamPartitionRegistry` 支持多个并发队伍（`[Alice,Bob]` 与 `[Charlie,David]` 可并存），是 Team ACK saga 的权威；而 `enable_peer_mail=True` 时经 `ConfigureTeamTool` / `DisbandTeamTool` / `SyncTeamTool`（`sar_orch/coordinator.py:412-456` 注入）操作的 `CoordinatorTeamRegistry`（`team_registry.py:67`）**只维护一个全局 team**。两者是完全独立的机制，服务不同目的。Router 须先调用 `configure_team` 才能使用 peer mail，该手动步骤尚未自动化。

## 1.6 两条编排路径

Coordinator 的 `orchestration_mode` 有两个取值，对应两条互不重叠的执行路径（`agent_executor.py:268` 分流）：

| 模式 | 入口 | 计划结构由谁保证 | 派发安全与通信授权由谁保证 |
|---|---|---|---|
| `dag` | `_execute_dag_loop`（`:452`–721） | **框架**（`router.route_dag` 计算依赖序与分层扇出） | prompt |
| `agentic` | `_execute_agentic`（`:305`–451） | LLM（迭代决定下一步派发） | **框架**（MissionRuntime 准入、单写者状态机、TeamPartition） |

**这两条路径不是同一条轴上的深浅两档。** 已核实 `_execute_dag_loop` 完全不触碰 MissionGraph / MissionRuntime / TeamPartition——该函数体内无任何 mission 引用，其后唯一的 mission 引用落在 `cancel()`（`:885`–901）内的 `:897`–898。反之 `_execute_agentic` 经 `:322` 的 `admit()` 进入 MissionRuntime，并在 `:450` abort。

因此"协调下沉"实际被分解为两个互相独立的关注点：

- **轴 A — 计划结构**：依赖序与分层扇出。`dag` 由框架保证。
- **轴 B — 派发安全与通信授权**：mission 准入、单写者物理状态机、team 独占分区、epoch 防重放。`agentic` 由框架保证。

两者兼有的配置（框架同时保证 A 与 B）需要把 MissionRuntime 接入 dag 循环，属新增功能，当前不存在。本章的这一区分是第 3 章实验设计的直接依据：两类下沉治的是不同的病，因而应当用不同的指标去看。
