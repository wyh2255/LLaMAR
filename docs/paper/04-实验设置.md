# 实验设置

> **初稿状态说明**：本章为文档驱动初稿，源自 `docs/system_docs/experiment_design.md` §3–5 与原论文 §5 Metrics。本章描述的是**目标实验设置**；当前磁盘上的数据尚不满足该设置，§4.7 如实列出差距。

## 4.1 研究问题

第 1 章 §1.6 将"协调下沉"分解为两个互相独立的关注点。据此，本文的实验回答两个问题：

- **RQ1**：把计划结构（依赖序、分层扇出）从 prompt 下沉到框架，带来什么？
- **RQ2**：把派发安全与通信授权（mission 准入、单写者状态机、team 独占分区、epoch 防重放）从 prompt 下沉到框架，带来什么？

两个问题需要分别回答，因为第 2 章 §2.2 已论证：前者是调度序正确性，后者是状态安全不变式，在形式模型中属不同类型的性质。

## 4.2 三配置对比

| 配置 | 计划结构 | 派发/通信安全 | 代码路径 |
|---|---|---|---|
| **C0** 原版 LLaMAR | prompt | prompt | `SAR/baselines/llamar.py` |
| **C1** `dag` | **框架** | prompt | `_execute_dag_loop`（`agent_executor.py:452`–721） |
| **C2** `agentic` | LLM | **框架** | `_execute_agentic`（`:305`–451） |

C0→C1 隔离 RQ1，C0→C2 隔离 RQ2。第四种配置（框架同时保证两者）需将 MissionRuntime 接入 dag 循环，属新增功能而非补充实验，列为未来工作。

## 4.3 主实验矩阵

沿用原论文的 SAR 评测格网：

- **场景**：scene 1–5
- **智能体数**：2, 3, 4, 5
- **随机种子**：0, 10, 20, 30, 40（5 个固定种子）

即每配置 5 × 4 × 5 = **100 格**，三配置共 300 次运行。该格网与 `SAR/baselines/results/llamar/actions/` 下现存的原版基线结果**完全一致**，故 C0 与 C1/C2 可逐格配对比较。

单格耗时实测约 170–590 秒（均值 5–6 分钟），并发 2 时单轮 100 格约 5–6 小时。

## 4.4 指标体系

### 4.4.1 任务完成

- **Success Rate (SR)** — `finished`，二值
- **Transport Rate (TR)** — 一轮内完成的子任务比例
- **Coverage (C)** — 已覆盖对象比例
- **Steps (L)** — 完成任务所用高层动作数

### 4.4.2 负载均衡（按原论文定义对齐）

原论文 §5 给出精确定义，本文照此实现：

$$B := \frac{\min\{s_1,\cdots,s_n\}}{\max\{s_1,\cdots,s_n\} + \epsilon},\qquad \epsilon = 10^{-4}$$

其中 $s_i$ 为智能体 $i$ 完成的**关键子任务相关**成功高层动作数——注意是子集而非全部动作（原文限定为 "a subset of high-level actions that must be executed to accomplish critical subtasks"）。$B=0$ 表示至少一个智能体无成功动作，$B=1$ 表示完全均衡。

**当前实现的 balance 是错的，必须修**。`sar_orch/aggregate.py:95` 写作 `"balance": 1.0 if finished else transport_rate`——这与负载均衡无关，是 success_rate 与 transport_rate 的复制品。且全 `sar_orch/` 内无任何真实的 balance 或 action_share 计算。

**成功判定的数据来源**（实测，`agent_interactions.csv`，71 个 run 具备）：
- 该文件的 `ErrorType` 列全 9782 行皆空，`EventType` 仅有 `tool_result` / 空 / `query_sar_state` — **两者都不能作成功标志**
- 无独立 `Success` 列；`subtasks.csv` 的 `Status` 实测 100% 为 `"assigned"`、`FailureClass` 全空 — 亦不可用
- **可行路径**：解析 `Observation` 文本中的 `"was successful"` / `"was not success"` 短语。实测可行——样本 run `20260721_201943_s4_s42_a5`（scene 4，5 智能体）得 per-agent 成功数 18 / 19 / 18 / 20 / 21，$B = 18/(21+10^{-4}) \approx 0.857$
- **该路径的局限**：短语仅存在于动作类工具（explore、navigate_to、use_supply、get_supply、carry_person、drop_off_person、clear_inventory、no_op、get_agent_state）；`report_observation` / `finish_task` / `map_agent__*` / 邮箱类工具无 pass/fail 信号
- **交叉校验**：`trajectory.csv`（85 个 run 具备）的 `Successes` 列与该步 `Actions` 列按位对齐（全量 3130 True / 156 False），但为 step 级多智能体联合，非直接 per-agent 标注

采用动作类工具成功数作为主口径——它天然贴近原论文"关键子任务相关动作"的限定——并以 `trajectory.csv` 交叉校验。论文正文须写明成功判定的具体来源与所含工具集合。

### 4.4.3 序相关指标（RQ1 专用）

第 2 章 §2.4 已论证：coverage / transport_rate / finished 均不对子任务顺序设门控，因此**成功率类指标对 C1 不敏感**——乱序但最终蒙对与严格按序执行在这些指标上等价。故为 RQ1 引入：

- 前置未满足导致的动作失败数
- 重复动作数
- 步数（`steps`）

### 4.4.4 框架指标（RQ2 专用）

dispatch 计数、barrier 超时计数、A2A 错误计数、以及第 2 章 §2.3 定义的不变式违规计数。

**C0 结构上不存在这些量**（无框架状态机可违反），故在结果表中标注 N/A，**不填 0**——填 0 会被误读为"零违规"。

### 4.4.5 成本

token 用量（prompt / completion / 总量，区分 cache 命中与未命中）与 `elapsed_seconds`。

## 4.5 统计方法

**置信区间**：复用原论文的实现（`meta/result_analysis/confidence_intervals.py`）。`get_CP_interval`（`:20`）对 SR 用 Clopper-Pearson 区间（SR 为二项指标），`get_mean_std_interval`（`:27`）对连续量用 t 分布区间。二者均为通用 pandas 函数，无 AI2Thor 依赖；唯一不匹配是列名（`get_ci_metrics`（`:44`）要求 `"success rate"` 带空格，而 `aggregate.py:116` 输出 `success_rate` 下划线），写一个改名适配器即可，不必重写数学部分。该文件即原论文产物，故统计口径与原论文天然一致（均值 + 95% CI）。

**配对检验**：三配置跑同一格网，每格构成**配对样本**而非独立样本。因此除各自的置信区间外，报告 per-cell 差值的 Wilcoxon 符号秩检验。在配对设计下这比"看两个独立区间是否重叠"的统计功效高得多。

## 4.6 必须对齐的三项混淆因素

| 因素 | C0 现状 | 新系统现状 | 原论文 |
|---|---|---|---|
| 模型 | `gpt-4-turbo` 硬编码（`llamar_utils_multiagent.py:497`） | 代码默认 `deepseek-v4-flash` | GPT-4V |
| 步数上限 | `env.task_timeout`（`SAR/baselines/llamar.py:95`） | `benchmark.py:223` 默认 50；实测 run 中 20×47 / 30×29 / 50×9 / 其他×6 | $L=30$ |
| balance 口径 | 原论文公式 | 假指标（`aggregate.py:95`） | 原论文公式 |

**模型**：C0 硬编码模型串于 `:497`、端点 `https://api.openai.com/v1/chat/completions` 于 `:577`，均需改为可配置以对齐 C1/C2。注意 `llamar.py:99` 的 `config = Arg(temperature=0.7, model="gpt-4")` 是死代码——payload 自行硬编码模型，改它无效。

**步数上限**：这一项比模型差异更隐蔽。实测 91 个 run 中 `max_steps` 为 20 的占 47 个，而 `max_steps_reached` 是首要失败原因（38 次）——**大量运行是被步数上限掐死的，而非能力不足**。三配置必须统一该上限，建议取原论文的 30。

**balance**：口径已由 §4.4.2 确定，可在跑实验前修完。

### 4.7.3 执行本设置所需的前置修复

以下四项必须在运行实验**之前**完成，否则跑完需重来：

1. 将 `--orchestration-mode` 接至 `sar_orch/experiment.py`（当前 `:278` 硬编码）与 `sar_orch/benchmark.py`——否则 C1 无法产生数据
2. 修 `benchmark.py` 的 `run_dir()`：当前仅按 scene/agents/seed 建目录，C1 与 C2 两轮 sweep 会互相覆盖
3. 修 `aggregate.py:95` 的 balance 假指标（口径见 §4.4.2）
4. run metadata 写入 `git_commit` + `orchestration_mode` + `model` + `max_steps`——否则结果无法绑定代码版本，"该轮跑过 MissionGraph 路径"不可复核
