## 3.1 ContextManager：三层记忆与降级式压缩

长时域任务的核心工程约束是上下文预算。SAR 任务动辄数十个高层决策步，每步都携带局部观测、工具结果与失败反馈，朴素地累积全部历史会在任务中途耗尽 token 预算。`ContextManager`（`src/Agent/router_agent/context.py:45`、`src/Agent/worker_agent/context.py:56`）在每次 LLM 调用前组装一个有界的 memory block。

### 3.1.1 三层结构

```
┌────────────────────────────────────────────┐
│  System Prompt                             │
├────────────────────────────────────────────┤
│  Context Memory（由 ContextManager 组装）   │
│  ┌─ Environment 层 ────────────────────┐   │
│  │   宏观场景信息（fires/persons/agents）│   │
│  ├─ Current State 层 ──────────────────┤   │
│  │   自身状态（position/inventory/step） │   │
│  ├─ Action History 层 ─────────────────┤   │
│  │   最近 N 步操作记录（episode 摘要）   │   │
│  └──────────────────────────────────────┘   │
├────────────────────────────────────────────┤
│  Raw Messages（最近 K 条 assistant/tool）   │
└────────────────────────────────────────────┘
```

三层的划分依据是**信息的时效性衰减速率不同**：Environment 层变化缓慢但始终相关；Current State 层每步都变但只有最新值有意义；Action History 层是历史，其价值随时间衰减但不为零——因此需要摘要而非丢弃。

### 3.1.2 配置

```python
@dataclass
class ContextConfig:
    strategy: str = "hybrid"             # none | summary | hybrid | raw
    state_mode: str = "semantic"         # semantic | oracle
    recent_messages: int = 12            # 保留最近 N 条 assistant/tool 消息
    summary_trigger_ratio: float = 0.8   # token_limit 的 80% 触发 LLM 压缩
    pinned_enabled: bool = True
    episodic_max_items: int = 20
```

四种策略的行为差异：

| 策略 | `observe()` | `prune_history()` | `assemble()` |
|---|---|---|---|
| `none` | 正常执行 | 跳过 | 注入 memory block |
| `summary` | 正常执行 | 正常 prune | 注入 memory block |
| `hybrid` | 正常执行 | 正常 prune | 注入 memory block |
| `raw` | 立即返回 | 跳过 | 透传 system + 原始消息 |

`none` 与 `hybrid` 的区别在于是否剪枝而非是否记录——`none` 下 pinned 与 episodic 仍然更新，只是不删原始消息。`raw` 是完全旁路，用于对照。

### 3.1.3 降级式压缩算法

关键设计是**被剪除的助手消息降级为 episodic 摘要，而非直接丢弃**：

```python
def prune_history(self, messages: list[Message]) -> None:
    if self.config.strategy in ("none", "raw"):
        return
    self._compress_phase1(messages)          # Phase 1：token 阈值压缩

    # 计数剪枝：保留最近 K 条 exec 消息
    recent = self.config.recent_messages
    exec_indices = [i for i, msg in enumerate(messages)
                    if msg.role in ("assistant", "tool") and i > 0]
    if len(exec_indices) <= recent:
        return
    to_remove = set(exec_indices[:-recent])

    # 移除孤儿 tool 消息（其 assistant 已被剪除）
    remaining_exec = [i for i in exec_indices if i not in to_remove]
    found_assistant = False
    for i in remaining_exec:
        if messages[i].role == "assistant":
            found_assistant = True
        elif messages[i].role == "tool" and not found_assistant:
            to_remove.add(i)

    # 降级：被移除的 assistant 消息 → episodic 条目
    for i in sorted(to_remove):
        msg = messages[i]
        if msg.role == "tool":
            continue                         # 已在 observe() 中记录
        if msg.role == "assistant" and msg.content:
            self._episode_counter += 1
            self.episodic.append(_Episode(
                step=self._episode_counter,
                tool_name="assistant",
                summary=f"assistant: {str(msg.content)[:200]}",
            ))

    messages[:] = [m for i, m in enumerate(messages) if i not in to_remove]
    self._prune_episodic()
```

两处细节值得注意。其一是**孤儿 tool 消息的处理**：多数 LLM API 要求 tool 消息必须紧随其对应的 assistant tool-call 之后，若 assistant 被剪而 tool 保留，请求会被拒绝。上述循环显式检测并连带剪除。其二是**摘要长度硬上限 200 字符**，使 episodic 层的总体积可预测（配合 `episodic_max_items=20`，该层上界约 4KB）。

### 3.1.4 组装顺序

```python
def assemble(self, system_prompt, messages):
    if self.config.strategy == "raw":
        return [Message(role="system", content=system_prompt)] + messages[1:]

    result = [Message(role="system", content=system_prompt)]
    result.extend(messages[1:])               # 原始消息在前
    memory_text = self._render_memory_block()
    if memory_text:
        result.append(Message(role="user", content=memory_text))  # memory block 在末尾
    return result
```

memory block 置于**末尾**而非紧随 system prompt，是为了配合 prefix caching：原始消息序列在多轮之间保持稳定前缀，而 memory block 每轮都变。若把变化的部分放在前面，会使整个前缀缓存失效。

### 3.1.5 一处实现边界

`_extract_pinned()` 中针对 `dispatch_task` 与 `collect_results` 两个 `tool_name` 的分支（`context.py:1204-1219`）在当前工具集下是死代码。`agentic` 模式下 LLM 只调用 `send_message` / `query_task_events`，从不产生这两种 `post_tool` 事件，因此 `CoordinatorPinnedState.dispatched_tasks` 与 `worker_results` 字段恒为空，`_render_current_state()` 中的 "Dispatched: N tasks" 一行实际不会出现。本文不将其描述为生效机制。

## 3.2 数据流与事件体系

### 3.2.1 标识符的生命周期

系统内有三个层级的标识符，其作用域不同：

- `context_id` — 一次 Mission 的会话标识，贯穿全程；
- `task_id` — 一次 A2A 任务，Coordinator 与 Worker 各持一个（`worker_task_id`）；
- `dispatch_id` — 形如 `dsp_<uuid>`，物理派发记录的键。

三者构成包含关系：一个 `context_id` 下有多个 `task_id`，一个逻辑节点的 fan-out 对应多个 `dispatch_id`。审计与日志关联依赖这一层级——`CorrelationID` 字段贯通各 CSV/NDJSON。

### 3.2.2 九层事件分类

事件体系按来源分九层，层间有三种关系：**包含**（containment，父事件涵盖子事件）、**派生**（derivation，事件由另一事件计算得出）、**生命周期**（lifecycle，同一实体的状态迁移序列）。这一分类的作用是使"某次失败归因于哪一层"成为可判定的问题，而非靠人工阅读日志推断。

实测的 Coordinator 侧事件分布（样本 run `20260721_201943_s4_s42_a5`）：`tool_start` 137、`tool_result` 136、`llm_response` 91、`task_status` 87、`task_complete` 5、`agentic_start` 1、`meta` 1、`task_start` 1。`tool_result` 事件的 payload 形如 `{"tool_name": "query_workers", "success": true}`，另有 `source` 与 `timestamp` 字段——这构成第 2 章 §2.3 所述不变式审计的采集通道。

### 3.2.3 暂停与恢复

Worker 执行中若需补充输入，抛出 `NeedInputError`，任务转入 `INPUT_REQUIRED` 状态并快照当前上下文；补充输入到达后从快照恢复。这使得"任务中途请求澄清"不必丢弃已完成的工作。

### 3.2.4 Token 记账

token 用量在三家 provider 之间归一化，区分 cache 命中与未命中。这一区分对成本分析是必要的：命中缓存的 prompt token 计价通常显著低于未命中。实测 `token_usage.csv` 中该字段有效。

**一处必须声明的观测缺口**：`LLMLatencyMs` 列存在但实测恒为 0.0（抽查 8 个文件，min = max = 0.0），故任何 LLM 级延迟结论均不可得。相对地，`agent_interactions.csv` 的 `ToolLatencyMs` **是有效的**（实测范围 0.13 ms – 60055 ms），工具级延迟可报。

## 3.3 PeerMail：Worker 间直连通信

### 3.3.1 动机与结构

默认拓扑下所有通信经 Coordinator 中转，这在协作型子任务（如两名 Worker 共同搬运一名伤员，需要就时机达成一致）中引入不必要的往返与 Coordinator 上下文膨胀。PeerMail（`src/a2a/worker/peer_sender.py:89`）允许 Worker 间直连，Coordinator 仅负责安装与吊销 team roster。

### 3.3.2 授权矩阵

信封分四类，鉴权来源不同：

| 信封类型 | 签名密钥 | 语义 |
|---|---|---|
| `MAIL` | team secret | 同队 Worker 间消息 |
| `TASK` | coordinator secret | 任务派发 |
| `TEAM_UPDATE` | coordinator secret | 安装/更新 roster |
| `TEAM_REVOKE` | coordinator secret | 吊销 roster |

以 team secret 签名的 `MAIL` 无法伪造为 `TASK`——后者需要 coordinator secret。这一分离使"Worker 不能自行派发任务给同伴"成为密码学保证而非约定（形式化为 I7）。

### 3.3.3 防重放

上下文刷新由版本三元组触发：`(env_step, mailbox_version, team_generation)`。`team_generation` 来自 Coordinator 全局单调 epoch，`WorkerTeamState._reject_stale()` 拒绝 epoch 不新的 `TEAM_UPDATE` / `TEAM_REVOKE`。这防止了被截获的旧 roster 消息在稍后被重放以恢复已解散的队伍（形式化为 I10）。

另有一处工程细节：endpoint 归一化把 `0.0.0.0` 重写为 `localhost`（经 `urllib.parse`），因为 Worker 绑定的通配地址不能直接作为对端可达地址使用。

### 3.3.4 实现边界与已知局限

**评测范围**：仅 `sar_orch/experiment.py` 支持 `--enable-peer-mail`，`sar_orch/benchmark.py` 未接线（`peer_mail.md:270-271`）。因此本文**不声称该路径已被大规模评测**。实测 91 个 run 的 metadata 中 `enable_peer_mail` 为 True 者仅 9 个。

`peer_mail.md:209-268` 记录的已知局限，本文如实继承：`CancelTask` 未鉴权；secret 以明文存储；secret 经明文 HTTP 传输；无重试逻辑；不支持跨 subject 的任务委派。这些是当前实现的真实边界，不在本文的贡献主张范围内。

## 3.4 沙箱

所有 Agent 工具经 `SandboxedTool`（`src/Agent/sandbox.py:132`）包裹，两种 profile：`off` 与 `workspace`。后者对文件系统与 Bash 施加路径根白名单，并检测 `..` 逃逸与符号链接解析。

明确的非目标：不做网络、内存、子进程或 OS 级隔离。这一机制的目的是防止 Agent 的工具调用意外触及工作区之外的文件，而非抵御恶意代码。
