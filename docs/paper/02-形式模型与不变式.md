# 形式模型与不变式

> **初稿状态说明**：本章为文档驱动初稿。底层形式化直接继承原论文（`2407.10031`）§3；协调层形式化为新写。所有不变式引自 `route_strategy.md:470-510`。

## 2.1 底层：继承的 POMDP

原始 LLaMAR 已给出完整的问题形式化，本文**直接继承**，不重新发明：

$$\langle N,\ \mathcal{I},\ \mathcal{S},\ \{\mathcal{O}_i\},\ \{\mathcal{A}_i\},\ \mathcal{P},\ \mathcal{G},\ T \rangle$$

其中 $N$ 为智能体数量，$\mathcal{I}$ 为高层语言指令集，$s \in \mathcal{S}$ 为联合状态，$o_i \in \mathcal{O}_i$ 为智能体 $i$ 的局部观测（不完整的环境状态信息），联合动作空间 $\mathcal{A} = \mathcal{A}_1 \times \cdots \times \mathcal{A}_N$ 按类别分解为

$$\mathcal{A} = \mathcal{A}_{NAV} \cup \mathcal{A}_{INT} \cup \mathcal{A}_{EXP}$$

即导航、交互与探索三类高层动作；$\mathcal{P}(s' \mid s, a)$ 为联合转移概率；$\mathcal{G} = \{g_1,\cdots,g_k\}$ 为完成指令所需的子任务集；$T$ 为规划视界。

### 与本文 SAR 实现的对应

为使记号可核验，此处给出形式符号到实现的映射：

| 形式符号 | 实现 |
|---|---|
| $\mathcal{A}$ | `Controller.ALL_ACTIONS + ['Explore']`（`SAR/env.py:108`） |
| $\mathcal{G}$ | `Checker.initialize()` 自场景参数确定性生成（`SAR/Scenes/checker.py:27`） |
| $\mathcal{O}_i$ | `generate_obs_text(agent_idx)`（`SAR/env.py:282`）逐 agent 局部观测 |

$\mathcal{G}$ 的生成规则是确定性的：每处火灾生成 `NavigateTo` + `UseSupply` + `EndFire`；每名待救人员生成 `NavigateTo` + `Carry` + `DropOff` + `NavigateTo(Deposit)` + `Spot`；每个必要水库生成 `GetSupply` + `NavigateTo`。

**写作口径**：这一形式化底座不是本文贡献，而是与原工作共享的基座。本文的贡献叠加于其上。

## 2.2 上层：协调层（本文贡献所在）

继承的 POMDP 刻画了"任务是什么"，但**不含"协调职责归谁"的形式表达**——因为在原始 LLaMAR 中协调完全位于 prompt 内部，没有可形式化的对象。这正是本文的形式化空间。

在 $\mathcal{G}$ 之上定义协调层：

$$\langle G_m,\ D,\ \pi \rangle$$

**$G_m = (V, E)$ — MissionGraph。** $V$ 为逻辑节点集合，$E \subseteq V \times V$ 为依赖边（要求无环、无自环、不引用图外节点）。每个节点 $v \in V$ 携带状态

$$\text{state}(v) \in \{\text{BLOCKED},\ \text{READY},\ \text{ACTIVATING},\ \text{ACTIVE},\ \text{COMPLETED},\ \text{FAILED},\ \text{CANCELED}\}$$

其中 COMPLETED / FAILED / CANCELED 为终态，不允许回退。

> **状态取值的权威来源是代码** `mission_graph.py:20-28` 的 `LogicalState`（7 值），`mark_canceled()` 在 `:599`。需注意 `route_strategy.md:436-456` 的状态机图只绘出 6 个状态，CANCELED 未作为独立转移目标出现（图中取消被折叠进 FAILED）。本文形式化以代码为准，并在此说明图与代码的这一差异。

**$D$ — PhysicalDispatch 的 opaque ID 空间**，满足

$$V \cap D = \emptyset$$

即逻辑 ID 空间与物理 ID 空间严格不相交。此条即不变式 I2。逻辑节点到物理记录的映射是一对多的 fan-out：节点 $v$ 的每个参与者对应一个 $d \in D$，$v$ 的终态由其全部 dispatch 的终态聚合而成。

**$\pi: W \to \text{Teams}$ — TeamPartition。** $W$ 为在线 Worker 集合，$\pi$ 将其划分为若干互不相交的通信授权域。I3 即"$\pi$ 是良定义的划分"：每个在线 Worker 恰属一个 team。

### 核心论述

三个配置在**同一形式框架**下的差异，是"哪些约束由系统保证"的差异，而非三个不同的系统：

- 原始 LLaMAR 把 $\mathcal{G} \to$ 执行 的映射整体交给 prompt；
- `dag` 配置把 $\mathcal{G}$ 上的偏序交给 $G_m$ 保证；
- `agentic` 配置把执行安全交给 $D$ 与 $\pi$ 上的不变式保证。

这一形式化使第 1 章 §1.6 的二维区分从经验观察上升为模型层面的必然：$G_m$ 保证的是**调度序正确性**（一个关于执行顺序的性质），$D$ 与 $\pi$ 保证的是**状态安全不变式**（关于任意时刻状态合法性的性质）。两者在形式模型中属不同类型的性质，故不可能落在同一条轴上。

## 2.3 不变式 I1–I12

十二条不变式表述为上述模型上的**安全性质**：

| 编号 | 性质 | 形式模型中的位置 |
|---|---|---|
| I1 | 一个 active agentic Mission admission lease 只归一个 `context_id` | Mission 准入唯一性 |
| I2 | $G_m$ 只含逻辑 ID；$D$ 只经 opaque dispatch ID 查询 | $V \cap D = \emptyset$ |
| I3 | 每个在线 Worker 恰好一个 active team | $\pi$ 是良定义划分 |
| I4 | 一个 Worker 不能同时被两个 active/transition 节点 claim | $\pi$ 的互斥性 |
| I5 | Team ACK 全部成功（或已跳过）前，不发送 participant task | saga 前置条件 |
| I6 | `apply_physical_status()` 是唯一物理状态权威，终态单调且 exact-once 聚合 | $D$ 上的单写者性 |
| I7 | peer mail 只在当前 team、epoch、roster、secret 下被接受 | $\pi$ 的授权语义 |
| I8 | peer mail 本身永不改变逻辑节点终态 | $G_m$ 与通信层解耦 |
| I9 | parent timeout/cancel/shutdown/recovery 都调用同一个 abort finalizer | 终止路径唯一性 |
| I10 | epoch 全局持久且 Worker generation 单调 | 防重放 |
| I11 | Context Memory 与日志不含 secret、token、签名、原始 credential | 信息流约束 |
| I12 | topology、DAG、dispatch 输出稳定排序且有界 | 渲染确定性 |

### 两条必须显式声明的口径

**其一：这是形式化规范，不是形式化验证。** I1–I12 由测试与运行时审计支撑，**没有机器检查的证明**。本文用"we formalize"而非"we prove"——后者会正当地招致 proof 或 model checker 产物的要求，而本文无此产物。

**其二：I1–I12 均为安全性质（不变式），非活性性质。** 本文不给出活性证明（例如"每个 READY 节点最终会被激活"），也不暗示存在此类证明。

### 可测性的三分

十二条性质的可验证方式不同，不可混为一谈：

- **可由现有事件流直接观测**：I1、I2、I4、I5。这类性质的违规会以失败信号形式出现在 Coordinator 的结构化事件日志中。需注意 `route_strategy.md` §10.1 明确写明失败信号"未必是逐字的独立错误码"，其呈现分三类——工具错误字符串、状态枚举值、以及通用 `reject` + `reason`——故须按来源分别解析，不可用单一字符串匹配。
- **需确认埋点后可观测**：I6、I9、I10。I9 的 abort finalizer 有三个调用点（`agent_executor.py:450`、`:897`–898、`mission_runtime.py:1339`）。
- **应归为测试验证，不得声称运行时审计**：I3、I8、I11、I12。这四条是缺失性或结构性性质（例如 I8"peer mail 永不改变节点终态"），跑基准测不出来——**未观察到违规不等于已验证**。本文引用既有测试断言（如 `tests/test_team_partition.py`）作为其证据。I11 可另用一次性静态扫描脚本检查日志产物。

审计只报告**违规计数与观测覆盖度**，不声称正确性证明；未被执行路径触发的性质如实标注为未覆盖。

## 2.4 依赖链：原论文遗留的空白

原论文附录 D.2 明确论述 SAR 环境具有依赖链——"要扑灭一处火灾，需先识别火源、识别火灾类型、获取相应资源、然后使用"。但该依赖链在原论文中**仅作为环境的叙述性质存在，从未被形式化，也从未被任何指标测量**。

本文实现侧的情况与之一致：`SAR/Scenes/base_checker.py:31` 明写"当前环境中所有子任务都是无条件触发的（不依赖于其他任务完成）"，checker 仅检查子任务字符串是否出现于完成列表；coverage、transport_rate、finished 三个指标**均不对子任务完成的先后顺序设门控**。

一处需精确表述的簿记细节：`base_checker.py:91` 的 `give_credit_for_navigate()` 设计意图是"非导航动作成功时追溯为对应 `NavigateTo` 子任务计分"，即一条顺序相关的簿记旁路。但 `:103` 实际写作 `f"NavigateTo({object})"`——`inner` 在 `:101` 解包后被丢弃，插值的是 Python 内建类型，渲染为 `NavigateTo(<class 'object'>)`，**永不匹配任何真实子任务**。故该旁路在当前代码下不生效，顺序无关性的结论成立。本文按"设计存在但因实现缺陷未生效"如实表述。

**由此确立 `dag` 配置的定位**：它不是"改善既有指标"，而是**首次使 SAR 的依赖链成为系统可保证的属性**。$G_m$ 上的 $E$ 显式编码了 $\mathcal{G}$ 元素间的偏序，并由框架而非 prompt 强制执行。

**同时必须诚实标注**：现有指标测不出这一收益。乱序但最终蒙对的执行与严格按序的执行，在 coverage / transport_rate / finished 上完全等价。因此第 4 章为该配置引入序相关指标（前置未满足导致的动作失败数、重复动作数、步数），并明确说明成功率类指标对其不敏感。
