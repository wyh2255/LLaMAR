# 2 形式模型与不变式

## 2.1 建模目的与层次

原始 LLaMAR 已将部分可观测多机器人长时程任务表述为 POMDP，回答了“环境中有哪些 agent、观测、动作、转移与任务目标”这一问题；但它并未显式区分 LLM 产生的计划建议、框架持有的执行状态以及通信授权状态。对于当前重构而言，后者正是需要可审计的对象。

因此，本章采用两层模型：

$$
\underbrace{\langle N,\mathcal I,\mathcal S,\{\mathcal O_i\}_{i=1}^{N},
\{\mathcal A_i\}_{i=1}^{N},\mathcal P,\mathcal G,T\rangle}_{\text{环境与任务层（继承原始 LLaMAR）}}
\quad \oplus \quad
\underbrace{\langle G_m,D,\Pi,\Lambda\rangle}_{\text{协调运行时层（本文实现化）}}.
$$

符号 $\oplus$ 表示协调层附着于环境层的执行过程之上，而非用任务图替换 POMDP 的物理状态。这一区分可避免两类常见误读：其一，MissionGraph 不等同于环境真实状态；其二，框架约束并不替代 LLM 对未知环境、资源状态或策略的推理。

## 2.2 底层：继承的 POMDP 与 SAR 映射

原始工作定义：

$$
\mathcal E = \langle N,\mathcal I,\mathcal S,\{\mathcal O_i\},
\{\mathcal A_i\},\mathcal P,\mathcal G,T\rangle,
$$

其中 $N$ 是 agent 数量，$\mathcal I$ 为高层语言指令，$s_t\in\mathcal S$ 为联合环境状态，$o_t^i\in\mathcal O_i$ 为 agent $i$ 的局部观测，$\mathcal P(s_{t+1}\mid s_t,a_t)$ 为联合转移，$\mathcal G$ 是目标所需子任务集合，$T$ 为规划视界。联合高层动作空间写为：

$$
\mathcal A=\mathcal A_{NAV}\cup\mathcal A_{INT}\cup\mathcal A_{EXP}.
$$

原始论文明确将该模型用于部分可观测多机器人任务，并说明了高层导航、交互与探索动作各自的角色【Nayak et al.：§3｜`paper/02_多机器人任务规划与分解/LLaMAR_Long-Horizon_Planning_Multi-Agent_Robots_2407.10031.md:L73–77`】。在当前 SAR 实现中，记号与代码的对应关系为：

| 形式对象 | 当前 SAR 实现 | 解释与边界 |
|---|---|---|
| $\mathcal O_i$ | `SAREnv.generate_obs_text(agent_idx)`，由 barrier 每回合写回 | 每个 Worker 接收局部文本观测；Coordinator 的 semantic state projection 是额外框架视图，不等于 $o_i$ |
| $\mathcal A$ | `Controller.ALL_ACTIONS + ['Explore']` | 高层动作经领域工具提交；零成本查询/汇报工具不等同于环境动作 |
| $\mathcal G$ | `Checker.initialize(params)` 生成的 checker 子任务集 | 每火灾、人员和必要水库产生可计分条目【`SAR/Scenes/checker.py:27–121`】 |
| $\mathcal P$ | `SARBarrier` 聚合联合动作后调用 `SAREnv.step()` | 当前实现以确定性仿真执行一次回合；形式上的概率核保留原论文一般性 |
| $T$ | `run_experiment(..., max_steps=...)` 的步数预算 | 默认取场景 `task_timeout`；论文实验是否采用统一预算，须在实验章节单独冻结 |

原始 POMDP 是本文的共享基座，不应被表述为新贡献。本文的新增内容是：在一个环境回合前后，如何限制**逻辑节点、物理派发和通信成员关系**的合法转换。

### 2.2.1 LLM 决策函数：从动态上下文到工具调用

POMDP 中的策略通常写为 $a_t^i\sim\pi_i(\cdot\mid o_t^i)$。对当前 LLM Agent 而言，这一写法过于简化：模型并非只读取一次局部观测，而是同时接收固定权重、system prompt、工具契约、原始消息历史、ContextManager 生成的 Context Memory，以及由语义地图等状态源投影出的运行时状态。为保持“模型输入”与“框架状态权威”之间的边界，令第 $k$ 次 LLM 调用中 agent $i$ 的决策表示为：

$$
y_{i,k}\sim p_{\theta_i}\!\left(
    \cdot\ \middle|
    \operatorname{Assemble}\bigl(\bar p_i, H_{i,k}, C_{i,k}\bigr),
    \mathcal T_{i,k};\ \eta_i
\right),
\tag{1}
$$

其中 $y_{i,k}$ 为模型输出（自然语言、tool call 或二者兼有），$\theta_i$ 为该 agent 本轮运行所使用的冻结模型权重/模型版本，$\eta_i$ 表示解码配置（如 temperature、token 上限和 provider 参数），$\mathcal T_{i,k}$ 是当前注册且对 LLM 可见的工具集合。`Agent.run()` 将组装后的 `messages` 和 `tool_list` 同时传给 `LLM.generate()`【`src/Agent/router_agent/agent.py:506–522`】；工具集合由 builtin、custom 和 runtime `extra_tools` 合并而成，其描述会附加到 system prompt【`src/Agent/router_agent/build.py:120–194`】。

这里 $\bar p_i$ 并非裸 prompt，而是已与工具描述、可选 skill 元数据合并后的有效 system prompt；$H_{i,k}$ 是当前原始消息历史；$C_{i,k}$ 是 ContextManager 生成的动态 memory block。实际组装顺序为"system prompt → 原始消息 → memory block"，其中 memory block 作为最后一条 user message 附加，以保留稳定前缀并兼顾缓存效率【`src/Agent/router_agent/context.py:629–649`】。

为展开 $C_{i,k}$，定义：

$$
C_{i,k}=
\operatorname{Render}\left(
    Z_{i,k}^{\mathrm{pin}},
    Z_{i,k}^{\mathrm{hist}},
    R_{i,k},
    \Omega_i
\right),
\tag{2}
$$

其中：

| 变量 | 实现对应 | 决策作用与边界 |
|---|---|---|
| $Z_{i,k}^{\mathrm{pin}}$ | typed pinned state / `pinned` | 结构化的当前位置、库存、任务状态、步数预算、已知对象等；由工具结果和运行时状态投影更新 |
| $Z_{i,k}^{\mathrm{hist}}$ | 原始 assistant/tool messages 与压缩/episodic 历史 | 保留最近交互及必要的历史摘要；其长度受 ContextConfig 与 token 预算约束 |
| $R_{i,k}$ | `StateProvider.snapshot()` 的 `RuntimeState` | 框架在每次调用前读取的动态运行时投影，而非模型自身推断出的真相 |
| $\Omega_i$ | ContextConfig、输出格式及 agent 角色配置 | 控制 `semantic/oracle` 模式、recent window、pinned state 和渲染格式 |

在默认 `semantic` 模式下，Coordinator 的 $R_{i,k}$ 进一步包含由语义地图构造的环境记忆：

$$
R_{\mathrm{coord},k}^{\mathrm{semantic}}
=\Phi\!\left(
    M_k^{\mathrm{map}},\Delta M_k,\bar M_k,
    G_{m,k},D_k,\Pi_k,B_k,Q_k
\right),
\tag{3}
$$

其中 $M_k^{\mathrm{map}}$ 是 `SemanticMapStore` 合并的、来自 Worker 上报观测的环境共识；$\Delta M_k$ 与 $\bar M_k$ 分别是地图差分和可选增量摘要；$G_m,D,\Pi$ 是本章定义的任务图、物理派发与通信分区；$B_k$ 为步数预算，$Q_k$ 为任务/监督状态。`SARCoordinatorStateProvider` 在 semantic 模式下将这些字段投影进 `RuntimeState.payload`，随后由 ContextManager 写入 pinned state 并渲染为 Context Memory【`sar_orch/coordinator_state_provider.py:186–294`；`src/Agent/router_agent/context.py:187–225,726–750`】。因此，**map memory 并非独立绕过 ContextManager 直接喂给模型的通道**，而是沿 `SemanticMapStore → StateProvider → ContextManager → memory block` 这一受控数据流传递。

模型输出通过受工具契约限制的解码函数映射为可执行决策：

$$
d_{i,k}=\operatorname{Decode}_{\mathcal T_{i,k}}(y_{i,k})
=
\begin{cases}
(\tau,\mathrm{args}), & \text{若 } y_{i,k}\text{ 含合法工具调用 }\tau\in\mathcal T_{i,k},\\
\texttt{final\_text}, & \text{若无工具调用且满足结束条件},\\
\texttt{invalid}, & \text{若输出不能通过协议/工具解析}.
\end{cases}
\tag{4}
$$

当 $d_{i,k}=(\tau,\mathrm{args})$ 时，框架执行工具、获得结果 $e_{i,k}$，并更新消息历史、pinned state、语义地图或协调运行时状态；下一轮再形成 $C_{i,k+1}$。因此，完整闭环可简写为：

$$
(H_{i,k},Z_{i,k}^{\mathrm{pin}},R_{i,k})
\xrightarrow{\ p_{\theta_i},\mathcal T_{i,k}\ }
d_{i,k}
\xrightarrow{\ \operatorname{Exec}\ }
e_{i,k}
\xrightarrow{\ \operatorname{Update}\ }
(H_{i,k+1},Z_{i,k+1}^{\mathrm{pin}},R_{i,k+1}).
\tag{5}
$$

该式刻画的是**推理时上下文与工具反馈的闭环**，而非参数学习过程：在一次实验内，ContextManager、工具结果和 map memory 改变的是 $H/Z/R$，不改变 $\theta_i$。若未来引入 fine-tuning、RL 或自进化 scaffold 更新，才需要额外定义 $\theta_{i,k+1}$ 或 prompt/topology 的跨任务更新方程；当前实现不应被表述为更新模型权重的自进化系统。

## 2.3 协调运行时状态

令 $W_t$ 为时刻 $t$ 在线 Worker 集合。协调运行时记为：

$$
\mathcal R_t=\langle G_{m,t},D_t,\Pi_t,\Lambda_t\rangle.
$$

其中 $G_{m,t}$ 是逻辑 Mission 图，$D_t$ 是物理 dispatch 记录，$\Pi_t$ 是 team assignment，$\Lambda_t$ 是 mission admission lease。环境状态 $s_t$ 与协调状态 $\mathcal R_t$ 通过任务执行、回调与终止过程相互作用，但二者的真相来源不同。

### 2.3.1 逻辑图 $G_m$

定义逻辑 MissionGraph：

$$
G_m=(V,E,\nu), \qquad E\subseteq V\times V,
$$

其中 $V$ 为逻辑节点集合，$E$ 为依赖边，$\nu(v)$ 包含节点的参与者、目标、分配和运行态。对任一节点 $v$：

$$
\nu(v)=\langle id(v),P(v),q(v),A(v),pred(v),\ell(v),\sigma(v)\rangle,
$$

其中 $P(v)\subseteq W_t$ 是非空且无重复的参与者集合，$q(v)$ 是 objective，$A(v)$ 是按 Worker 的 assignment，$pred(v)$ 是前驱集合，$\ell(v)\in\{\texttt{pending},\texttt{skipped}\}$ 是声明态，$\sigma(v)$ 是框架持有的运行态。当前实现要求 ID 唯一、依赖指向图内节点、无自环且无环【`src/a2a/coordinator/mission_graph.py:206–247`】。

运行态集合为：

$$
\Sigma_L=\{\texttt{planned},\texttt{blocked},\texttt{ready},\texttt{activating},
\texttt{active},\texttt{completed},\texttt{failed},\texttt{canceled}\}.
$$

`completed/failed/canceled` 是终态。依赖 frontier 定义如下：

$$
\operatorname{ready}(v) \iff \ell(v)\neq\texttt{skipped}\ \land\
\bigl(pred(v)=\varnothing\ \lor\ \forall u\in pred(v),\operatorname{succ}(u)\bigr),
$$

其中 $\operatorname{succ}(u)$ 在当前实现中表示 $u$ 已 `completed` 或其声明态为 `skipped`【`mission_graph.py:643–665`】。因此，`failed` 与 `canceled` 前驱不会放行后继；这是一条显式的失败传播语义，而非由 LLM 自行解释依赖文本。

### 2.3.2 物理记录 $D$

每个逻辑节点为每个参与者展开一条物理 dispatch：

$$
D(v)=\{d_{v,w}\mid w\in P(v)\},\qquad D=\bigcup_{v\in V}D(v).
$$

每个 $d\in D$ 的核心字段为：

$$
d=\langle id_d, id_v,w,id_{task},\sigma_D,artifact,result,seq\rangle,
$$

其中 $id_d=\texttt{dsp\_uuid}$ 是框架生成的 opaque ID，$id_v$ 是逻辑节点 ID，$id_{task}$ 为 Worker A2A task ID，$seq$ 是终态写入序号。定义逻辑与物理 ID 空间：

$$
V_{id}\cap D_{id}=\varnothing.
$$

这并非概率意义上的 UUID 碰撞分析，而是 API 语义约束：逻辑图 API 只解释 logical ID，dispatch 查询只解释 `dispatch_id`，不会以另一个 namespace 作为回退【`mission_runtime.py:220–287,311–317`】。

物理状态集合为：

$$
\Sigma_D=\{P,Di,A,R,I,C_p,C,F,X\},
$$

分别对应 `PREPARED`、`DISPATCHING`、`ACCEPTED`、`RUNNING`、`INPUT_REQUIRED`、`CANCEL_PENDING`、`COMPLETED`、`FAILED`、`CANCELED`。允许边由 `_ALLOWED_TRANSITIONS` 显式限定，终态 $\{C,F,X\}$ 没有出边【`mission_runtime.py:37–106`】。对一条状态更新 $u=(id_d,s,source,t)$，只有当 $s$ 是当前状态的允许后继时才改变 $\sigma_D$；重复、未知或过晚的状态只产生 diagnostic，不能回写新的终态【`mission_runtime.py:451–532`】。

逻辑聚合定义为：

$$
\sigma(v)=
\begin{cases}
\texttt{failed}, & \exists d\in D(v):\sigma_D(d)\in\{F,X\},\\
\texttt{completed}, & \forall d\in D(v):\sigma_D(d)=C,\\
\texttt{active}, & \text{其他非终态情形}.
\end{cases}
$$

该聚合只接受 canonical 物理终态；一封 MAIL、一次 artifact 更新或单个 Worker 的自然语言结果，都不构成逻辑完成的依据【`mission_graph.py:543–590`】。

### 2.3.3 Team assignment $\Pi$

令 $\mathcal T_t$ 为活动 team 集合，定义：

$$
\Pi_t:W_t\rightarrow \mathcal T_t.
$$

对 $w\in W_t$，$\Pi_t(w)$ 包含 `team_id`、全局单调 `epoch`、成员列表和可选 Mission/node 上下文。当前 registry 为新上线 Worker 建立 singleton $\texttt{solo:}w$；多人协作 team 以 `team:<node>:r<epoch>` 形式产生【`src/a2a/coordinator/team_partition_service.py:59–78,204–220,286–362`】。

注意 $\Pi_t$ 表达的是**通信授权拓扑**，不是环境中机器人空间位置，也不是任务依赖图。peer mail 的接收需同时满足 recipient、team ID、epoch、roster、secret 等条件；而 Router 声明任务的权力仍在 Coordinator。故通信可达性既不自动完成任务，也不自动产生新的依赖边。

### 2.3.4 Admission lease $\Lambda$

当前 agentic Coordinator 只允许一个 active context：

$$
\Lambda_t\in\{\bot\}\cup\{context\_id\},\qquad |\Lambda_t|\le1.
$$

在 `_execute_agentic()` 中，`admit(context_id)` 是第一个可变 Mission 操作；只有持有 lease 的 context 才可拥有对应 runtime【`src/a2a/coordinator/agent_executor.py:317–354`】。这是一种以并发能力换取状态隔离的安全选择，不是多 Mission 调度算法。

## 2.4 协调转换系统

可将当前 agentic 路径抽象为标签转换系统：

$$
\mathcal R_t\xrightarrow{\alpha}\mathcal R_{t+1},\qquad
\alpha\in\{\mathrm{Admit},\mathrm{ReplacePlan},\mathrm{Activate},
\mathrm{Status},\mathrm{Abort},\mathrm{Recover}\}.
$$

关键转换及其前置条件如下：

| 转换 | 主要前置条件 | 原子/权威更新 | 失败时的真实状态 |
|---|---|---|---|
| `Admit(c)` | $\Lambda=\bot$ | $\Lambda\leftarrow c$ | `mission_already_active`，不覆盖既有 Mission |
| `ReplacePlan(S)` | 规格无重复、无环；active 节点语义不变 | `MissionGraph.replace(S)` | 拒绝整次替换，旧图保持 |
| `Activate(v)` | $v$ ready；$P(v)$ 未被 claim/fence 占用 | claim + `PREPARED` dispatch；随后 team saga/acceptance | `participant_busy`、team/acceptance 失败；不把半完成写为成功 |
| `Status(d,s)` | $s$ 是当前物理状态合法后继 | `apply_physical_status` 与一次终态聚合 | diagnostic，不回退终态 |
| `Abort(r)` | runtime 存在 | 冻结激活、取消/标记未确认 dispatch、reconcile team、释放 lease | 保留 `CANCEL_PENDING/DEGRADED`，不伪造完成 |

`Activate(v)` 的关键在于“先检查、再在锁内重检并 claim、再做网络 I/O”：无锁预检只用于快速失败，竞争结果必须以原子 claim 为准。这样两个并发激活即使都观察到 ready，也只有一个可成功取得同一 Worker【`src/a2a/coordinator/mission_runtime.py:603–696,698–732,734–860`】。

若配置了 delivery adapter，多人节点要先经历 Team ACK saga；若未配置，该 saga 被显式跳过，而非生成虚假的 ACK。因而“所有 ACK 后才发 participant task”必须被理解为**saga 启用配置下**的安全条件；默认未接线 peer mail 的运行不提供该项网络安装证据【`mission_runtime.py:829`；`team_partition_service.py:779–790`】。

## 2.5 安全不变式 I1–I12

下表把文档中的十二项要求重新绑定到上述状态对象。全部是**安全性质**：它们限制“不会发生什么非法状态/转换”，并不保证“最终一定发生什么”。

| 编号 | 形式化表述（简写） | 当前机制 / 主要证据 | 验证类型 |
|---|---|---|---|
| I1 | $|\Lambda_t|\le1$ | `MissionRuntimeManager.admit()` | 单元/并发测试 + 事件审计 |
| I2 | $V_{id}\cap D_{id}=\varnothing$；逻辑/物理 API 不跨解析 | MissionGraph 与 dispatch API 分离 | 单元测试 + 代码审查 |
| I3 | $\forall w\in W_t,\exists!\tau:\Pi_t(w)=\tau$ | singleton 初始化与 partition registry | 结构测试 |
| I4 | 活动节点或非终态 transition 不共享 Worker：$P(v)\cap P(u)=\varnothing$ | graph claim + partition fence | 并发激活测试 / 事件审计 |
| I5 | saga 启用时，participant task 的派发蕴含 team ACK 已成功：$dispatch(v)\Rightarrow ack(v)$ | Team ACK saga 后再 fan-out | 配置化路径测试；默认 skip 不适用 |
| I6 | 物理状态仅经 canonical transition 改变，终态单调；绑定 TaskStore status owner 时聚合 exact-once | `TaskStore.apply_physical_status()` + `_aggregated_terminal_dispatches` | 乱序/重复回调测试 |
| I7 | MAIL 被接受蕴含当前 team、epoch、roster、secret、时间窗口与未重复消费均满足 | Worker ingress / team state | 协议测试 |
| I8 | MAIL 事件不改变 $\sigma(v)$ 的逻辑终态 | 终态只由 dispatch 聚合触发 | 缺失性测试 |
| I9 | 父级 timeout/cancel/shutdown/recovery 走同一 `abort()` 终止原语；远端取消仅有界等待 | runtime finalizer 调用点 | 生命周期测试 + 代码审查 |
| I10 | membership epoch 单调且恢复后不回退 | registry global epoch、Worker generation | 恢复/重放测试 |
| I11 | Context Memory、日志、事件投影不含 secret/token/signature/raw credential | safe view 与脱敏投影约束 | 负向扫描/测试 |
| I12 | topology、DAG、dispatch 投影稳定排序且有界 | snapshot/render contract | 确定性输出测试 |

### 2.5.1 I1：单 Mission 准入

I1 约束的是 Coordinator 内 agentic Mission 的所有权，不是“系统只允许一个用户”或“每个 Worker 只接一个任务”。它防止第二个 context 覆盖第一个 context 的 MissionGraph、dispatch map、回调映射和 runtime state。若未来实现多 Mission 并发，必须把这些附属状态都按 `context_id` 隔离；不能仅移除 admission check【`docs/system_docs/route_strategy.md:L110–148`】。

### 2.5.2 I2、I6：标识符分离与单写者状态机

I2 防止将 `logical_id`、`dispatch_id`、`worker_task_id` 互相当作同一种键。I6 则防止多个回调入口各自维护不同生命周期：push callback、周期同步、取消和恢复必须收敛到 canonical 物理状态机。需要保留一个实现前提：`MissionRuntime.apply_physical_status()` 在绑定 `_status_owner` 时委派给 `TaskStore.apply_physical_status()`；后者在同一锁内以 `_aggregated_terminal_dispatches` 对首次终态做 exact-once 聚合【`src/a2a/coordinator/task_store.py:406–473`】。未绑定 TaskStore 时，runtime fallback 仍保证物理状态迁移合法与单调，但不单独提供该逻辑聚合的 exact-once 守卫【`mission_runtime.py:451–532`】。两者共同的作用是避免迟到回调或字符串碰撞污染新任务；它们不保证远端 Worker 在网络故障中已真正停止。

### 2.5.3 I3–I5、I7、I10：分区、授权与重放边界

I3/I4 将“一个 Worker 同时属于多个协作 team”或“同一 Worker 被两个节点并发占用”视为非法。I5 约束 Team ACK saga 的派发顺序；I7/I10 将消息可接受性绑定到当前成员关系和单调 epoch，而不是仅靠 agent 名称判断。I7 还要求 envelope 时间戳处于 `max_skew_seconds` 窗口，且只在认证和授权均通过后消费 `message_id`，以提供有界幂等去重；它不是单纯的 roster 检查。这里要特别避免过度宣称：

- team partition 有真实 delivery adapter 时，才实际完成 Worker 侧 roster 安装与 ACK；
- peer-mail 的当前实现仍存在文档已记录的传输、取消鉴权、重试等工程限制，故不应被称为完整生产级安全协议；
- epoch 防重放只针对该成员关系协议，不等同于端到端网络安全证明。

I9 的统一 finalizer 也不是瞬时原子操作：`abort()` 对远端取消最多等待 30 秒；等待结束仍未终态的 dispatch 保持或转为 `CANCEL_PENDING`，而非被伪装成 `CANCELED`，随后 team release 使用独立的有界 ACK 等待【`src/a2a/coordinator/mission_runtime.py:538–599`】。因此 Coordinator 的终止视图可以先于远端实际停止；该状态差异应在日志和讨论中保留，而不应被归零。

### 2.5.4 I8、I11、I12：非干扰与可审计输出

I8 是状态非干扰性质：通信内容可以影响 Worker 后续决策，但不能直接把 logical node 标为完成。I11 是信息流边界：运行时渲染应投影必要状态而不投影 secret、签名或凭据。I12 是工程确定性要求：同一状态快照应产生稳定、有界的可读输出，避免插入顺序导致 prompt 或审计记录随机变化。三者多为“未发生”的性质，单次 benchmark 未观察到违规不足以验证；应由针对性测试、静态扫描和字段审计支撑。

## 2.6 安全、活性与证据强度

### 2.6.1 本文不证明的内容

本章使用 *formalize/specify*，不使用 *prove/guarantee*。原因是当前仓库提供的是运行时检查、单元测试和结构化日志，而没有 TLA+/Ivy/Coq 等模型检查或机器证明产物。特别地，本文**不证明**：

1. 每个 `ready` 节点最终会被激活；
2. 每条已发送任务最终被 Worker 接受或完成；
3. 网络分区后所有 team 都能恢复一致；
4. LLM 的计划一定正确、完整或最优；
5. 当前安全不变式蕴含 SAR 任务成功。

前四项是典型活性、可靠性或智能性主张，而 I1–I12 的大多数是安全约束。一个系统可以始终不违反 I1–I12，却因 LLM 过早结束、环境预算耗尽或缺乏可用 Worker 而不完成任务。

### 2.6.2 可测性的分层

| 证据层 | 可支持的结论 | 示例 |
|---|---|---|
| 代码结构与单元测试 | 某 API 拒绝/允许特定状态转换 | ID 分离、epoch 单调、secret-free safe view |
| 运行时事件审计 | 已执行路径上是否出现可观测违规、覆盖到哪些分支 | `participant_busy`、acceptance error、状态拒绝 |
| 端到端实验 | 在对齐设置下，机制与任务/成本指标是否相关 | C0/C1/C2 的比较 |
| 形式验证 | 所有模型化状态均满足性质 | **当前未提供** |

据此，论文应报告“违规计数、触发覆盖度、未覆盖性质”，而不是把“零日志错误”写成“已证明正确”。对于 C0 这类没有对应状态机的配置，框架违规指标应标记为 N/A，不能填 0。

## 2.7 SAR 依赖链与评测鸿沟

原始 LLaMAR 的 SAR 叙述包含资源获取、灭火和协作搬运等依赖链【原始论文：附录 D.2｜`LLaMAR_Long-Horizon_Planning_Multi-Agent_Robots_2407.10031.md:L129–142`】。但当前 SAR checker 的基类明确说明“所有子任务都是无条件触发的”，其完成度主要检查动作字符串是否成功出现【`SAR/Scenes/base_checker.py:25–54,141–153`】。因此，任务语义中的“先获取资源再使用”与指标层的“最终哪些条目出现”并不完全一致。

尤其是 `give_credit_for_navigate()` 意图在非导航动作成功时回溯 `NavigateTo` 计分，但当前代码将 Python 内建 `object` 插入 f-string，生成的 `NavigateTo(<class 'object'>)` 不会匹配真实条目【`base_checker.py:91–104`】。严谨表述应为：当前 checker 设计上有一个顺序相关的簿记旁路，但该实现未生效；因此现有 `coverage`、`transport_rate` 和 `finished` 不能充分识别“严格遵守依赖”与“乱序后偶然完成”的差异。

这给 C1（DAG 路径）带来直接评价要求：若要检验依赖结构下沉，除成功率外还应报告前置未满足导致的失败、重复动作和步数；否则对顺序约束的收益可能在现有末态指标中不可见。该主张是**评测设计推论**，不是当前已获得的实验结果。

## 2.8 当前模型的已知边界

1. `ActiveMissionRegistry` 不是当前实现；真实机制是单 active admission lease。
2. 节点完成不会自动 release collaborative team fence；当前 release 主要发生在整个 Mission abort，故同 Mission 内多人节点复用受限。
3. `VERIFIED` 不应被当作 A2A/MissionGraph 的额外生命周期状态。DAG verifier 输出的 PASS/FAIL 是另一条验证循环的结果，不改变本节定义的物理/逻辑状态机。
4. 当没有 delivery adapter 时，Team ACK saga 被跳过；相关不变式的网络安装语义必须在论文中条件化。
5. 形式化只覆盖当前 `agentic` MissionRuntime 路径；`dag` 路径使用独立执行循环，不能不加证明地继承 $D$ 与 $\Pi$ 的全部性质。
