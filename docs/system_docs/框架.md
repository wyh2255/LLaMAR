# LLaMAR 系统框架

## 1. 系统概述

LLaMAR (Long-Horizon Planning for Multi-Agent Robots) 是一个**多智能体协同系统**，采用 **Coordinator-Worker（协调器-工作者）** 主从架构，基于 Google A2A (Agent-to-Agent) 协议实现智能体间通信。

系统代码位于 `src/` 和 `sar_orch/` 两大目录，Agent 框架位于 `src/Agent/`，使用自定义 ReAct 引擎。所有组件共享同一套 `src/a2a/` 传输层、`sar_orch/` SAR 实验编排和 SAR 领域工具。

## 3. A2A 传输层 (`src/a2a/`)

### 3.1 架构概览

A2A 层提供 Coordinator-Worker 通信基础设施。项目的 `src/a2a/` 通过命名空间包合并与 `site-packages/a2a/` (a2a-sdk) 组合。

### 3.2 双通道通信

| 通道 | 端口 | 协议 | 用途 |
|------|------|------|------|
| WebSocket | 8080 | JSON | 注册、心跳、任务中继、取消 |
| A2A HTTP | 8081/8090 | Protobuf JSON-RPC | 任务下发、流式响应、AgentCard 发现 |

**注册流程：**
1. Worker 启动 A2A HTTP 服务器 (端口 8090)
2. Worker 通过 WebSocket 连接 Coordinator (端口 8080)
3. Coordinator 从 `/.well-known/agent-card.json` 拉取 AgentCard
4. Coordinator 注册 Worker 能力/后端/模型

### 3.3 协调器侧 (`src/a2a/coordinator/`)

| 组件 | 文件 | 职责 |
|------|------|------|
| `CoordinatorServer` | `server.py` | FastAPI 主服务，整合所有组件 |
| `RouterAgent` | `router.py` | LLM 驱动的 DAG/Agentic 规划器 |
| `CoordinatorAgentExecutor` | `agent_executor.py` | DAG / Agentic 两种编排模式 |
| `AgentRegistry` | `agent_registry.py` | 混合注册表 (YAML + 动态 AgentCard) |
| `WorkerRegistry` | `worker_registry.py` | WebSocket 节点管理 + 心跳 |
| `TaskQueue` | `task_queue.py` | 任务状态机 (PENDING→RUNNING→COMPLETED/FAILED) |
| `TaskStore` | `task_store.py` | Agentic 编排的生命周期状态 |
| `VerifierAgent` | `verifier.py` | 可选的结果验证智能体 |
| `EventStore` | `event_store.py` | 线程安全的事件记录器 |
| `MeshGuide` | `mesh_guide.py` | Worker 间直连引导 |
| `TaskLogger` | `task_logger.py` | NDJSON 日志记录 |

#### 架构假设：Worker A2A TaskStore 为纯内存

Worker 侧 A2A server（`worker/a2a_server.py:170-176`）把 `InMemoryTaskStore()` 直接传给 `DefaultRequestHandler`，全仓没有落盘的 TaskStore 实现。由此产生以下约束：

- **生命周期**：A2A 协议层的 Task 对象只在 Worker 进程存活期间有效。Worker 进程在实验期间**不可重启**——重启后所有 in-flight task 的协议层记录全部丢失，Coordinator 侧对这些 task 的查询/取消会得到 `TaskNotFoundError`。
- **两层会话状态互不覆盖**：Worker 侧 Agent 的会话快照（`src/Agent/worker_agent/context.py` 的 `save_snapshot`/`load_snapshot`）是独立的另一层持久化，只恢复 Agent 对话历史，不恢复 A2A 协议层 Task 对象。
- **Coordinator 持久化不覆盖 Worker**：Coordinator 侧 `mission_runtime.py` 有完整的 `_persist`/`recover`/`reconcile` 机制，但只持久化 Coordinator 自己的 dispatch 状态，Worker 任务状态不在其范围内。
- **已知降级行为**：Coordinator `cancel_dispatch_remote` 在远端取消失败（如 `TaskNotFoundError`）时记录 `remote_cancel_failed` 诊断事件并返回；abort 路径使用 30 秒 bounded wait（`asyncio.wait(..., timeout=30.0)`）兜底，不会死锁。

### 3.5 内置工具 (`src/a2a/builtin_tools/`)

Agentic 模式下真正注册为 LLM 可见工具的只有下表前 6 项（`agent_executor.py:356-368`）：

| 工具 | 用途 | 模式 |
|------|------|------|
| `query_workers` | 查询在线 Worker 及能力 | 通用（Router 规划阶段单独注入） |
| `update_plan` | 声明/修改编排计划 (MissionGraph) | Agentic |
| `send_message` | 统一派发/激活/回复/取消（见 3.6 下方说明） | Agentic |
| `query_task_events` | 查询 EventStore 中 Worker 任务状态 | Agentic |
| `verify_result` | 验证输出 | Agentic |
| `query_task_results` | 查询已完成结果 | DAG（Router 内部注入）+ Agentic |

以下类仍存在于 `src/a2a/builtin_tools/` 中，但**不会**作为独立工具注册给 LLM，只被 `SendMessageTool` 内部持有并复用其执行逻辑：

| 类 | 内部角色 |
|------|------|
| `DispatchTaskTool` | `send_message(message_type="assign_task")` 底层实现 |
| `RespondWorkerTool` | `send_message(message_type="reply_to_help")` 底层实现 |
| `CancelTaskTool` | `send_message(message_type="cancel_task")` 底层实现 |
| `AssignTaskTool` | 已废弃，代码库中未见任何调用点 |

DAG 模式（`_execute_dag_loop`）不经过工具调用；`RouterAgent.push_task()` 由系统代码直接调用向 Worker 派发任务，是系统驱动而非 Agent 驱动的循环。

### 3.6 两种编排模式

| 维度 | DAG 模式 | Agentic 模式 |
|------|----------|-------------|
| 规划方式 | Router 一次性输出整个 DAG | Router 自主使用工具驱动 |
| 执行模型 | 系统驱动: 逐层并行 + 重规划 | Agent 驱动的循环 |
| 状态管理 | `completed_results` dict | `TaskStore` + PlanNode |
| 适用场景 | 结构化多步骤工作流 | 灵活自适应编排 |

## 4. Agent 框架 (`src/Agent/`)

### 4.1 架构概览

三层架构，灵感来自 DeepSeek-Reasonix Controller 设计模式：

```
┌──────────────────────────────┐
│  Controller 层               │
│  AgentController, EventSink  │
├──────────────────────────────┤
│  Agent 内核 (两层并行副本)     │
│  router_agent/  worker_agent/│
│  (中文注释)     (英文注释)    │
└──────────────────────────────┘
```

### 4.2 两个并行的 Agent 内核

`router_agent/` 和 `worker_agent/` 是两个**近乎相同的副本**。

| 维度 | `router_agent/` | `worker_agent/` |
|------|-----------------|-----------------|
| 语言 | 中文 | 英文 |
| Hook 类 | `CoordinatorSARHooks` | `WorkerSARHooks` |
| 上下文管理器 | `CoordinatorContextManager` | `WorkerContextManager` |
| 日志输出 | NDJSON `.ndjson` | NDJSON `.ndjson` |
| OpenAI 客户端 | 无额外参数 | `extra_body: {"reasoning_split": True}` |
| NeedInputError | 不支持 | 支持 (暂停/恢复工作流) |
| 构建入口 | `build_router_agent()` | `build_agent()` |

### 4.3 Agent.run() 核心循环

```
步进循环 (max_steps):
  1. 安全检查点 (取消/继续?)
  2. Token 预算检查 → 必要时压缩历史
  3. Hook: pre_llm() → 组装上下文记忆
  4. LLM.generate(messages, tools)
  5. 累计 token 使用量
  6. Hook: post_llm()
  7. step_callback("llm_response")
  8. 若 LLM 无工具调用 → 退出
  9. 遍历 tool_calls:
     a. step_callback("tool_start")
     b. Hook: pre_tool()
     c. tool.execute(**args)
     d. Hook: post_tool() → 更新 pinned 状态
     e. step_callback("tool_result")
     f. 检查 task_complete 标志
```

### 4.4 上下文管理

三层记忆模型：

| 层级 | 内容 | 限制 |
|------|------|------|
| **Pinned 状态** | 结构化键值事实 (位置、库存、已知火灾等) | 每次工具执行后更新 |
| **Episodic 记忆** | 压缩后的历史工具片段 | 最多 20 条 |
| **Recent 窗口** | 原始 assistant/tool 消息 | 最近 12 条 |

### 4.5 Controller 编排层 (`src/Agent/controller/`)

`AgentController` 是前端无关的编排器：
- 管理会话 (`context_id` -> `ContextManager` 映射)
- 并发控制 (每个 `context_id` 一把 `asyncio.Lock`)
- 通过 `agent_factory` 回调创建 Agent
- 输出通道: `EventSink` 协议 (llm_response / tool_start / tool_result)

| 工具 | 类 | 功能 |
|------|-----|------|
| `read_file` | `ReadTool` | 读取文件 |
| `write_file` | `WriteTool` | 写入文件 |
| `edit_file` | `EditTool` | 精确替换 |

## 5. SAR 编排层 (`sar_orch/`)

### 5.1 四组件管道

```
experiment.py
  ├── SARBarrier     (包裹 SAREnv, 多智能体回合同步)
  ├── SARCoordinator (包裹 A2A CoordinatorServer + SAR 工具)
  ├── SARWorker × N  (包裹 A2A Worker 服务 + SAR 工具)
  ├── ExperimentLogger (线程安全 CSV 日志)
  └── 环境步骤轮询
```

### 5.2 数据流

```
SARCoordinator (RouterAgent)
  → send_message(assign_task/activate_plan_node) → A2A 协议
    → SARWorker × N (Agent/worker_agent 的 ReAct WorkerAgent)
      → NavigateTo / GetSupply / UseSupply 等工具
        → barrier.submit_action(agent_idx, action)
          → SAREnv.step(actions)
            → generate_obs_text()
              → 观测返回 Worker LLM
```

### 5.3 SARBarrier 线程模型

| 原语 | 用途 |
|------|------|
| `threading.Event` (按 agent) | 跨线程唤醒信号 |
| `threading.Lock` | 防止 `_execute_step()` 并发执行 |
| `STEP_TIMEOUT = 60s` | 超时自动填充 NoOp |

**步进生命周期：**
1. Worker 调用 `submit_action(idx, action)` → 存储动作
2. 全部提交 → 调度 `_execute_step()`
3. `env.step(actions)` → 生成观测 → 设置所有 Events → Worker 唤醒
4. 超时: 60s 后自动填充 NoOp

## 9. 关键设计决策

| 决策 | 原因 |
|------|------|
| router_agent/ 和 worker_agent/ 代码重复 | 允许各自独立演化 (worker 支持 NeedInputError, router 不需要)|
| Barrier 使用 threading 而非 asyncio 原语 | Worker 运行在不同线程的独立 asyncio 事件循环中 |
| .env 字段必须小写 | 框架统一读取逻辑 |
| `step_callback` 作为唯一输出通道 | 解耦 Agent 内核与前端 (A2A/CLI/实验) |
| `get_agent_state` 不消耗步数 | 零成本 GPS 查询，避免 LLM 因位置感知而浪费步数 |
| NavigateTo 是瞬移 | SAR GridEngine 直接 set_position()，无需路径规划 |
| 增量写入 summary.csv | 进程崩溃时保留最新数据 |
