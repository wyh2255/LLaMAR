# LLaMAR 系统框架

## 1. 系统概述

LLaMAR (Long-Horizon Planning for Multi-Agent Robots) 是一个**多智能体协同系统**，采用 **Coordinator-Worker（协调器-工作者）** 主从架构，基于 Google A2A (Agent-to-Agent) 协议实现智能体间通信。

系统代码位于 `src/` 和 `sar_orch/` 两大目录，Agent 框架位于 `src/Agent/`，使用自定义 ReAct 引擎。所有组件共享同一套 `src/a2a/` 传输层、`sar_orch/` SAR 实验编排和 SAR 领域工具。

## 3. A2A 传输层 (`src/a2a/`)

### 3.1 架构概览

A2A 层提供 Coordinator-Worker 通信基础设施。项目的 `src/a2a/` 通过命名空间包合并与 `site-packages/a2a/` (a2a-sdk) 组合。

### 3.2 双通道通信

| 通道 | 端口 | 协议 | 用途 |
|------|------|------|------|
| WebSocket | 8080 | JSON | 注册、心跳、任务中继、取消 |
| A2A HTTP | 8081/8090 | Protobuf JSON-RPC | 任务下发、流式响应、AgentCard 发现 |

**注册流程：**
1. Worker 启动 A2A HTTP 服务器 (端口 8090)
2. Worker 通过 WebSocket 连接 Coordinator (端口 8080)
3. Coordinator 从 `/.well-known/agent-card.json` 拉取 AgentCard
4. Coordinator 注册 Worker 能力/后端/模型

### 3.5 内置工具 (`src/a2a/builtin_tools/`)

Agentic 模式下真正注册为 LLM 可见工具的只有下表前 6 项（`agent_executor.py:356-370`）：

| 工具 | 用途 | 模式 |
|------|------|------|
| `query_workers` | 查询在线 Worker 及能力 | 通用（Router 规划阶段单独注入） |

| `verify_result` | 验证输出 | Agentic |
| `query_task_results` | 查询已完成结果 | DAG（Router 内部注入）+ Agentic |

以下类仍存在于 `src/a2a/builtin_tools/` 中，但**不会**作为独立工具注册给 LLM，只被 `SendMessageTool` 内部持有并复用其执行逻辑：

| 类 | 内部角色 |
|------|------|
| `DispatchTaskTool` | `send_message(message_type="assign_task")` 底层实现 |
| `RespondWorkerTool` | `send_message(message_type="reply_to_help")` 底层实现 |
| `CancelTaskTool` | `send_message(message_type="cancel_task")` 底层实现 |

### 3.6 两种编排模式

| 维度 | DAG 模式 | Agentic 模式 |

| 状态管理 | `completed_results` dict | `TaskStore` + PlanNode |

## 4. Agent 框架 (`src/Agent/`)

### 4.1 架构概览

三层架构，灵感来自 DeepSeek-Reasonix Controller 设计模式：

```
┌──────────────────────────────┐
│  Controller 层               │
│  AgentController, EventSink  │
├──────────────────────────────┤
│  Agent 内核 (两层并行副本)     │
│  router_agent/  worker_agent/│
│  (中文注释)     (英文注释)    │
└──────────────────────────────┘
```

### 4.2 两个并行的 Agent 内核

`router_agent/` 和 `worker_agent/` 是两个**近乎相同的副本**。

| 维度 | `router_agent/` | `worker_agent/` |
|------|-----------------|-----------------|
| 语言 | 中文 | 英文 |
| Hook 类 | `CoordinatorSARHooks` | `WorkerSARHooks` |
| 上下文管理器 | `CoordinatorContextManager` | `WorkerContextManager` |
| 日志输出 | NDJSON `.ndjson` | NDJSON `.ndjson` |
| OpenAI 客户端 | 无额外参数 | `extra_body: {"reasoning_split": True}` |
| NeedInputError | 不支持 | 支持 (暂停/恢复工作流) |
| 构建入口 | `build_router_agent()` | `build_agent()` |

### 4.3 Agent.run() 核心循环

```
步进循环 (max_steps):
  1. 安全检查点 (取消/继续?)
  2. Token 预算检查 → 必要时压缩历史
  3. Hook: pre_llm() → 组装上下文记忆
  4. LLM.generate(messages, tools)
  5. 累计 token 使用量
  6. Hook: post_llm()
  7. step_callback("llm_response")
  8. 若 LLM 无工具调用 → 退出
  9. 遍历 tool_calls:
     a. step_callback("tool_start")
     b. Hook: pre_tool()
     c. tool.execute(**args)
     d. Hook: post_tool() → 更新 pinned 状态
     e. step_callback("tool_result")
     f. 检查 task_complete 标志
```

### 4.4 上下文管理

三层记忆模型：

| 层级 | 内容 | 限制 |
|------|------|------|
| **Pinned 状态** | 结构化键值事实 (位置、库存、已知火灾等) | 每次工具执行后更新 |
| **Episodic 记忆** | 压缩后的历史工具片段 | 最多 20 条 |
| **Recent 窗口** | 原始 assistant/tool 消息 | 最近 12 条 |

### 4.5 Controller 编排层 (`src/Agent/controller/`)

`AgentController` 是前端无关的编排器：
- 管理会话 (`context_id` -> `ContextManager` 映射)
- 并发控制 (每个 `context_id` 一把 `asyncio.Lock`)
- 通过 `agent_factory` 回调创建 Agent
- 输出通道: `EventSink` 协议 (llm_response / tool_start / tool_result)

## 5. SAR 编排层 (`sar_orch/`)

### 5.1 四组件管道

```
experiment.py
  ├── SARBarrier     (包裹 SAREnv, 多智能体回合同步)
  ├── SARCoordinator (包裹 A2A CoordinatorServer + SAR 工具)
  ├── SARWorker × N  (包裹 A2A Worker 服务 + SAR 工具)
  ├── ExperimentLogger (线程安全 CSV 日志)
  └── 环境步骤轮询
```

### 5.2 数据流

```
SARCoordinator (RouterAgent)
  → send_message(assign_task/activate_plan_node) → A2A 协议
    → SARWorker × N (Agent/worker_agent 的 ReAct WorkerAgent)
      → NavigateTo / GetSupply / UseSupply 等工具
        → barrier.submit_action(agent_idx, action)
          → SAREnv.step(actions)
            → generate_obs_text()
              → 观测返回 Worker LLM
```

### 5.3 SARBarrier 线程模型

| 原语 | 用途 |
|------|------|
| `threading.Event` (按 agent) | 跨线程唤醒信号 |
| `threading.Lock` | 防止 `_execute_step()` 并发执行 |
| `STEP_TIMEOUT = 60s` | 超时自动填充 NoOp |

**步进生命周期：**
1. Worker 调用 `submit_action(idx, action)` → 存储动作
2. 全部提交 → 调度 `_execute_step()`
3. `env.step(actions)` → 生成观测 → 设置所有 Events → Worker 唤醒
4. 超时: 60s 后自动填充 NoOp

### 5.7 TaskWatchdog 监督环

`TaskWatchdog`（`task_watchdog.py:42`）固定在 Coordinator event loop 内运行，只生成去重后的 actionable 事件，不自动取消或重派任务。

**配置（`WatchdogConfig`，`task_watchdog.py:30-39`，全部由系统给出、不由 LLM 创建）：**

| 阈值 | 默认值 |
|------|--------|
| `task_stale_seconds` | 120.0 |
| `worker_unreachable_seconds` | 120.0 |
| `deadline_warning_seconds` | 300.0 |
| `task_hard_deadline_seconds` | 600.0 |
| `watchdog_tick_seconds` | 5.0 |
| `grace_period_seconds` | 10.0 |
| `no_progress_step_threshold` | 3 |

**事件类型（写入 `SupervisionStateStore` + EventStore `supervision_event`，并经 `SupervisionEventAdapter` 进 canonical Memory）：**

| 事件 | 触发条件 | 代码位置 |
|------|----------|----------|
| `WORKER_UNREACHABLE` | WorkerRegistry last_contact 超 `worker_unreachable_seconds` | `task_watchdog.py:313-337` |
| `TASK_STALE` | 进展时间超 `task_stale_seconds` 或无进展步数 ≥ `no_progress_step_threshold` | `task_watchdog.py:365-390` |
| `TASK_DEADLINE_EXCEEDED` | 运行时长超 `task_hard_deadline_seconds` | `task_watchdog.py:408-429` |
| `TASK_DEADLINE_WARNING` | 运行时长超 `deadline_warning_seconds` | `task_watchdog.py:438-459` |

**进展刷新规则（只有真实进展才重置 stale 计时）：**

- A2A push callback 的 terminal 状态更新（`record_state_change`，`task_watchdog.py:537`；INPUT_REQUIRED 也刷新进展，`task_watchdog.py:562-565`）
- `artifact_update` 回调（`server.py:1704` `record_progress(source="artifact_update")`）
- `observation_report` 回调（`server.py:1110` `record_progress(source="observation_report")`）
- 领域指标变化：barrier `coverage` / `transport_rate` / `finished` 任一变化（`_refresh_progress_by_domain_delta`，`task_watchdog.py:261-301`）；环境 step 增长本身不算进展
- 首次 tick 只建立基线（防任务创建于环境中期时误报 STALE，`task_watchdog.py:294-300`）

消费路径：`SARCoordinatorStateProvider._build_supervision_view`（`coordinator_state_provider.py:794`）把 alerts/unacknowledged_events 并入 RuntimeState payload["supervision"]，Coordinator 下一次 pre_llm 时读取。

### 5.8 System Health 诊断通道（DiagnosisLoop）

诊断通道是滚动反思的第二通道（并存不替代）：有界、同步、多轮审查者，消费一个 scope 的已提交证据并产出 `DiagnosisCandidateV1`。

- **循环**：`DiagnosisLoop`（`sar_orch/diagnosis_loop.py:198`），每轮一次 LLM function-call（`record_diagnosis` 置于 `tools[0]`），轮间工具结果回喂；`max_rounds`/`diagnosis_sec` 双预算（`DiagnosisConfig`，`memory/contracts.py:861-878`：代码默认 max_rounds=3、diagnosis_sec=90；当前仓库运行配置 `long_term.config` [diagnosis] 段 diagnosis_sec=150，`load_diagnosis_config`，`contracts.py:1077`）。
- **四件只读工具**（`sar_orch/tools/coordinator/`）：`query_projection`（spatial/embodied 投影）、`query_temporal_flow`（时序事件流，R6 过滤 `diagnosis.*` 审计事件）、`query_supervision`（监督事件计数）、`query_control_journal`（控制迁移日志）。
- **独立诊断 port**（cb54b06 @08-17）：诊断不复用滚动反思的 `ReflectionModelPort`；`experiment.py:676-678` 按 `diagnosis_sec` 构造独立 `diagnosis_model_port`，每轮按剩余全局预算临时收紧 timeout，调用结束恢复原值；反思通道默认 300 秒行为不变。
- **注入**：coordinator-only `### System Health` 段（`Agent/environment_state.py:130`），由 `EnvironmentStateProvider._system_health_section`（`environment_state_provider.py:490`）按 `min_confidence`（D4，默认 0.6）过滤、同 target 保留最高置信；`inject_enabled` 为独立消融开关（A2）。
- **D8 语义**：增强非必需、绝不阻塞——缺 store/config/port 是 typed skip（`_run_diagnosis_channel`，`long_term_reflection.py:320-375`）；超时/结构违规 fail-closed 零写入（`validate_diagnosis_response`，`memory/diagnosis.py:292`）；诊断结果只附加在 reflection 结果的 `diagnosis` 字段，永不替换反思状态。
- **触发**：与滚动反思共享触发点与 coalesce 槽位——每 task 完成 / 每 supervision 事件 / 每 `every_env_step`（默认 5）个 env step（`experiment.py:867-895`，`long_term.config` [trigger] 段）。

### 6.2 per-run 回调密钥机制

- 实验入口每次 run 生成 32 字节 per-run 密钥：`experiment.py:541` / `experiment.py:550`（`secrets.token_bytes(32)`），分发给 SARCoordinator（`experiment.py:630`）与全部 SARWorker（`experiment.py:730`）。
- 校验下限 16 bytes：worker 侧 `MIN_COORDINATOR_SECRET_LENGTH = 16`（`sar_orch/worker.py:19`，构造即校验 `worker.py:77-87`）；coordinator 侧 `configure_memory` 对 shadow/read_port 强制 secret ≥16 bytes 否则 `memory_auth_not_configured` fail-closed（`server.py:679-682`）。
- 独立 worker CLI 从受保护本地配置解析：`.env` 的 `coordinator_secret` 或环境变量 `A2A_COORDINATOR_SECRET`（`worker/cli.py:73-86`）。
- 运行期：Worker 的 push callback 由 `CallbackSigner` 对每次请求体签名（`src/a2a/worker/callback_sender.py:35-36,68`，头 `X-A2A-Callback-Proof` + `X-A2A-Worker-Id`）；Coordinator 在 `/a2a/push-callback` 路由前端验证 proof → 解析可信 control state（active runtime + dispatch + worker 匹配）→ durable nonce 预留（`callback_nonce` UNIQUE 防重放）→ 脱敏后才扇出给任何 writer（`server.py:1556-1618`）。proof 失败产生零域写入，只留脱敏安全审计。

### 6.3 长期记忆（long-term memory）read 正式可用

G4 审批后（c866cc3 @08-12 / 32bfe57 @08-13）`--long-term-mode read` 为正式可用档位（`experiment.py:1157-1166`，默认 `off`；`shadow`/`read` 都从 committed snapshot 持久化发布产物，`read` 额外注入 Context）。

- **注入**：coordinator-only `### Long-term Memory` 段（标题注册 `Agent/environment_state.py:134`；渲染 `environment_state.py:189-211`）。ACL 判定在 provider：`_is_system && long_term_mode == "read"` 才挂 `long_term_memory` key（`environment_state_provider.py:441-442`），worker viewer 永不可见。
- **预算截断序**（`SECTION_PRIORITY`，`environment_state_provider.py:43-57`）：Task > Spatial > Embodied > System Health > Long-term > Temporal(relevant_events) > Freshness；固定上限段（system_health / long_term_memory，阈值档 3）被裁时显式标记 TRUNCATED，绝不静默消失（`_apply_budget`，`environment_state_provider.py:519-561`）。
- **存储**：`<memory_root>/long_term/long_term.sqlite3`（`contracts.py:846-847`），run-local，随 run 目录走。
- **组合约束**：`memory_read_mode="shadow"` + `long_term_mode="read"` 被禁止（fail-closed，`sar_orch/coordinator.py:23-37`）。
- **滚动反思触发**：每 task 完成 / 每 supervision 事件 / 每 `every_env_step`（默认 5）个 env step + `min_interval_sec`（默认 30）节流 + in-flight coalesce（`long_term.config` [trigger] 段；`LongTermRuntimeConfig`，`contracts.py:943-955`；触发点 `experiment.py:867-895`）。

### 6.4 System Health 诊断通道

见 5.8（DiagnosisLoop）；诊断产物（`DiagnosisCandidateV1`）写 run-local `diagnosis.sqlite3` 并追加一条 canonical `diagnosis.audit` 时序事件（`diagnosis_loop.py:453`），审计事件永不进入反思输入窗口（collector 前缀不含 `diagnosis.`）也不进入 `query_temporal_flow` 视图（R6 过滤）。

## 10. 关键设计决策

| 决策 | 原因 |
|------|------|
| router_agent/ 和 worker_agent/ 代码重复 | 允许各自独立演化 (worker 支持 NeedInputError, router 不需要)|
| Barrier 使用 threading 而非 asyncio 原语 | Worker 运行在不同线程的独立 asyncio 事件循环中 |
| .env 字段必须小写 | 框架统一读取逻辑 |
| `step_callback` 作为唯一输出通道 | 解耦 Agent 内核与前端 (A2A/CLI/实验) |
| `get_agent_state` 不消耗步数 | 零成本 GPS 查询，避免 LLM 因位置感知而浪费步数 |
| NavigateTo 是瞬移 | SAR GridEngine 直接 set_position()，无需路径规划 |
| 增量写入 summary.csv | 进程崩溃时保留最新数据 |
| Memory 为一等公民、read_port 默认（H3） | canonical SQLite 单库是唯一真值源；legacy 路径仅作回滚目标，read-port 失败一次性回滚闩保证不混用两种真值 |
| push callback 必须带 body 绑定 HMAC proof + durable nonce | 防伪造/防重放，认证失败零域写入（fail-closed） |
| 长期记忆/诊断仅 coordinator-only 注入 | worker 上下文预算与真值边界（H1/H2）：发布产物不得影响 worker 行为 |
| 诊断通道 fail-closed、绝不阻塞（D8） | System Health 是增强非必需：typed skip / 超时丢弃，run 退出路径永不被诊断阻塞 |
| 监督阈值全部系统给出（WatchdogConfig） | 不由 LLM 创建阈值，防止监督环被被监督者操纵 |
