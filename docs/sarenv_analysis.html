摘要

SAREnv 是 LLaMAR 框架中搜索与救援（Search & Rescue）实验环境的主类，定义于 SAR/env.py。它继承自 SARBaseEnv（SAR/base_env.py），封装了 SAR 核心引擎的 Controller，提供与 AI2Thor 环境一致的统一接口。该类承担四大职责：（1）管理智能体生命周期与状态追踪；（2）生成 LLM 可读的观测文本与状态描述；（3）分发动作执行并收集结果；（4）维护子任务、记忆和历史记录。

在 LLaMAR 的 Plan-Act-Correct-Verify 循环中，SAREnv 作为环境抽象层，为 Planner、Actor、Verifier 三个 LLM 模块提供结构化输入，并通过 step() 方法执行动作、更新状态。llamar.py 作为实验主入口，通过 env.step(action) 驱动整个循环。

§3 方法详解

3.1 __init__(self, num_agents, scene=1, seed=42, save_frames=False)

构造函数，完成环境的基本配置但不创建控制器。控制器的创建延迟到 reset() 调用时执行。

  • num_agents：智能体数量，范围 1-6，对应 AGENT_NAMES 列表中的前 N 个名称
  • scene：场景编号（1-5），决定加载哪个场景定义
  • seed：随机种子，同时设置到 SARBaseEnv.seed 以确保探索行为可重复
  • save_frames：是否在每一步保存渲染帧图像到磁盘

关键状态：self.initialized = False，在 reset() 后变为 True。step() 会检查此标志，未初始化时抛出断言错误。

3.2 reset(self)

重置并完整初始化环境，是环境生命周期的起点。执行流程：

  1. 设置 self.initialized = True
  2. 通过 get_scene_initializer(scene) 获取场景初始化器和检查器类
  3. 创建场景初始化器实例，获取任务超时时间和任务描述
  4. 调用 preinit() 创建控制器（Controller）和场景参数（pg_params）
  5. 创建任务完成度检查器（Checker）
  6. 初始化所有状态追踪变量：子任务列表、记忆列表、动作历史、成功历史等
  7. 调用 update_current_state() 设置初始观测
  8. 设置渲染图像和动作记录的保存路径

返回值：格式化后的初始输入字典字符串（通过 SARBaseEnv.convert_dict_to_string() 转换）。

3.3 update_current_state(self, act_texts: List[str])

核心状态更新方法，为每个智能体刷新 LLM 输入字典（self.input_dict）。在 step() 末尾调用，确保下一步的 LLM 输入包含最新信息。

对每个智能体，更新以下字段：

  • {name}'s observation：当前观测文本（由 generate_obs_text() 生成）
  • {name}'s state：当前状态描述（由 get_agent_state() 生成）
  • {name}'s previous observation：上一步的全局观测名称列表
  • {name}'s previous action：上一步的动作文本描述
  • {name}'s previous failures：之前的失败动作描述

同时更新共享字段：子任务（subtasks）、记忆（memory）、开放子任务（open_subtasks）、已完成子任务（closed_subtasks）。

3.4 generate_obs_text(self, agent_idx)

生成指定智能体的观测文本，是 LLM 提示中最关键的信息来源。分为两个层次：

  • 局部观测（local_obs）：智能体周围各方向（Up/Down/Left/Right 及对角线）的可观察物体。可燃物显示强度和所属火源名称，障碍物标记为 'Obstacle'，空方向标记为 'Empty'
  • 全局观测（global_obs）：智能体视野内所有已知物体的详细描述和名称列表。过滤掉非区域名的火对象以避免冗余

返回值：(obs_text, global_obs_list) -- 格式化的完整观测文本 和 仅含名称的全局观测列表（用于历史记录）。

3.5 get_agent_state(self, agent_idx: int)

返回描述智能体当前状态的简洁文本，格式为：

"I am at co-ordinates: (x, y) and I am holding {'Sand': n1, 'Water': n2, 'Person': n3}."

通过 controller.get('agents', agent_idx) 获取位置，controller.get_inventory(agent_idx) 获取库存。

3.6 step(self, actions)

环境的核心方法，为所有智能体执行动作序列并更新状态。这是 llamar.py 主循环中驱动环境前进的关键调用。

执行流程（每个智能体）：

  1. 处理 SendMessage 通信消息（直接标记成功）
  2. 调用 parse_action() 将动作字符串解析为控制器参数
  3. Explore 动作会展开为多个 Move 子步骤批量执行
  4. 通过 controller.step(**kwargs) 执行动作
  5. 记录成功/失败状态，更新失败动作集合
  6. 调用 checker.perform_metric_check() 验证任务进度
  7. 生成动作执行结果文本

DropOff 特殊处理：如果任一智能体的 DropOff 成功，所有执行 DropOff 的智能体都标记为成功（协同搬运语义）。

返回值：(格式化后的输入字典字符串, 各智能体动作成功状态列表)

3.8 辅助方法

  • update_memory(memory, agent_idx)：更新指定智能体的记忆列表
  • update_subtask(subtask, agent_idx)：更新指定智能体的子任务列表
  • update_plan(plan)：更新全局规划文本
  • get_id(name)：根据对象可读名称查询其唯一 ID，委托给 controller.get_id()
  • render(save_path, show)：调用 utils.render() 绘制环境俯视图
  • save_frame()：将当前帧保存为 PNG，文件名格式 frame_{step_num}.png
  • _create_path(pth)：创建目录路径（如不存在）

§4 llamar.py 调用分析

4.1 调用流程

llamar.py 是 SAR 实验的主入口脚本，实现了 LLaMAR 的 Plan-Act-Verify 循环。以下展示 SAREnv 在整个流程中的调用点：

llamar.py 主流程中的 SAREnv 调用

// 阶段 0：初始化
env = SAREnv(num_agents, scene, seed, save_frames=True)   // 创建环境实例
env.reset()                                              // 重置环境、创建控制器
timeout = env.task_timeout                               // 读取任务超时步数
logger = SARLogger(env=env, ...)                         // 日志器引用 env

// 阶段 1：初始规划（仅执行一次）
response = get_gpt_response(env, config, "planner")      // 内部调用 env.get_planner_llm_input()
outdict = get_action(response)

// 阶段 2：主循环（Plan → Act → Verify）
for step_num in range(timeout):

    // 2a. 更新计划
    update_plan(env, outdict["plan"], env.closed_subtasks)

    // 2b. Actor — LLM 选择动作
    response = get_gpt_response(env, config, "action")   // 内部调用 env.get_action_llm_input()
    action = action_mapping(env, preaction)               // 内部调用 env.get_id()

    // 2c. 更新智能体状态
    env.update_subtask(subtask, 0)
    env.update_memory(memory, 0)

    // 2d. 执行动作
    d1, successes = env.step(action)                      ★ 核心调用

    // 2e. Verifier — LLM 判断完成情况
    response = get_gpt_response(env, config, "verifier") // 内部调用 env.get_verifier_llm_input()
    env.closed_subtasks = outdict["completed subtasks"]   // 直接写入已完成子任务
    env.get_planner_llm_input()                           // 刷新 Planner 输入

    // 2f. Planner — LLM 更新计划
    response = get_gpt_response(env, config, "planner")  // 内部调用 env.get_planner_llm_input()

    // 2g. 统计指标
    coverage    = env.checker.get_coverage()
    transport   = env.checker.get_transport_rate()
    finished    = env.checker.check_success()

// 阶段 3：清理
env.stop()                                               // 停止环境

4.2 使用模式

模式 1：环境生命周期管理

llamar.py 遵循标准的"创建-重置-使用-停止"模式：

  • 构造时仅做配置（不创建控制器）
  • reset() 完成全部初始化，返回初始状态字符串
  • 主循环中通过 step() 驱动环境
  • 结束时调用 stop() 释放资源

模式 2：LLM 输入获取

三个 LLM 模块（Planner、Actor、Verifier）通过各自的输入方法获取结构化字典，这些字典在 get_gpt_response() 内部被转换为 LLM 提示文本：

  • get_planner_llm_input()：返回任务 + 观测 + 子任务进度
  • get_action_llm_input()：返回任务 + 观测 + 状态 + 动作历史 + 失败信息 + 记忆
  • get_verifier_llm_input()：返回任务 + 观测 + 状态 + 动作历史 + 记忆

模式 3：状态直接写入

llamar.py 在 Verifier 阶段后直接修改 env.closed_subtasks 和 env.input_dict，而非通过专用方法。这种模式虽然简洁，但破坏了封装性：

  • env.closed_subtasks = outdict["completed subtasks"] -- 直接赋值已完成子任务
  • env.input_dict["Robots' completed subtasks"] = env.closed_subtasks -- 同步到输入字典

模式 4：错误重试机制

llamar.py 对每次 LLM 调用都使用 while not success: try-except 循环，处理 JSON 解析错误等异常。SAREnv 本身不涉及此逻辑，但其返回的字典格式必须与 get_action() 的解析逻辑兼容。

模式 5：SAREnv 方法在 llamar.py 中的调用频率

表 6：每步循环中 SAREnv 方法的调用次数

方法 每步调用次数 调用位置
get_planner_llm_input 1-2次 Verifier后刷新 + Planner调用
get_action_llm_input 1次 Actor阶段
get_verifier_llm_input 1次 Verifier阶段
step 1次 动作执行阶段
update_subtask 1次 Actor后更新
update_memory 1次 Actor后更新
checker.get_coverage 1次 统计阶段
checker.check_success 1次 统计阶段
