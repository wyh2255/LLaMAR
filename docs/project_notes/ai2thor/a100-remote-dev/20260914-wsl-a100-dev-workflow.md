# 2026-09-14 双机开发分工建议（WSL 侧 vs A100 侧）

> 状态：**已拍板（09-14 晚）**——用户确认原话：「我同意在 WSL 侧主开发，A100 侧主执行」。
> 包：本文件属 `.hermes/spec/a100-remote-dev/` 包（入口 `README.md`）。

## 背景
- 用户问：「是我在 WSL 远程开发好，还是直接在 A100 上面开发好？」
- 语境：A100 首跑全绿（见 `20260914-a100-remote-worker-channel.md`）；下一阶段 = 真机行为调优 + 框架修复迭代；A100 为共享/易抖主机（当日已见：驱动错配、glvnd 缺失、文件系统卡壳、reboot-required）。
- 用户同期定下方向：「A100 很可能会有时候出现故障，要及时做好 commit+push」。

## 讨论要点
- 真机 run 成本低（≈2.6s/回合；8 步 28s、50 步 132s）→「同机编辑-运行」的提速收益有限；跨机节奏 = push → pull → run，仅多两条命令。
- 稳定性不对称：A100 故障 = 未推成果丢失风险（用户点名）；WSL 侧 = 本机（代码 + 编排层 + kanban + 评测工具链全在此；260 个 fake 回归单测本机可跑）。
- 工具链不对称：修复/审查/评测/文档/编排在 WSL 侧成熟；GPU 仅 A100 有（任何真机验证都得上 A100）。
- 谁都不锁死：origin = GitHub 为唯一真源 → 两侧可随时接手。

## 建议（已拍板）
- **默认分工：WSL 侧 = 主开发场（改码 / 修复 / 评测 / 文档 / 编排）；A100 = 真机执行场（unity 验证 / sweep）**。
- **例外窗口**：连续真机行为调试（改一点 → 跑一跑）允许就地在 A100 进行（同机效率高）——但每完成一个小点即 commit+push。
- **三条纪律（两侧通用）**：
  1. 开工先 `git pull --ff-only`；
  2. 小步推：一个能跑通的改动就 commit+push、不过夜；
  3. A100 上不留「只此一份」的成果——产物/日志尽快回传提交（首跑报告即此例，已归档 `e8d127e`）。
